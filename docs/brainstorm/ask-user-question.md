# B1：结构化询问用户工具

状态：方向已定（human 2026-10-23），B2 草案见 [blueprints/ask-user-question.md](../blueprints/ask-user-question.md)。

## 目标

请求、代码和合理默认值都不足以解决、必须由用户决定的分歧，agent 用结构化问题提出；候选答案帮用户组织语言，用户点选或直接打字回答。不用于计划批准、操作授权或确认是否继续。

## 已定方向

- **问题与展示分开**：core 只认问题本身；各渠道按自己的方式展示。Web 用会话内卡片，微信用文字。工具只开放给有人能回答的会话，定时触发和子 agent 不开放。
- **提问即结束本轮**：
  - 提问后 run 正常结束，不挂着等待；这时轮到人，会话按未读处理。
  - 用户的回答就是下一条普通用户输入。模型在新一轮里结合自己的提问理解回答。
  - 因此没有等待状态、取消竞争或重启恢复的问题；微信不需要单独做一套。
- **提问单独调用**：
  - 有没想清楚、要问用户的事，就不该同时做别的。description 用轻提示说明：提问时不要并行调用其他工具。
  - 模型仍然在同一批里带了其他调用时，那些调用不执行，返回一句简短说明，让模型拿到回答后再调用。
- **下一条输入即回答**：问题出现后，这个会话的下一条用户输入就是对它的回答，无论用户是点卡片还是直接打字。
- **形式**：
  - 最多 4 题，每题 2–4 个选项，单选或多选；界面统一提供「其它」自由输入。
  - 选项用 1/2/3/4 编号。
  - 第一个选项是推荐项，界面默认选中。
  - 沿用 Claude Code AskUserQuestion 的模式，description 和回答格式先照抄再按 micnext 调整（见下）。
- **Web**：
  - 每题一张小卡片，手机上纵向排列；点选后点「提交」，一次交整组回答。
  - 提交后把选择组织成一条普通用户消息发出，卡片随即不再可操作。
  - 用户也可以不点卡片，直接在输入框里回答。
- **微信**：
  - 问题和带编号的选项以文字发出；用户按题序回 `1 1 3 2` 这类简写或直接打字，由模型理解。
  - 文字排版实在不好读时，再考虑拼成一张图片发出。首版先用文字。
- **首版不做**：preview、annotations、metadata，以及计划模式联动。

## 参考：Claude Code 的写法

**description**（AskUserQuestion 原文要点，B2 改写成中文并删去 Plan mode 部分）：

- 只在被一个真正需要用户决定的问题卡住时使用：请求、代码或合理默认值都无法解决。
- 有惯例做法或能自己查证的事实，不要问，直接选显而易见的做法并在回复里说明。
- 用户总能选「Other」自由输入，不要自己生成「其它」选项。
- 有推荐项时放第一位，标签末尾加「（推荐）」。
- 不要用它问「方案可以吗」「要不要继续」这类确认。

**参数**：`questions[]`，每题有 `question`（完整问句，以问号结尾）、`header`（极短标签）、`options[]`（2–4 个，每项 `label` 1–5 个词加 `description` 说明取舍）、`multiSelect`。

**回答格式**：工具结果是 `User has answered your questions: "问题"="答案", …`，多选用逗号连接，自由输入原样放入。micnext 里这段改为 Web 提交时组织出的用户消息正文，例如：

```
「问题一」→ 选项标签
「问题二」→ 选项A、选项C
「问题三」→ 其它：用户自填文字
```

提问本身的工具结果只给模型一句「已向用户提问，等待回答」。

## B2 待明确

- run 在提问批次后怎样结束；同批其他调用如何打回。
- 「当前有待回答问题」从已有消息推导（最近一次提问之后还没有用户输入），不另建状态。
- 未读：以提问结束的 run 要能点亮侧栏未读点。现在未读只看 `Reply` 和 `Notification`，需要决定提问用什么消息事实来算。
- Web 卡片的样式和回答后的只读态。
- 微信的文字排版。
