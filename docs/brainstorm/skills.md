# B1：Skill 加载，以及缓存冷了以后整理历史

**状态：梳理中（2026-10-27）；Skill 加载见 [B2](../blueprints/skills.md)，冷时整理另立 B2。** 前作：[next-gen-architecture](next-gen-architecture.md) 待办 15（Skill 注入粒度）、[compaction-retention](compaction-retention.md)（压缩时把旧工具输出换成占位）。

## 现状

- 系统提示由三块组成，顺序固定：`instructions` → `persona` → `context`（`crates/mic-core/src/request.rs`），这样同一会话的前缀保持稳定。
- 只有压缩时才改历史：压缩本身就会让前缀失效一次，所以趁这时把旧工具输出换成占位。平时历史只追加，不改动。
- 有一个现成的先例：定时任务触发时，如果上下文占用超过 50%，先压缩再跑（`SCHEDULE_COMPACT_PERCENT`）。距离上次调用已经很久，缓存本来就冷了，这时压缩不会多损失缓存。

## 一、Skill 本体

### 来源

只设一个目录：`<数据目录>/skills/<name>/SKILL.md`，按开放规范只读 `name`、`description` 和正文，附带的脚本、参考资料放在同一目录。单用户场景不分项目级、用户级、组织级。agent 可以用现有的 fs 工具自己写 skill。

待定：要不要再扫会话工作目录下的 `.agents/skills`，好让仓库里的 skill 跟着仓库走。有实际需要再加。

### 目录放在哪

在 `context` 块里加一段 Skill 目录，每项一行：名称加描述。每次请求按磁盘现状渲染。

- 增删或修改 skill 的描述会改变前缀，导致一次缓存失效。这种情况很少，可以接受。
- 也可以只在缓存冷的时候或边界处刷新目录（见第三节），但这样要另外存一份目录快照。先不做。
- skill 数量多到目录本身太长时，再考虑预算和检索。个人使用短期内用不到。

### 怎么加载正文

| 方式 | 做法 | 取舍 |
|---|---|---|
| 模型自己用 `read` 读文件 | 目录里写上路径 | 不用写新代码；但区分不了哪次读取是加载 skill，没法去重，上下文构成里也统计不出来 |
| **专用工具 `skill(name)`**（推荐） | 返回正文、skill 所在目录和资源清单 | 加载这件事就是一条工具调用，记录本来就存在消息里，不用另设「已加载」状态 |

去重直接从当前窗口推导：窗口里已经有同名 skill 的结果，就只返回一句「已加载，见上文」。压缩或整理把正文换成占位后，窗口里就不再有正文，自然允许重新加载。

### 用户显式指定

在 Web 输入框里用 `/名称` 或 `$名称` 选中 skill（可以和现有的斜杠命令共用补全），由 harness 直接注入正文，不靠模型去找。

- 注入的正文作为这条用户输入的一部分存下来（新增一种 ContentPart，或固定格式的文本块），记录的是模型当时实际看到的内容。之后磁盘上的文件改了，历史也不跟着变，前缀不会失效。
- 这和工具加载是两个入口，但去重和占位用同一套规则。

### 关键词或正则自动加载

在 frontmatter 里可选写一个 `match:` 正则，用户输入命中时由 harness 处理。分两档：

1. **只提示**：在这条输入后附一行「可能相关的 skill：X」，由模型决定要不要加载。成本低，误触发只多几个 token。
2. **直接注入**：效果等同用户显式指定。适合结果确定的情况，比如消息里出现某类链接就一定要用对应的 skill。

模型根据描述来选，大部分情况已经够用。正则的价值在于确定性：微信渠道没有斜杠补全，正则相当于一个隐式的显式指定。建议第一版不做，等有具体的 skill 需要时再加，并且先做「只提示」那一档。

## 二、什么叫卸载

「禁用 skill」或「删掉 skill」只影响以后的目录，已经进入历史的正文还在。真正减少占用，只能在组装下一次请求时，不再发送那段正文。

micnext 已经有现成的手段：压缩时把工具结果换成一行占位，工具调用和结果的配对保持不变。skill 正文本身就是一条工具结果，或者用户输入里的一部分，同一套占位规则可以直接套用，占位文字写成「已加载过 skill X，需要时重新调用」。

问题在于什么时候换占位。随时换会破坏缓存，这就是之前不做卸载的原因。

## 三、缓存冷了以后整理历史

### 想法

服务商的前缀缓存只能保留一段时间。距离这个会话上次调用模型的时间超过缓存有效期，缓存已经失效，这次请求无论如何都要全额计费。这时大幅改写历史，不会额外损失什么。

- **缓存还热**：历史只追加，不改动（和现在一样）。
- **缓存已冷**：在这次 run 开始前做一次整理，然后照常运行。整理后的前缀从这次起重新稳定下来。

最典型的场景是长期不断开的会话：微信渠道的会话、隔天回来接着聊的 Web 会话。人离开一段时间，回来往往已经换了话题，正好适合清理。

### 冷了以后整理什么

按代价从小到大：

1. **轻整理**：不调用模型，只在整理点之前套用占位规则：skill 正文、超过阈值的旧工具输出、图片。规则和压缩保留段一致，复用同一段代码。
2. **提前压缩**：上下文占用超过一个较低的阈值（例如 50%，和定时任务一致）时，直接走完整压缩，不等到 80%。定时任务的做法就是这一条的特例，可以统一成同一条规则。

整理点要作为事实记下来，形式是一种不带摘要的轻量边界（`messages.kind = boundary` 已经能表达边界）。之后热状态下的每次请求都按同一个边界渲染，前缀才能保持稳定。不能每次请求都按当前时间临时算一遍。

### 有效期从哪来

公开资料（2026-10-27 查）：

- OpenAI：GPT-5.6 及以后的模型只支持 `prompt_cache_options.ttl = 30m`，承诺至少保留 30 分钟，实际可能更久；旧模型默认在显存里保留，空闲 5 到 10 分钟失效，可以选 24 小时。前缀至少 1024 token 才缓存。
- DeepSeek：硬盘缓存，尽力保留，不用的条目几小时到几天内清掉，没有确切数字。
- ChatGPT 订阅接口：没有公开说明。

一开始先用公开资料定阈值，用自己的数据校准：调用记录本来就在 `core_model_calls` 里持续积累，不用另外采集，隔一段时间重跑一次统计即可。

判断错了有代价：缓存其实还热却当成冷的去整理，会白白损失一次命中。DeepSeek 命中和未命中的价格差很多倍。所以有效期宁可估长，确定冷了才整理。

更可靠的办法是用自己的数据测：每次调用都记录了 `cache_read_tokens` 和时间。按「距离上次调用多久」分组统计命中率，每个模型的实际有效期就能直接看出来。

#### 实测（2026-10-27，服务器数据）

只比较同一会话、同一模型、两次压缩之间相邻的两次调用。命中率：命中的 token 至少占上一次输入一半的调用所占比例。

| 间隔 | deepseek-flash 次数 / 命中率 | gpt-6.1-sol 次数 / 命中率 |
|---|---|---|
| <1m | 15776 / 100% | 133 / 84% |
| 1–5m | 39 / 100% | 20 / 80% |
| 5–10m | 6 / 100% | 8 / 100% |
| 10–30m | 9 / 89% | 6 / 100% |
| 30–60m | 4 / 75% | 7 / 43% |
| 1–3h | 2 / 100% | 6 / 0% |
| 3–12h | 1 / 0% | 2 / 50% |
| 12–24h | 5 / 60% | 6 / 0% |
| >24h | 4 / 0% | 2 / 0% |

- gpt-6.1-sol：30 分钟内基本都在，30–60 分钟一半失效，1 小时后基本冷了。3–12 小时那 1 次命中，样本太少，不作依据。
- deepseek-flash：10 分钟内一定在，10 分钟到 3 小时大多还在，3 到 24 小时一半一半，超过 24 小时一定冷。和官方说的「尽力保留」一致。
- deepseek-v4-pro、gpt-6.1-terra 只有 1 分钟内的数据，还没法判断。
- 附带发现：gpt-6.1-sol 在 1 分钟内也只有 84% 命中。查了没命中的那几次，命中数全是 0，不是少了尾部一块，所以和缓存按块划分无关。其中不少是间隔 0 秒的紧邻调用，可能是缓存还没写好；其余几次推测是请求被路由到了没有缓存的机器。没命中的调用大多出现在早期，id 小于 1500。

#### 由此得出的触发规则

按「确定已经冷了」来设阈值：gpt-6.1-sol 1 小时，deepseek-flash 24 小时。DeepSeek 在 3 到 24 小时之间猜不准，可以不猜，改用观察：

- **过了阈值**：在调用前整理。
- **还在猜不准的区间**：先照常调用，从这次调用的 `cache_read_tokens` 看缓存是不是已经冷了。冷了就在下一次调用前整理，代价是整理后较短的前缀再全价算一次。只在间隔已经很长时才看这个信号：间隔很短时偶尔也会整次不命中（见上），不能据此判断缓存已冷。

只靠观察也行，那样完全不需要配置有效期，但每次缓存冷掉都要多一次全价调用，长会话里更划算的还是先按阈值整理。阈值作为模型设置项还是写成 `limits.rs` 常量，写 B2 时再定；目前只有两个模型有数据，倾向先写成常量。

## 四、建议的顺序

1. **Skill 基础**：目录 + `skill` 工具 + 去重。上下文构成里新增「Skill」一项。
2. **显式指定**：Web 端 `/名称`，注入内容存进用户输入。
3. **冷时整理**：先用 SQL 测出各模型的有效期，再做轻整理和提前压缩，把定时任务那条 50% 的规则并进来。这一步和 skill 没有绑定，单独做也能让长会话受益。
4. **正则匹配**：等有具体的 skill 需要时再做，先做「只提示」那一档。

暂不做：子 agent 里执行 skill（类似 Claude 的 `context: fork`），用多级来源，按 skill 限制工具权限。

## 写 B2 时要定的契约

- 新工具 `skill`：参数、返回格式、去重时返回的提示文字。
- 系统提示 `context` 块里 Skill 目录的位置和格式；`PromptPartKind` 新增一个种类。
- 用户输入中显式 skill 的存法：新增 ContentPart，还是固定格式的文本。
- 轻量边界的种类，以及它和现有压缩边界、`/clear` 怎么区分和展示。
- 缓存有效期放在哪里（模型设置项还是 `limits.rs`），以及整理的触发条件。
