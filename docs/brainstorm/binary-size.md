# 二进制瘦身：结构与依赖

状态：B1 候选评估，尚未选定实现方向。2026-11-10。

目标是保持能力与公开行为，通过缩短重复生成路径、收窄实际使用的依赖能力来减小交付体积；编译选项不是本轮重点。不因 crate 多就合并 crate，不用减少源码行数代替体积验收。

基线与证据见 [体积审查](../reviews/binary-size-2026-11-10/README.md)。当前去符号产物 21.567 MiB，机器码 14.150 MiB。下述投入是探索预算，不是交付承诺；尚未做改动前后实验，不能承诺节省量。

## 候选与顺序

| 顺序 | 候选 | 探索投入 | 预期 ROI 与取舍 |
|---|---|---|---|
| 1 | 图片输出改用明确 PNG encoder，保留现有 JPEG encoder | 半天以内 | 高：改动局部、行为可保持，发布产物已有未使用的 WebP/GIF 编码符号；先验证是否随通用输出路径消失 |
| 2 | 把 `Assembly::run_once` 的通用回调限制在薄入口，内部执行使用固定回调类型 | 半天至一天 | 中高：大段启动与等待流程不需要携带回调类型；先保持公开签名，只在私有路径使用借用的动态回调；是否减少机器码须实测 |
| 3 | 在 `Engine::run`、微信 inbound 的自然阶段建立少量 Future 边界 | 一至两天 | 中：同时改善职责清晰度；单纯拆 async 函数未必缩小代码。必要时只在大的阶段边界装箱，衡量分配与清理代码变化 |
| 4 | HTTP handler 的业务 Future 与提取/响应适配分开 | 一至两天，先选少量典型接口 | 中且不确定：handler 相关代码约 441 KiB，但包含必要的提取与业务代码，不能按整个桶估收益；不把不同业务合成一个大路由分支 |
| 5 | 文件图标嵌入方式调整：同一图标集比较 data URL、SVG sprite 或资源表 | 半天至一天 | 中低：现有压缩 chunk 为 165.3 KiB，保持完整图标集合的收益未测；动态加载只减少首次下载，不减少嵌入体积 |
| 6 | 重复版本、依赖 feature 的定向清理 | 半天扫描，逐项决定 | 低：已有多个库关闭默认 feature；重复项不都属于运行时代码。仅在已有依赖能力可替代时做，避免手写协议/解析器 |

建议先做 1、2 的独立实验，每项记录去符号文件、机器码、相关函数族与必要功能验收；收益不足且结构更复杂则放弃。之后根据结果决定是否推进 3、4。不预设总节省目标。

## 暂不采用

- 删除 GIF/WebP、微信、非 UTF-8 网页支持：都是已有能力，属于产品取舍，不能包装为无行为变化的瘦身。
- 换掉 SQLite、HTTP/TLS、HTML 解析或正则引擎：体积大不等于多余，替代的正确性与维护成本高。
- 用手写 frontmatter 解析替代 YAML：现有 skill 格式会受影响，只因几十 KiB 引入自制解析规则不划算。
- 合并所有 CRUD 或引入统一动态 JSON 分发：会削弱边界类型和业务可读性，未证明能获得足够收益。
- 为减少几个加密/随机数小 crate 强行对齐版本：先看运行时代码归因，不能用 `cargo tree -d` 的条目数当结果。

## 实施边界

私有整理可在确定方向后直接实现；若需要更改依赖、公开类型/签名、模块或 HTTP 契约，先写 B2 并获批准。每个实验独立比较，避免收益重叠相加。最终按仓库要求运行 fmt、clippy，涉及前端时运行 bun check；取消、超时、错误与任务终态必须保持原契约。
