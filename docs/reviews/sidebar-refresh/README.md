# b58a98b 周边设计审查

日期：2026-11-03。范围：侧栏标签筛选、刷新与分页；只审查，不修改实现。

结论：显示全部标签正确；切换筛选立即请求、保留旧列表的方向合理。建议局部整理 `sessions.svelte.ts` 的请求生命周期，无需改后端或引入通用查询框架。

## 具体问题

### P2：绕过串行队列后，旧响应可以覆盖新结果

位置：`web/src/state/sessions.svelte.ts:24-29,56-71,100-108,125-134`。

切换标签直接启动刷新，与 SessionsSync 正在执行的刷新并行。只比较 tag 值不能区分不同次查询：A 请求未完成时切到 B 再切回 A，新 A 先完成，旧 A 随后仍能提交，恢复旧标题、运行状态、未读状态或成员集合。同标签的直接刷新和事件刷新也没有提交先后保证。置顶列表同样受影响。

用 Bun 转译当前源码、以恒等函数替代 `$state`、手动控制 API Promise 的完成顺序，验证 A→B→A 后，新结果 id=200 被旧结果 id=100 覆盖。这是状态逻辑验证，不是浏览器或真实网络验收。

原先队列串行约束覆盖了整轮刷新；本次绕开队列扩大了并发路径，现有 tag 校验不足以替代该约束。

### P2：失效请求的失败仍能污染当前筛选

位置：`sessions.svelte.ts:70-71,87-90,107-108`。

A 请求未完成时切到 B，B 成功后 A 失败，catch 不检查请求是否有效，会在 B 的列表上显示 A 的错误。成功路径有 tag 校验，失败路径没有。此问题原已存在，本次直接并发刷新使其更容易出现。loading 的收尾也需要归属于具体请求，不能让旧任务清理新任务状态。

### P2：刷新与翻页分别写入同一组分页状态

位置：`sessions.svelte.ts:56-90`。

`loading` 只防止两次 loadMore 并发，不协调 refresh。翻页按旧 next 发出，后台刷新因会话活动重排并替换前几页，旧翻页随后把旧边界的数据追加到新列表。去重只去掉重复 id，不能补回两次分页边界之间被跳过的会话。`#pages` 在 refresh 等待期间仍会变化，也使这一轮刷新的覆盖范围取决于响应顺序。

这是原有结构问题；本次修改触及同一生命周期，适合一起处理。无需承诺 HTTP 多页查询具有数据库快照一致性，先消除前端不同轮查询相互拼接即可。

## 结构摩擦与取舍

Tags 同时拥有词表、筛选值、分页重置和所有列表调度；SessionsSync 声称是唯一刷新入口，实际已不成立。问题在于没有一个位置统一决定哪次请求仍有提交资格，单纯恢复“所有操作都排进 500ms 队列”会重新引入已修复的交互延迟。

建议由侧栏状态协调筛选变化与后台事件，列表负责自身结果和分页：

- 保留交互立即刷新、后台事件合并节流两种触发策略，共用请求失效与提交规则。
- 筛选变化使旧查询轮次失效；同一列表的新替换请求也使旧替换请求失效。成功、失败和收尾都检查所属请求。
- 在请求开始时固定本轮筛选和页数；翻页绑定所属结果轮次及游标。刷新与翻页选择串行执行，或在替换刷新时废弃旧翻页并允许新结果继续翻页，不把两套边界直接拼接。
- 保留旧条目时显式表达正在切换。否则新标签已经选中、旧列表仍显示，失败后还会长期停留，用户仍可能误判筛选结果。具体用加载提示还是其他视觉表达交由 human 决定。

优先采用当前文件内的少量私有状态与方法；不需要新 store 库、通用基类、缓存体系或后端 API。将筛选调度从 Tags 移给协调者可以改善职责，但这是实现选择，不单独列为缺陷。

本次未改功能、公开契约或 todo 状态；未执行 Rust / 前端构建检查。若实施涉及导出类型或签名变化，按仓库流程另写 B2 批准后实现。
