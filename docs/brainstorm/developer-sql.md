# B1：开发者只读 SQL

**状态：方向收敛：凭据列由建表方声明、只读连接归 mic-store；契约见 [开发者诊断 B2](../blueprints/developer-diagnostics.md)，待批准（2026-10-10）。**

## 需求与建议

服务器数据库不便直接查看。在开发者页面增加 SQL 查询入口，用于检查引用消息、媒体记录和投递状态，有实际收益。保持个人工具的规模：SQL 输入、表与列提示、少量结果、复制即可；不做数据库管理平台，不支持写库。

日志 B2 继续独立审查，本项另起契约，不把查询接口混入日志批准范围。更新重启仍在日志之后。

## 已知事实与边界

- Store 当前是单个 Connection 加 Mutex。若经同一连接执行诊断 SQL，即使只读也会占业务锁；应使用同一数据库文件的独立只读连接，不运行 Store 初始化或迁移，不猜数据库路径。
- 数据库启用 WAL。读查询会持有读事务/锁，通常不阻塞其他连接的正常写入；长读事务会妨碍 checkpoint 推进和 WAL 回收。只读不代表没有资源影响，也不承诺永不出现 SQLITE_BUSY。
- 查询必须在 SQLite 执行层限制时间；仅给异步等待套 timeout 不能停止阻塞线程中的 SQL。候选为 progress handler 中断，查询结束立即释放 statement/事务，再向网页返回有界结果，不能随网页慢传输一直持有读事务。
- 微信表含明文 bot_token、context_token；只读仍能泄露凭据。现有 Web 不展示凭据的边界需保留。

## 候选与取舍

推荐允许诊断查询，拒绝读取凭据列。另一候选是只开放诊断表/视图，规则更直观，但跨表排查范围更窄。保护规则由知道凭据的领域模块声明、二进制装配，不能让 Gateway 硬编码微信私有表结构；最终形式在 B2 前确定。不限范围的只读 SQL 会改变凭据披露边界，不作为默认方案。

只读连接与 SQLite authorizer 在执行边界共同约束：单条只读查询，禁止写操作、ATTACH、改变配置的 PRAGMA 和加载扩展。由 SQLite 解析，不用 SELECT 前缀或正则判断 SQL。表结构浏览与允许的查询范围一致。

建议固定上限：SQL 16 KiB、结果 200 行/1 MiB、执行约 2 秒，同时只运行一个诊断查询；达到行数/大小上限返回明确截断提示，超时返回错误。上限只是草案，集中在所属 crate 的 limits.rs，不新增设置旋钮。耗时统计与复制足够，不做历史落库、导出整库或分页长事务。BLOB 显示类型/大小；整数、文本、NULL 等须有明确结果类型和序列化约定。

## 实体、写者与状态

| 实体 | 唯一写者 | 状态 |
|---|---|---|
| 业务数据库 | 现有 Store/领域迁移 | 保持现有生命周期；诊断入口无写权限 |
| 诊断查询 | 查询执行器 | idle → running → completed / failed / interrupted → idle |
| 查询结果 | 查询执行器产生、网页持有 | 有界结果快照；不保留数据库事务 |

查询场景：登录网页 → 提交 SQL → 鉴权/请求解析 → 取得诊断执行名额 → 独立只读连接准备 SQL、检查授权 → 有界执行 → 释放数据库资源 → 返回结果 → 网页展示/复制。

长查询场景：执行期间业务仍走原 Store → 到达时间预算，SQLite 被中断 → 释放读事务与执行名额 → 网页收到超时错误。已有查询运行时新请求直接报告忙，不排长队。

不变量：诊断不能写库或读出受保护凭据；不持有业务连接 Mutex；结果传输不持有读事务；没有无限执行或无限结果；数据库错误可见，不自动改配置绕过。
