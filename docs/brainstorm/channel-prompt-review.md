# 渠道提示：契合性审查与范围选择

**状态：B3 已审；B2 已批准并实现（2026-10-09）**

审查对象：[channel-prompt](../blueprints/channel-prompt.md) 的初稿；以下保留审查依据。
human 要求直接调整蓝图、提示精简直接；B2 已采用候选 A，修正 F1～F4。
human 实测确认微信支持大部分 Markdown：数学块、脚注和折叠块不支持，代码块可复制但无高亮。
B2 与本文已同步，只列具体限制，不笼统要求简单格式。本文不是实现授权。

## 一、结论

渠道声明自己的呈现特点、core 放进 `context`、模型消费，契合现有装配和提示词布局。
不需要通用 prompt 插件框架，也不需要重构整条执行路径。需要先收敛的是：这段说明究竟描述哪个会话的用户界面，
以及它能规定多少助手行为。当前草案把事件归属直接当成呈现渠道，还把篇幅偏好和投递时序带入了契约。

## 二、Findings

### F1 — accept：事件归属不能直接作为呈现渠道

**分类：本次方案缺陷；根因是既有架构缺陷。**

`mic-core/src/kernel.rs::session_channel` 给 Root 返回渠道、Task 返回祖先归属、Triggered 返回触发模块。
这个混合语义已记在 [正交审查 E](orthogonality-review-2026-09-24.md#二e-余项会话身份与来源关系needs-investigation)。
它服务事件过滤，不能证明当前模型在直接与该渠道用户对话。

现有 `SessionKind` 和 `delivery_target` 分开存储；微信 `delivery.rs::run` 还按绑定的 root session 过滤。
因此 Task 的事件归属为微信，并不代表其回复会发微信；让它继承“先告知、最终回复短”会把内部工作产物当成用户回复。
Triggered 的模块名也不是界面。候选中的 cron 场景明确区分普通运行历史与显式 `send_message` 推送
（[roadmap §2.4](product-roadmap.md#24-消息任务与取消)），不能在此提前决定其呈现契约。

建议：本次只为 `SessionKind::Root` 根据自身 channel 选说明；Task/Triggered 不根据事件归属推断呈现渠道。
保留现有事件字段及查询行为，不顺手重构 E；内部会话和显式跨渠道发送随真实生产者的 B1/B2 决定。
也不改成统一按 `delivery_target` 查提示：Web 没有投递目标，但仍有自己的呈现特点。

### F2 — accept：渠道事实与用户篇幅偏好混在了一段声明里

**分类：本次方案缺陷。**

`runtime-settings` 和 `system-prompt-layout` 已把人设、通用偏好放在 `persona`，
`run-execution` 附录 A 明确语气与篇幅归人设。渠道格式限制并不意味着用户只能获得短回答。
`Final reply short` 会与用户要求详细说明、人设和通用偏好冲突。

建议：渠道描述主要回复界面的事实及必要的表达适配，如微信仅呈现已落盘正文、不显示推理与工具过程、支持大部分 Markdown；
只避开数学块、脚注和折叠块，允许代码块，不强制缩短用户要求的内容。“长任务先简短告知”可作为工具过程不可见时的适配建议，
不能把最终回复篇幅固定为短。Web 描述为支持 Markdown、可实时查看工具过程；用户当前打开哪个页面不影响所属渠道说明。

### F3 — accept：验收承诺超过提示词与现有投递路径的保证

**分类：本次方案缺陷。**

微信按每次模型调用的落盘 `Reply` 提取正文发送，因此模型在带工具调用的回复中写一句告知，无需新增事件就能投递。
告知应与工具调用出现在同一次模型回复：单独生成一句无工具调用的告知且没有新输入，当前 run 就会完成，不能假定还有下一次模型调用。
但 core 在 Reply 落盘后执行工具，sender 异步消费；网络慢、发送失败或模型没写告知时，
均不能保证“先收到一句提示”才开始工作。`wechat-channel` §6.1 的成功也只表示服务端接受。

建议：验收拆开：核对组装请求确有正确说明；人工观察长任务是否生成告知、正文是否适合微信；
再核对告知沿已有 Reply 投递路径发送。模型遵循程度是行为观察，不是框架时序不变量。
如果要求开始工作前用户必然收到消息，那是执行与投递协调的新方向，须另走 B1，不能靠本功能隐含引入 ack。
typing 归渠道运行状态，当前尚未实现；它与模型对具体工作内容的告知独立，不合并生命周期。

### F4 — accept：契约修订与兼容核对不完整

**分类：本次方案缺陷。**

草案说“公开 API 新增一个方法，其余均为私有改动”，但 `AssembleError` 新增公开变体也属于契约变化。
除具体 install 调用方外，还需列出 `Assembly::new` 错误消费者；穷尽匹配者需要新增分支，传播/通用展示者通常兼容。
当前二进制 `main.rs` 通过 anyhow `with_context` 收口，没有穷尽匹配，新增错误变体兼容；声明重复应仍在装配阶段失败。
同步清单除 system 布局外，应包含 `mic-core-module` 的 Registry/装配错误契约，以及微信对提示与验收边界的说明。
`run-execution` 已指向 system 布局，不必复制提示文本。已批准文档等范围与 B2 批准后再同步。

## 三、保留与拒绝

- **reject（本次方案方向挑战）**：为此增加通用 ContextContributor、Hook 或 prompt 框架。
  理由：当前消费者只需要一段按 Root 渠道选择的静态文本，已有 request 职责足够。
- **reject（本次方案方向挑战）**：把渠道提示塞进 `ChannelSetup`。
  理由：登录设置和模型表达独立变化；Web 有提示需求却不需要微信式登录设置。两个声明保持独立即可。
- **reject（本次方案方向挑战）**：注册键统一取 `Registry.current`。
  理由：Gateway 模块名是 `gateway`，Web 会话 channel 是 `web`；显式渠道键有已观察到的必要性。
- **accept（本次方案设计）**：可选静态声明、装配去重报错、渠道拥有文本、core 汇总。
  最终消费者明确；未声明就没有附加说明属于可选贡献契约，不是错误后的 fallback。
  本次无新增 crate 依赖，不影响 Provider、落盘消息和主路径事件，也不要求扩展 L0 `mic-message`。

## 四、B1：范围候选与待决定项

| 候选 | 收益 | 代价/未知项 |
|---|---|---|
| A：仅 Root 的主要回复界面（建议） | 解决当前 Web/微信问题，不扩大事件归属语义；只需私有选择逻辑 | Task/Triggered 的受众规则暂不承诺，随其生产者定义 |
| B：沿 `session_channel` 继承 | 实现改动少，Task 自动拿到祖先提示 | 内部产物受用户回复规则影响；Triggered 仍只有模块来源，没有界面语义 |
| C：现在统一建模执行受众与发送目的地 | 可明确内部产物与跨渠道发送 | 尚无 Task/cron 生产者，必须先确定其产物消费者及主动发送契约；会扩大公开契约范围 |

**needs-investigation（既有架构缺陷）**：Task/Triggered 的回复最终给谁、内部任务应否知道父会话界面，
留给对应生产者；本文不替 human 决定，也不把来源等同受众。

Root 选择规则、声明文本、错误调用方、同步清单和验收已补齐；B2 批准后才实现。
