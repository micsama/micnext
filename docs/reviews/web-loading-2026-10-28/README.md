2026-10-28。范围：本地浏览器访问服务器的会话列表、会话消息、Trace 运行列表与内容。仅审查，未修改运行代码。现已取得 human 下载的服务器数据库备份，完成副本上的查询与阻塞机制测量；仍没有故障现场的服务端日志或完整浏览器录制。以下按最新结论在前、历史记录在后的顺序保留，不把本机结果当作服务器耗时。

## 上线反馈与结论边界（2026-10-28，修复后复核）

human 转述：服务器更新后不再卡顿，与本地 release 的真实库对照结果一致。仓库已包含 `b874279` 的查询与 v31 索引修复；具体前后计时见下方“存储侧压测”。本轮复核阅读了当前实现，没有重新运行这组计时，也没有直接测量服务器。本文早期“尚未实施”、core=30 等描述保留为对应实验时点的记录，不代表当前仓库状态。

**这次修复消除了已证实的查询退化，解决了当前这次整页卡死；不能进一步宣称所有常用读取均只随当前会话窗口增长，或任意历史规模、并发量下页面都不会变慢。** 当前实现的成本边界如下：

| 路径 | 修复后的主要工作量 | 尚存的增长因素 |
|---|---|---|
| 上下文窗口 | 利用范围索引读取活动段，另取边界保留输入 | 活动段和显式引用的条数、正文大小；没有有效压缩边界时活动段仍可很长；索引定位本身也有成本 |
| 订阅最后一条 id | 索引定位末条记录 | 已消除为了一个 id 解码整个会话的工作 |
| 会话用量 | `load_usage` 读取该会话全部调用，必要时再读取后代树调用 | 会话及后代的历史调用数，与当前压缩边界无关 |
| 任务用量 | 按历史触发关联 run，读取调用后汇总 | 历史触发数和关联调用数 |
| Trace 会话列表 | `core_runs` 按会话聚合，并构建会话树 | 全库历史 run、会话数及失败工具结果数 |
| Trace run 首页 | 分页获取完整 run，同时取总数和全部标题旁路调用 | 单页 run 的消息/调用/正文量、会话 run 总数及标题调用数；限制 run 个数不等于限制数据字节数 |
| 看板 | 按时间范围读取 run、调用和工具结果再汇总 | 所选时段的记录数；固定天数不等于固定记录数 |

这些是当前 `context.rs::read_range`、`trace/mod.rs::{session_usage,schedule_usage,trace_sessions,trace_runs,dashboard}` 的直接代码结论，不代表这些路径目前仍然慢。30 天与 366 天在这份约一周历史的备份上覆盖的数据接近，20–22ms 的结果不能当作多年数据增长验证。一次真实快照上的顺序 Store 测量证明该样本提速，不证明复杂度上界、HTTP 尾延迟或多人容量。

### 后续决策

1. **本次修复可以单独验收**：保留真实库前后对照及服务器恢复反馈。无需为当前问题立即换 DuckDB、分库或按压缩边界物理分表。
2. **下一步优先测干扰，而非继续泛化“治本”**：同一实例内让看板/搜索/Trace 重读与 settings、消息提交、Channel 更新并发，记录锁等待、执行、解码及请求 p95/p99。仍使用真实库副本，不为此自动制造或复制业务数据。服务端记录请求/操作标识和分阶段耗时，不记录凭据或正文。
3. **读写隔离仍是明确的候选方向**：`Store` 仍共享 `Arc<Mutex<Connection>>`。这次减少了已知查询的持锁时间，没有消除一个重读拖住所有业务的结构条件。若要支持稳定的多客户端、多 agent 并发，可起草有界只读执行路径的 B2，明确队列容量、读超时/取消、短事务快照及错误范围；不是直接增大连接池。隔离也不能消除共享 CPU、磁盘的竞争。
4. **全量统计独立治理**：优先保留当前窄字段查询；若真实规模或频率使统计重新成为瓶颈，再选择 SQL 聚合、可重建汇总或按需求缓存。汇总必须处理失败/重试、后代归属、可恢复 run 及现有价格口径，不能随意增量相加；更不能用最新压缩边界截断全历史用量来换取速度。
5. **定时任务费用另行验收**：限频降低触发次数，工作窗口治理减少无关历史；二者都不等于费用保证，压缩也有调用成本。当前存储修复不能据此推导定时任务不再过度消耗 token。限频 B2 的批准状态应以 human 明确指令为准，不从转述或工作区已有修改推断。

审查文档及脱敏的可复现实验适合作为本次优化证据保留。提交前应核对目录中不含真实数据库、对话正文、密钥及无关产物，并保留历史测量与新 Rust 测量的版本、环境差异。本轮只更新审查文档，不因转述中的“提交推送吗”自行提交或推送，也不改动其他工作区实现。

### 按真实数据修订优先级

1. 消息反查索引 + 用量/看板与调用详情的查询职责拆分；不先批量改所有字段和所有表。
2. 建立有界轻读/重读/写入执行边界，补排队、执行、取消和提交日志。不能等下一次出现新慢查询再补救。
3. 高频自动化的期限/次数/预算与可见累计用量。这是本次实际暴露的资源治理问题，需要明确产品选择，不擅自暂停或限额。
4. 长会话 Trace 分层、树分页、搜索与事件放大治理，按真实测量继续推进。当前列表和 peers 本身较快，优先级低于全量 usage。
5. 多租户与换库仍属于独立产品/容量决策。16MB 就发生严重排队，说明先修访问和执行模型，不是先把 SQLite 换掉。

### 超长会话：已有语义边界，还要让查询真正利用边界

human 明确要求把长会话结构作为主线，而非将“最短 10 分钟 + 30% 压缩”当作根治。限频只减缓历史增长；降低压缩比例不解决查询扫描、统计全量读取和全局锁排队。

当前并非每次把整个会话历史发给模型。已有 `Boundary / Compaction.keep_from / Trim.base` 定义活动窗口，但 `context.rs::read_range` 的 CASE、OR 和跨边界输入补入混在同一谓词，难以把窗口下界用于索引定位。最新有效压缩边界为 35883、keep_from=35762，会话 25 共 35,465 条消息，实际当前窗口只返回 1,530 条。

使用 [context_probe.py](context_probe.py) 在真实副本比较，结果见 [context-probe-result.json](context-probe-result.json)：

| 同一活动窗口，返回 1,530 条 | 三次耗时范围 | 约 SQLite VM 指令数 |
|---|---:|---:|
| 当前 CASE + OR 查询 | 7.2–7.9ms | 970,000 |
| 窗口范围与边界保留引用拆为 UNION | 5.1–5.2ms | 576,600 |
| UNION + `(session_id, created_at, id)` 索引 | 2.1–2.2ms | 137,000 |

逐行比较了返回值、顺序和未认领过滤标记，三种方案一致。这个实验覆盖当前真实 Compaction/keep_from 场景，尚未覆盖所有 Trim、撤销、无边界、延迟回填和历史 through 游标，不能直接当成完整实现验收。它当前不是 96 秒卡死的主因，但证明“有语义边界”不等于“数据库只扫描边界内数据”。

访问应按用途分边界：模型工作窗口按有效 boundary/keep_from 加显式必要引用；聊天历史按消息游标分页；Trace 按 run/调用游标定位；全量统计走专门聚合。不能把它们都机械限定到最新压缩边界，否则历史和统计会丢失。必要的 quoted、待处理输入和跨边界工具引用须按 id 补取，不能只加 `id > boundary_id`。

### 分区、分表、DuckDB 与 SQLite 特性选择

MySQL 的分区裁剪与这里目标相似：跳过不可能匹配的范围；不过物理分区也依赖查询能提供可裁剪条件。当前先通过复合索引和明确谓词做到范围读取，不需要为每次压缩或每个会话建表。[MySQL partition pruning](https://dev.mysql.com/doc/refman/8.4/en/partitioning-pruning.html)、[SQLite range/index planning](https://sqlite.org/queryplanner.html)

压缩边界可撤销，保留段可能位于边界消息之前，旧消息还可被 Trace/工具/引用访问。因此它是逻辑工作集边界，不适合直接当作“边界前全部移走”的物理分区规则。以后确需冷归档，应独立定义可归档对象、跨边界引用、回看与恢复契约，而不是每次压缩搬数据。

真实副本 `dbstat`：消息表占 10,223,616 字节（约 9.75MiB），图片表约 2.11MiB，调用表约 1.74MiB。没有容量证据要求换存储引擎。把元数据与正文在同一 SQLite 内纵向分表，与把会话搬到另一引擎是两个决定：前者可以保持同一事务，后者要处理跨库引用、提交和恢复。

| 候选 | 当前判断与消费者 |
|---|---|
| 复合索引、范围扫描、游标分页 | 优先；工作窗口与历史列表都有直接消费者；保留 `(created_at,id)` 展示位置和消息 id 提交游标的区别 |
| 部分索引 | 优先评估；当前 37,365 条消息中 18,575 条有关联模型调用，其余无需进入此反查索引 |
| WAL + 有界独立 reader | 已有 WAL，缺执行隔离；避免重读持有写者应用锁，同时限制重读数量与期限 |
| 生成列/表达式索引 | 当前 kind 已是生成列；工具结果类别/名称等可按实际筛选需求投影、索引，避免散落重复 JSON 规则 |
| 事务维护的窄摘要 | 当全历史精确汇总成为热点时，再为实际查询维护可重建计数/用量投影；价格仍按现行口径计算 |
| FTS5 | 搜索专用候选，不能无声改变中文短词/子串匹配语义 |
| `PRAGMA optimize` | 索引变更与连接生命周期中维护统计信息；辅助查询规划，不替代缺失索引或有界执行 |
| SQLite JSONB | 可减少 SQLite JSON 解析，但不是索引，不消除扫描；当前 Rust 按文本 JSON 解码，需要同步修改读取/转换，当前优先级低 |
| 元数据/正文在同一库纵向分表 | 有大正文拖累元数据访问的测量后再做；写入、生命周期与引用仍同事务，索引能覆盖的场景先不拆 |
| DuckDB / Parquet | 后续离线历史分析或可重建分析副本的候选；当前不作为会话主存储，不引入两套必须同步成功的事实写入 |

部分索引真实实验：[index-choice-result.json](index-choice-result.json)。针对 17,730 次调用的三类消息反查，全量索引占 638,976 字节（624KiB），`WHERE model_call_id IS NOT NULL` 的部分索引占 307,200 字节（300KiB）；三次查询分别约 10.6–11.2ms 与 10.4–10.6ms，结果一致、三个反查均走索引。说明该特性可用；不把单次建索引耗时当写入吞吐基准。候选 DDL：

```sql
CREATE INDEX idx_messages_call_kind
ON core_messages(model_call_id, kind)
WHERE model_call_id IS NOT NULL;
```

SQLite 官方说明部分索引可减少条目、生成列可将 JSON 投影纳入索引、JSONB 多数操作仍为 O(N)：[partial indexes](https://sqlite.org/partialindex.html)、[generated columns](https://sqlite.org/gencol.html)、[JSONB](https://sqlite.org/json1.html#jsonb)。统计维护见 [PRAGMA optimize](https://sqlite.org/pragma.html#pragma_optimize)。

DuckDB 官方将并发设计定位为读密集分析，原生进程内支持多 writer 线程，但更新相同行可能产生冲突；并不能因为能并发就替代应用的事务和任务顺序契约。当前会话负载是按 session/id 查短范围、频繁提交消息/认领/投递状态，已用 SQLite 测出低成本路径；引入 DuckDB 的主存储迁移成本缺少对应收益证据。若以后做多年跨会话离线分析，可从一致性副本导出再用 DuckDB，主事实仍保留在业务库。[DuckDB concurrency](https://duckdb.org/docs/2.0/connect/concurrency.html)

这些结论不反对未来物理拆分；判断门槛应是索引与工作集边界正确之后，实际 I/O、维护或分析负载仍成为瓶颈，而不是看到“超长会话”就先更换文件格式。

## 深入审查更新（2026-10-28）

human 要求进一步审视数据库设计、多模块交互与并发使用，而不止补索引。本节记录本轮新证据；下方此前排查与补充保留时间顺序。**缺索引的查询退化已证实，但生产现场具体持锁者仍未直接捕获；此前“根因已确认”的措辞应理解为高可信解释，不能替代生产诊断。**

- **原先的单连接理由需要修订**：历史 `docs/brainstorm/mic-store-design.md` §二由 SQLite 单 writer 推导单连接串行读写；现有 `schema.rs` 已开启 WAL。SQLite 单 writer 不要求所有 reader 与 writer 共用应用互斥锁。拆只读执行路径有当前的 Trace、搜索、列表消费者，已经不是为假想未来设计。
- **索引无法给其他模块提供可用性边界**：`Store::blocking` 先 `spawn_blocking`，再在线程里等同一把锁；没有业务级等待上限或排队容量。Trace、搜索、Channel、设置与 agent 提交共用它。新增 reader 若没有容量和查询取消约束，只会把锁等待转成 CPU、内存和磁盘竞争。
- **搜索是另一个现存长扫描入口**：`search.rs::search_sessions` 按候选会话扫描正文，`instr(lower(body), term)` 不能靠本次三个 B-tree 索引消除；无命中可能扫完整个候选集合。每个会话全部命中正文先 collect，再截成显示用的 3 条，分页只限制返回会话数，不限制工作量。
- **发布锁内存在无必要的全量读取**：`Kernel::subscribe_from_now` 持有全局 `Events::publisher`，调用 `messages_after(session, None)` 读全部消息并解码，最后仅使用最后一个 id；微信 `service.rs` 建立订阅消费该入口。应查最后一个可回放消息 id，保留排除 `SideOutput` 的当前语义。改数据库连接之前也值得独立修复。
- **模块读写接口未区分**：微信引用查找等纯读通过 `with_module_tx` 进入业务连接事务；只迁移 Trace 仍会留下渠道读取与写入之间的排队。重构应按操作是否需要事务、是否属于重查询划分，而不是为每个业务模块单开一套数据库。
- **独立 SQL 诊断不是完整隔离**：`diagnostic_query` 有独立只读连接、try-lock 和执行期限，是可借鉴的现有机制；但 `diagnostic_schema` 仍经过主连接。诊断写入先在主锁内执行整库 `VACUUM INTO`，备份阶段不在后续 SQL 的 2 秒 deadline 内。运维操作也须明确阻塞范围。

上述均来自当前源码；尚未实施重构。方向与取舍见 [B1：存储执行与并发使用](../../brainstorm/storage-concurrency.md)。本轮核心建议是：**补索引和轻量查询，同时建立有界的读写执行隔离；保持业务事实与事务一致性，再调整页面读取粒度。** 不是直接换一个通用连接池，也不立即换数据库。

| 实验 | 结果 | 说明 |
|---|---|---|
| 无索引的 CALL_SELECT | 2515.559ms；三个相关子查询均 SCAN core_messages | 复现查询退化 |
| 加 `(model_call_id, kind)` 后同一查询 | 5.274ms；三个子查询均使用新索引 | 验证索引方向 |

后两项的重读是显式注入的递归 SQL，用来制造可控占用；不是对现有 settings 或 Trace 的端到端测量。单次运行受缓存、机器和 SQLite 版本影响，不据此给生产性能承诺。这是 SQL/连接机制实验，不是 Rust Store 功能测试，不代表真实数据分布或多用户容量。

**human 随后提供了真实数据库，本轮已经转为真实库分析，不继续扩展合成规模测试。** 最新结果见本文顶部“真实库核验”。只读 SQL 分析无须解密 endpoint 凭据，没有使用 `master.key`；若之后确需通过 Store::open 测完整 Rust 路径，再决定如何处理初始化校验。分析输出只记录行数、字节数、耗时和计划，不打印对话、凭据或其他业务正文。

### 更深的结构发现

| 层面 | 当前证据与触发 | 推荐方向 |
|---|---|---|
| 汇总读取 | `session_usage` / `schedule_usage` / `dashboard` 复用调用详情查询，取消息引用、重试等汇总不用的数据 | 按用途取窄投影，复用计价规则；费用仍按当前价格，不能盲目永久缓存历史金额 |
| 数据布局 | kind 是 payload 的虚拟生成列，工具结果统计反复解析 JSON；Trace 预览完整解码消息 | 先索引/窄投影；确有收益再把已有查询消费者需要的工具关系、时序、结果移为权威窄字段，不复制两套事实 |
| 一致性 | 原 `Store::call` 中多条查询隐含不被业务写入穿插；拆 reader 后不再如此 | 组合查询使用短只读事务；提交后新读可见；不跨 SSE/用户翻页保持事务 |
| 取消 | 普通 HTTP fetch 无取消参数，过期响应仅通过序号忽略；普通 store 查询无执行期限 | 取消传到队列和 SQL/解码；不能只超时 HTTP 等待者而让工作继续堆积 |
| 提交与发布 | async Publisher 持锁包围 blocking 写入；async 调用方取消后 blocking 可能继续 | 验证取消窗口；提交、按序发布和唤醒由明确服务端拥有者完成，不直接删除发布锁 |
| 失败范围 | scheduler/title 的存储错误向 assembly 传播并触发整体停止 | 页面容量不足和只读超时须是请求级错误，不能误用同一种致命存储错误路径 |
| 事件与刷新 | 所有订阅者接收全局 KernelEvent 后才过滤；Message 为可深拷贝结构；前端丢弃 activity 的 id 后全量刷新 | 分清轻量通知与会话数据流，减少无关复制/唤醒；按 session 收窄失效与请求合并 |
| agent 并发 | 同会话互斥，但跨会话 worker、标题、同批工具缺少统一资源容量边界 | 按模型请求、工具进程、重读等具体资源限并发；父 agent 等子任务时不能耗尽子任务也需要的额度 |
| 长读运维 | WAL 已开启；长读 snapshot 与诊断整库备份有不同阻塞特征 | 短事务、记录 WAL/checkpoint；整库运维明确维护范围，不用无限 reader 掩盖压力 |

`subscribe_from_now` 的全量读取、搜索无命中扫描、诊断整库备份是本轮发现的其他阻塞入口；不能把整个结构的可用性寄托在 CALL_SELECT 的三个索引上。

SQLite 官方说明 WAL 可以读写并行，但长读会影响 checkpoint 回收：[WAL](https://sqlite.org/wal.html)。Tokio 说明已开始的 blocking 任务不能靠 abort 停止：[spawn_blocking](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)。取消 SQL 可使用连接级进度回调，但它不覆盖 Rust 解码：[progress handler](https://sqlite.org/c3ref/progress_handler.html)。详细约束见 B1。

### 对下方“存储侧压测”草案的修订建议

该草案能作为查询性能起点，但不能单独验收本次“一个请求拖住全站”的问题。以下暂为审查意见，不表示已经实现测试：

1. **先测原始真实副本，再做必要的放大**。合成数据只用于定向机制/极端边界验证；不必把拷贝 N 倍作为分析前提。
2. **复制四张表并整体加偏移不足以形成正确数据**：root `(channel, chat)` 有唯一约束；消息 payload 含工具回复引用、job、边界等关系；`core_jobs`、`core_model_call_inputs`、`core_boundary_inputs`、会话已读/明文水位、run 报告消息等也有引用。只改四张表的主外键，会冲突或指向旧副本；foreign_key_check 也不能发现所有“指向存在但错误的旧对象”。有语义错误的 fixture 不适合验证实际 store 返回值。
3. **N 倍会话不等于 N 倍长会话**。必须分别覆盖总历史量、单个超长会话、工具大输出、子树深宽、近期与旧日期分布。复制旧时间数据不会自动增大“最近 N 天”看板负载。
4. **1 秒不是机器无关的标准**。记录环境、SQLite 版本、热/冷状态、多次分布、结果行数和字节数；基准比较采用相同数据和环境。把正确性、成本增长曲线与性能目标分开，阈值在目标服务器上定。
5. **必须补混合并发验收**：一个重读与 settings/消息提交/Channel 更新同时执行，测轻请求与提交尾延迟；再测刷新、取消、断连、过载、重启，检查队列回落、内存/WAL 和事件完整性。顺序执行每项都小于 1 秒，并不能说明并发下可用。
6. **一致性备份优先使用 SQLite backup**。运行中分别拷主文件和 WAL 不保证两个文件处于同一个快照；停服后完整复制或 SQLite backup 更合适。原副本保留不动，转换和索引实验在另一个工作副本执行。只做 SQL 分析无需先复制 master.key。[SQLite backup](https://sqlite.org/backup.html)

### 本轮范围与多用户结论

先按同一实例多客户端、多会话与 agent 并发设计有界读写隔离；真正独立账户作为待明确的产品方向。当前单 Bearer、固定 owner、全局 settings、session 上共享已读水位与全实例事件流不能自然扩展成租户隔离。若需要互不信任的多人，需另选“每人独立实例/工具环境”或“共享账户与 workspace 权限模型”，不能仅靠换数据库解决。详见 B1 §九。

当前产物为审查文档、B1 候选、可复现脚本和真实副本的统计/计时结果，没有修改运行代码或生产数据。真实库已确认形状并修订优先级，后续按选择的执行边界形成 B2，再实施和做 Rust/HTTP 混合并发验收。

## 当前故障现场与排查结论

### 用户可见现象

- 会话和 Trace 加载慢，Trace 显示“正在加载运行记录”。后来出现整个页面外围一直加载，会话显示“会话 25”等占位名称，侧栏列表不能正常取得。
- 服务器入口为 `https://124.223.224.225`。普通业务请求大量 Pending；仅打开一个页面也发生，新的无痕窗口同样复现。
- 尚未确认故障发生时是否有 agent 执行、备份、Trace 查询或其他后台操作，也不知道生产二进制与当前工作区是否完全一致。

### 当前判断与未确认事项

**已确认带有效认证的请求直连应用本机端口仍超时，故障范围已缩到应用内部处理路径。优先排查业务数据库连接等待，尚未确定具体根因。** 浏览器、公网和反向代理都不是本次超时的必要条件，当前不再优先排查浏览器连接额度或网络配置。

当前源码中普通业务读写共用 `Arc<Mutex<Connection>>`；被挂起的多个接口依赖业务存储，而轻量接口仍可返回。这与长时间持锁导致其他请求排队的情形吻合，但没有实际锁等待或持锁者日志，不能宣布是某条 Trace SQL 导致。

服务器本机直连结果已绕过反向代理转发，但仍未区分应用处理、阻塞线程池等待、Rust 互斥锁等待、SQLite 锁等待和 SQL/解码执行。无凭据 401 快只验证拒绝路径；不能代替有效认证后的业务查询。HTTP 协议版本尚未查明，不影响本机直连超时的结论。

此前讨论中的两项假设需要保留修正：

- “Stalled 说明浏览器连接占满”证据不足，不能作为定论。
- 源码已发现 Trace 查询性能风险，但不能直接等同于本次整页挂起的根因。

### 下一步：最小服务端诊断

先补能解释挂起的诊断，再决定性能改造；当前未实施日志或修复。

1. HTTP 入口记录请求标识、方法、去除 query 的路径与进入时间；完成时记录状态与总耗时。只记完成日志不足以诊断一直挂起的请求。
2. 在存储调度边界区分：进入阻塞任务前的排队、互斥锁等待、取得锁后的执行。操作名称需要能关联到请求；同时覆盖后台持锁操作，不能只标记 HTTP 等待者。
3. 等待超过阈值时，在等待期间输出一次诊断，指出等待操作和已知持锁操作及其持续时间；持锁操作执行过久也要能被观察。不要让诊断日志本身再次依赖业务数据库锁；复用独立运行日志设施。具体实现不能为了计时引入新的锁竞争。
4. 用同一条带登录凭据的 settings 请求复现并对照日志：没有入口日志则向入口/代理查；有入口但阻塞任务未启动则查线程池；等待互斥锁则找持锁者；已取得锁但不结束则继续细分 SQLite 等待、SQL 与解码。
5. 本机直连复测已完成：应用端口为 `7878`，HTTP 地址带有效凭据仍超时。后续用这条请求作为最小复现，结合日志定位应用内部卡点；修复后复测本机与公网入口。

日志字段仅包含操作、关联标识、耗时和数量，不输出 Bearer、ticket、完整 URL query、SQL 参数或消息正文。新增诊断不自行取消请求、不重放副作用、不改变错误范围。若涉及公开类型、签名、依赖或 HTTP 契约，按 B2 先批准；私有诊断细节在授权后实现。

```text
store_wait_slow operation=settings request_id=… wait_ms=1000 holder=…
store_acquired operation=settings request_id=… wait_ms=…
store_finished operation=settings request_id=… execute_ms=…
http_finished request_id=… status=200 total_ms=…
```

故障解除的验收：带凭据 settings、模型配置、会话列表均能完成，页面显示真实标题；Trace 加载单独测耗时；再在 agent 执行与重查询并发时复测。不能以未认证 401、SSE 保持连接或重启后短暂恢复代替验收。

## 优先处理

### 1. Trace 查询缺索引，存在阻塞其他业务查询的风险

- 证据：`crates/mic-store/src/trace/mod.rs` 的 `CALL_SELECT` 每条模型调用执行三次按 `model_call_id + kind` 反查消息；`schema/core.sql` 没有对应索引。`trace_runs` 按会话查已结束 run、计数，也没有对应 session 索引；父子会话递归查 `parent_session_id` 同样无索引。
- 使用 Python sqlite3 在内存加载当前 `core.sql`，对上述三种查询执行 `EXPLAIN QUERY PLAN`，分别得到 `SCAN core_messages`、`SCAN core_runs`、`SCAN core_sessions`。这是当前 schema 的计划验证，不是生产数据基准。
- 触发：消息库增长、模型调用多的会话、子任务多的会话树。反查消息的工作量会随模型调用数和全库消息量共同增长。
- 放大：`store.rs` 所有普通业务读写共用 `Arc<Mutex<Connection>>`；查询、消息解码与摘要构造均在锁内。Trace 全库统计、慢查询会让其他会话请求和写入排队；前端 Promise.all 无法使这些数据库操作并行。
- 建议首先验证并增加 `core_messages(model_call_id, kind)`、`core_runs(session_id, id)`、`core_sessions(parent_session_id)` 索引。索引选择用真实库计划、耗时与写入成本确认；不直接认定每一个都同样必要。按仓库规则通过独立转换脚本和 build.sh 停服检查更新，不在二进制自动迁移。

### 2. “正在加载运行记录”读取了完整 run 正文

- 证据：`trace_runs` 默认 20 个完整 run，逐个调用 `load_run`。每个 run 查询完整消息并经 `row::message` 解码，再 `trace_message` 截成 200 字预览；工具大输出和模型长回复虽然不完整传给前端，仍完整读取、解析和部分复制。每页至少逐 run 发起消息、调用两类查询，另外有计数和首页全部标题调用。
- 触发：单个 run 含很多工具调用或大段 shell 输出；20 个 run 并不构成字节或消息数量上限。
- 优先候选：保持现有 HTTP 形状，只读取预览与工具统计需要的数据；先批量查询这一页的 run，减少重复查询与 prepare。须保留所有消息种类、工具归属与统计口径，不用截断数据冒充完整结果。
- 进一步候选：运行列表只取摘要，选中 run 后再取其时间线。收益是首屏成本更稳定，代价是新增 HTTP 契约与一次详情往返，须 B2 批准。

### 3. 远程访问存在不必要的前置等待

- 会话：`SessionView.#run` 先 await `getSession`，随后 `readSse` await 取票，再建立 EventSource。至少三段串行网络往返后才能取得首次消息；网络 RTT 越高越明显。候选：会话信息与流连接并发，分别维护错误和就绪状态，保留现有鉴权与一次性票据机制。
- Trace 首次进入/刷新：`TraceTab.refresh` 等待全会话树与全库 peers 都完成才 `open` 请求运行记录；即使 URL 已有目标会话，仍等待两项。`call_peers` 扫描历史模型调用、读取工具 JSON 并排序求中位数。候选：有目标会话时立即加载其 runs；树和 peers 独立加载，比较耗时稍后补齐，不挡主内容。
- 这两项可先保持公开接口不变实现。并发只能去掉等待依赖，数据库锁内的重查询仍须一起优化。

## 其他持续放大因素

### 会话列表刷新过宽

`sessions.svelte.ts` 每轮刷新标签、置顶、web、cli、wechat；每个列表从第一页逐页重拉所有已加载页。全局 `session_activity` 均触发这一轮。虽然已有单轮互斥与 dirty 合并，用户翻页越深、服务器活动越多，重查与请求越多。全局流连接成功和侧栏挂载也会请求刷新。

`sessions.rs::summaries` 从消息推导活动时间、未读、首条输入预览和运行状态；列表排序依赖推导出的 act，不能简单通过现有会话索引直接取前 30 条。`json_each` 处理输入预览也增加候选会话查询成本，真实成本须看计划与数据。

候选：先按事件已有会话 id 缩小失效范围，减少无关标签与渠道刷新；明确旧页排序一致性后再调整重拉规则。若实际仍慢，再考虑事务维护最近活跃事实和适合排序的索引，需 B2，避免直接建设一套宽泛缓存系统。

### Trace 内容反复读取

`TraceTab.load` 切换选中项与详情页签会重新请求；工具概览同时取工具结果和父回复以读取参数。调用输入重建当前上下文窗口，可能返回很长消息列表；input 页签同时请求 system。当前用请求序号避免过期结果展示，但没有取消这些 HTTP 请求，也没有消息级缓存。

候选：对已结束调用关联的不可变消息做页面内按 id 缓存并合并在途请求；不长期缓存会变化的当前系统提示、会话状态和运行日志。大输入先测传输和渲染，再决定分页或分段展开，后者涉及完整输入查看体验与接口契约。

### 会话回放与传输

初次 `messages_page` 最多先解码 101 条消息，再按最近 5 轮裁切；条数限制没有限制字节。浏览器逐 message 执行 `#merge`，每次重建 Map 并排序整个已加载列表，回放越多重复工作越多。可先合并同一批回放事件的状态更新，保留时序与去重语义。

仓库发现静态资源的 Brotli 预压缩，但没有发现 API JSON 通用压缩层。服务器反代是否已有压缩、HTTP/2 和 SSE 缓冲设置未知。大 JSON 可验证压缩收益；SSE 不应机械套用会积攒输出的压缩/缓冲策略。

## 建议实施顺序与验收

1. 先记录一次慢会话与慢 Trace：请求 TTFB、下载字节/耗时、服务端数据库锁等待与锁内耗时、前端解码/渲染耗时。分别测冷打开、重复打开和 agent 正在运行时，记录数据规模。
2. 优先补关键索引、去掉首次打开的串行依赖、优化 Trace 预览读取；这些直接对应用户等待。
3. 再做会话列表刷新范围、页面内不可变消息缓存、回放批量归约。用相同样本复测，确认统计、分页、未读和实时事件行为一致。
4. 若剩余瓶颈仍是锁等待，讨论独立只读连接；若仍是大 payload，讨论 Trace 摘要/详情拆分与内容分段。只读连接收益是隔离重读排队，代价是连接生命周期、读一致性和写入竞争管理，不先引入连接池。

上述顺序用于一般性能优化。本次已出现带凭据业务请求长时间不返回，优先完成前文最小诊断、确定挂起原因，再落实对应修复与优化。涉及 schema/公开契约的部分先起 B2，批准后实现；纯私有前端调度与查询整理可以随批准范围完成。真实服务器速度和页面观感由 human 验收，不预设未测的毫秒目标。

## 排查结论（2026-10-28 补充）

**根因在数据库：模型调用反查消息没有索引，全表扫描期间占住唯一的业务连接锁，其他业务请求只能排队。网络、HTTPS 入口和浏览器都不是瓶颈。**

### 证据链

1. 不访问业务库的接口（`update`、`stream-ticket`、`model-kinds`）几十毫秒返回，未认证 401 为 21ms；卡住的都是访问业务库的接口，带凭据的 curl 同样超时。
2. `store.rs` 的 `blocking()` 在 `Arc<Mutex<Connection>>` 锁内执行 SQL。只要一个查询执行几分钟，settings 这种毫秒级的查询也要等几分钟。
3. `trace/mod.rs` 的 `CALL_SELECT` 每条调用都用 `model_call_id + kind` 反查 3 次 `core_messages`，这两列都没有索引，每次反查都是全表扫描，工作量约为调用数 × 3 × 消息表大小。用到它的地方：
   - Trace 一页 run（20 个 run 内的全部调用）；
   - `session_usage`（整个会话的全部调用，Trace 顶栏使用）；
   - `dashboard`（最近 N 天的全部调用）；
   - `call_record`（单条调用）。
4. 合成库实测：5 万条消息约 200MB，5000 次调用，其中一个会话 2434 次调用。

   | 查询 | 现状 | 加 `core_messages(model_call_id, kind)` 索引后 |
   |---|---|---|
   | 单个 run 的 10 次调用 | 0.65s | — |
   | 单会话 `session_usage` | 144s | 0.00s |

   扫描时要读整张表的页面，正文越大越慢。一页 Trace 涉及几百次调用，就是十几秒到几分钟。
5. 浏览器断开后，服务端已派出的阻塞任务不会取消，仍会排队执行。每次刷新再追加一批重查询，等这批全部跑完页面才会自行恢复，这与现场观察到的「很久之后自己好了」一致。

### 时间线上的判断

此前也出现过类似的卡顿，所以这不是某一次改动引入的。这个开销随调用数和全库消息量增长：本地开发库只有 169 条消息，测不出来；服务器库持续增长后，从「慢」变成了「整页挂起」。服务器编译 release 时 CPU 和内存吃紧，Trace 的「到顶」和自动加载更早运行会多拉几页，这些都可能起放大作用，但不是根因。服务器真实数据量尚未取得。可以在开发者 SQL 页确认，它走独立只读连接，主锁被占时也能查：

```sql
SELECT (SELECT count(*) FROM core_messages), (SELECT count(*) FROM core_model_calls);
EXPLAIN QUERY PLAN SELECT id FROM core_messages WHERE model_call_id = 1 AND kind = 'Reply';
```

## 存储侧压测

`crates/mic-store/src/trace/tests.rs` 里的 `real_database_reads_stay_bounded`（`#[ignore]`）直接测 store 方法，不经过 HTTP。

- **准备**：在仓库外做一份副本，先清空 `core_endpoints.key_cipher`，再用 `python3 scripts/db/convert.py --db <副本> --apply` 转换到当前版本。不需要 `master.key`，测试会在副本旁生成一个临时密钥。原文件不动；副本含真实对话，不进仓库。输出只有耗时。
- **运行**：`MICNEXT_PERF_DB=<副本> cargo test -p mic-store --release real_database -- --ignored --nocapture`
- **范围**：取消息最多的会话，测上下文窗口、上下文占用、最后一条 id、Trace 会话列表、首页 run、会话用量、任务用量，以及 30 天和 366 天看板。任一项超过 300ms 即失败。
- **结果**（本机 release，同一份真实库副本，37k 条消息，会话 25 有 3.5 万条）：修改前为 `b0cc28e` 代码 + v30 库，修改后为 `b874279` 代码 + v31 库：

  | 项 | 修改前 | 修改后 |
  |---|---|---|
  | context_window | 27ms | 4ms |
  | context_usage | <1ms | <1ms |
  | 最后一条 id（订阅） | 61ms | <1ms |
  | trace_sessions | 21ms | 2ms |
  | trace_runs | 64ms | 4ms |
  | session_usage | 95.7s | 7ms |
  | schedule_usage | 96.4s | 11ms |
