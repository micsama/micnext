# B1：Web 会话分段加载

状态：已定（2026-10-12），选方案 B，滚到顶部自动加载。契约见 [B2](../blueprints/archive/web-message-paging.md)。

## 一、现状与实测

- 打开会话时，`/sessions/{id}/stream` 会回放该会话的全部稳定消息，然后发 `ready`，再推实时增量。前端把所有消息都放进 `SessionView.messages`（深层 `$state`），并全部渲染进 DOM。
- 之前的「卡」主要是两个已经修掉的 bug：前端贴底竞争（3b98736），以及 WebKit 压住流尾（fb75c7d）。全量回放本身目前不算慢。
- 本地实测，Chromium 下 612 条消息、288 KB 的会话：从打开到渲染稳定 150 ms，CPU 降速 4 倍（相当于手机）时约 0.5 s，DOM 约 5 千个节点，JS 堆约 16 MB。线上 `/s/4` 是 113 条、150 KB。
- 开销随消息数线性增长。Web 会话一般会新开，问题不大；微信会话是一个联系人一条，长期不换，会一直变长。按上面的比例，6000 条时手机打开要约 5 s，DOM 约 5 万个节点。分段加载主要是为这类会话做准备。

## 二、候选

### A. 以生效压缩为起点

先显示生效压缩之后的消息（从 `keep_from` 或 Boundary 开始），往上滚再加载更早的。

- 好处：语义好，「模型现在看到的」和「页面默认看到的」是一致的。
- 问题：
  - 加载量不可控。从没压缩过的会话照样全量加载；压缩很久以前发生的会话，保留段也可能很长。
  - 刚压缩完时，页面几乎是空的，用户一进来就得往上翻。
  - 撤回压缩后起点会变，流的起点要跟着重算。
- 结论：适合作为显示上的标记，不适合作为分页的单位。

### B. 按最近 N 轮，配合条数上限（推荐）

一轮 = 一条 `UserInput` 及其后、下一条 `UserInput` 之前的所有消息。

- 初始窗口取最近 N 轮（比如 20 轮），但总条数不超过 M（比如 300 条）。往上滚，每次再加载 N 轮，同样受 M 条限制。
- 好处：
  - 加载量可预测。
  - 按轮切开时，工具调用和结果大多在同一页。
  - 和有没有压缩无关。压缩产生的 Boundary 照常作为列表里的卡片显示，滚到那里就能看到。
- 问题：一轮内工具调用特别多（单轮超过 M 条）时，会在轮中间切开，ToolResult 和它的 ToolCall 会分到两页。前端已经能把找不到对应调用的结果单独显示，更早的一页加载进来后会自动合并，只需确认这一点。

### C. 数据全量，前端只渲染尾部

协议不变，`messages` 仍然全量，只渲染最后 K 条，往上滚再多渲染一些。

- 好处：零契约变更，改动最小。
- 问题：网络、JSON 解析和深层 `$state` 的开销仍然是全量。微信长会话依然会线性变慢，只解决了 DOM 这一部分。

### D. 虚拟列表

只渲染视口附近的消息，滚出去的就回收掉。

- 问题：
  - 消息高度不固定（Markdown、代码块、图片），滚动容易跳。
  - 和贴底逻辑会互相打架。
  - 浏览器自带的 Cmd+F 搜不到没渲染的内容。
- 结论：复杂度和这个场景的规模不匹配，不推荐。

### 可以独立做的小优化（与上面不冲突）

- `messages` 改用 `$state.raw`，追加时整体替换数组，省掉深层代理的开销。
- 图片加 `loading="lazy"`。
- 消息项加 CSS `content-visibility: auto`，让浏览器跳过屏幕外内容的排版和绘制。这一项和贴底的高度计算可能互相影响，要单独验证。

## 三、推荐方案（B）的大致契约

这一节只说个大概，定下方向后再写 B2。

- **流**：`/sessions/{id}/stream` 不带 `after` 时，从窗口起点开始回放。`ready` 增加 `has_earlier: bool`。重连仍然用 `after`，行为不变。
- **新接口**：`GET /sessions/{id}/messages?before=<id>`，返回 `{ messages, has_earlier }`。按同样的「N 轮 + M 条」规则往前取一页。
- **前端**：
  - 列表顶部放一个哨兵元素，进入视口就自动加载上一页。
  - 插入时保持「离底部的距离」不变，视口不跳。
  - 加载过的内容不回收。
  - 顶部显示「加载更早的消息…」或「已到最早」。
- **N 和 M** 放在 `limits.rs`，按使用情况再调。
