# 交叉核对：micnext 产品与架构设计（2026-09-23）

**状态**：第二轮核对中。已确认的方向见 [`product-roadmap.md`](product-roadmap.md) §二；
仍需决策的契约见其 §四与 [`../../todo.md`](../../todo.md)。本文是核对入口，
不代替 [`mic-message`](../blueprints/mic-message.md)、
[`mic-store`](../blueprints/mic-store.md)、
[`mic-core-module`](../blueprints/mic-core-module.md) 的 B2。

## 一、项目目标

- 单人自用、单进程的高质量 Rust agent 小项目，电脑用 Web、手机用个人微信。
- 轻量、可 hook、正交、可组合；外部边界强类型、失败行为明确、核心事实只有一处。
- 不支持钉钉、TUI、多实例/分布式、WASM，也不把 MCP 当内核的一等公民。
- 保留 Person 数据概念以统一身份与权限语义，但多人使用不是当前版本目标。

## 二、本轮已确认的设计方向

1. v0 先让 Web 闭环可用，再在同一版本接个人微信。Web 设置页提供微信注册/连接入口；
   具体注册与凭据流程要先核实 ClawBot 的实际接口。
2. Web 与微信是不同 Channel，各自的会话和上下文独立。Web 会话列表按 Channel 区分；
   切换会话后能正确回放历史与接续实时显示。后续长期记忆可以跨 Channel。
3. 微信单会话；`/clear` 清空上下文但保留历史，`/compact` 压缩。Web 不续聊微信会话。
4. 定时任务由模型自行决定是否调用 `send_message`。试运行允许漏推；Web 提供不调用
   模型的任务看板，显示任务、每次运行状态与详情、是否推送及目的地，再据实际结果
   决定要不要增加框架级推送策略。失败仍由框架记录并通知。
5. 定时任务不增加默认 Channel 配置。`send_message(to?, via?, text)` 省略 `via` 时
   回来源会话；需要发微信等其它 Channel 时由 agent 在调用中明确选择 `via`。
6. 定时任务每次用干净上下文，加上一次成功运行的最终回复作交接笔记；需要长期精确
   状态的真实任务出现后，再讨论专用持久状态。
7. 普通新消息按模型/工具边界插嘴；运行中的同步 shell 不承诺即时停止，不为此增加
   强制杀进程和取消落盘机制。提示词向 agent 说明限制。异步任务的主动停止另议。
8. 子 agent 按异步方向规划。同步/异步首先区别于调用方是否等待结果，但异步还需要
   独立执行句柄、完成回注、崩溃和停止语义；不能只改变 agent 下一轮何时说话。
9. v0 Web 使用固定 token；密码登录以后再做。
10. 微信绑定是低频操作：Web 设置页先确认保存，显示重启后生效；是否提供重启按钮
    取决于实际进程守护，不做配置热更新。
11. 基础工具的模型侧契约照搬 DSH `47f943859b`：`read/glob/grep/write/edit/bash`
    的名称、入参、必填项和默认值见 roadmap §2.3；工具简介、字段描述与使用提示
    也以 DSH 为底稿，由工具模块拥有，并删去 micnext 尚无能力的承诺；内部实现可优化。
    当前单人用户默认放行，不做逐次审批；可达范围由进程 OS 权限和部署沙箱决定。
    不把 `sandbox_permissions`/`justification` 带给模型。
    v0 使用 DSH 的后台禁用形态，`bash` schema 隐藏 `run_in_background`；v2 与
    job 运行时及 `job_output/job_list/job_kill` 一起启用。
12. 微信投递先记录尝试、外部响应与失败，不急于加显式 adapter ack 或去重。
    一次发送的完成判据和重启是否补发，待微信接入方式核实后定；日志不能证明已送达。

## 三、版本与尚未定的契约

- **v0**：Web 流式多会话与切换、基础工具、一个模型、崩溃收尾；接着接微信及 Web
  设置页。微信适配器、主动推送、注册与 Gateway 鉴权的具体契约待核实和起草。
- **v1**：定时任务与看板、Skill、压缩与 `/clear`、DeepSeek、用量展示、边界插嘴。
- **v2**：异步后台 shell 与子 agent、Hook、长期记忆、其它主动能力。异步子 agent
  不沿用“必定 `wait=true`”的旧设定。
- **v3**：trace/费用面板、重放比较、浏览器工具、语音等按实际需求推进。

## 四、全项目待核对点

1. **微信注册与配置**：已选保存后重启生效；设置页能否完成真实绑定、凭据存哪里、
   配置写入失败怎么显示、由谁提供重启按钮，待接入接口核实后定。
2. **会话列表与事件**：`mic-store` 现有 B2 尚无列举会话的公开 API；SSE 实时 chunk
   不是稳定 entry，不能直接把每个 chunk 的事件 ID 当 `SessionEntryId`。Gateway 和
   store B2 需在实现前补齐切换、重连、回放契约。
3. **微信投递与入站重复**：先记录发送尝试、外部响应和失败，不加显式 adapter ack
   与去重；接入后仍需定发送完成判据及重启补发行为，不声称恰好一次。
4. **定时任务可观察性**：看板从哪个模块取得任务、运行、推送事实？如何标记一次运行
   “没有推送”与“投递失败”？仅展示落盘事实，不引入模型判断。
5. **同步/异步执行**：后台 shell 和子 agent 的调用者、状态、完成写者、通知路由、
   崩溃收尾及停止权限需在 B1 画清；尤其子 agent 默认异步后，现有 `Task wait=true`
   文档要同步修订。
6. **人工审批**：v0 基础工具默认放行；以后哪些副作用需要审批、在微信纯文本交互中
   如何确认、等待期间新消息和崩溃如何收尾，另行 B1/B2。
7. **边界与权限**：固定 token 能访问哪些 Gateway API？Web 查看微信历史、微信连接
   凭据、shell 工具分别由谁授权？单用户也需明确最小权限边界。
8. **规模与限额**：模型轮次、工具输出、附件、历史与 SQLite 的尺寸边界，以及失败时
   用户能看到什么；这些是 v0 运行质量问题，避免无限增长或静默截断。
9. **基础工具与退出**：v0 默认放行，可达范围由进程 OS 权限与部署沙箱决定。
   工具 B2 要定路径基准、
   精确替换歧义、超时/输出上限及错误结果；进程关闭时正在执行的命令与未完成投递
   怎样收尾，才不误报成功或自动重放副作用？

公开契约在对应 B2 批准后再实施。
