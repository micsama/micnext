# B1：专题

日期：2026-11-06。状态：讨论中。第 3 节已定方向，草案见 [B2](../blueprints/topics.md)，待批准；第 4、5 节在讨论，暂不实现。

## 1. 需求

human 经常和 agent 围绕若干专题长期聊天，有研究类、项目类，也有持续追踪类。每个专题都会积累笔记和数据，希望在任何会话里都能接着聊，包括微信那个长期单会话。

已确认的偏好：

- 笔记和数据都有。human 很少亲手改，主要通过对话让模型维护；想看内容时，让模型生成网页。
- 进入专题靠自动识别。human 说清楚「聊聊 X」本身就是主动入口，不再另设 `/专题` 指令或选择器。
- 一次对话很少同时涉及多个专题，但不排斥。
- 专题和标签是两回事：标签是笼统的分类，专题是带内容的知识容器。两者不合并，今后的关系暂不定。

## 2. 与现有机制的关系

- **skill**：形态几乎一样，都是一个目录加一段描述，描述进索引，模型按需加载。区别在内容：skill 讲「怎么做事」，基本稳定；专题存「知道了什么」，会持续增长、反复改写。
- **压缩**：会定期回看完整历史，是把结论沉淀进专题的天然时机，见第 4 节。
- **微信长会话**：不需要按专题拆会话，在同一会话里先后打开不同专题即可，符合「长会话是设计内的」。
- **长期记忆**：路线图里列为后续能力。专题可以算是它的第一种落地形态：按主题分区，内容可以直接读。

## 3. 专题本体（已定方向）

### 形态

`<data_dir>/topics/<name>/`，一个目录一个专题：

- `TOPIC.md`：frontmatter 写 `description`，用于索引和识别。正文是「现状」：当前结论、已做的决定、未决问题，以及目录里资料的导读。正文是不断改写的快照，不是流水账。
- 其余文件随意放，比如数据、抓取结果、脚本、模型生成的网页。

新建、改名和整理都由模型用现有的文件工具完成，和 skill 一样。

### 识别与进入

| 候选 | 做法 | 结论 |
|---|---|---|
| **A** | 照搬 skill：索引放进 context，新增 `topic { name }` 工具，返回现状正文、目录路径和文件清单 | **采用** |
| B | 只给索引，不加工具，模型自己用 `read` 读 `TOPIC.md` | 占位规则和「打开过哪些专题」都只能从文件路径推断，是跨层的隐含约定 |
| C | 专题直接做成 skill | 一个概念承载两种语义；skill 索引会被话题撑大，`/name` 补全也会混进专题 |
| D | 杂活模型预先分类，自动注入专题 | 每轮多一次调用，猜错时白白注入一大段；暂不需要 |

选 A 意味着专题由 harness 管理，而不只是 prompt 约定。它的价值是「这段对话打开过哪些专题」成为可以直接查询的事实，可以从 `topic` 工具的调用记录里推出来，不用新建表。第 4 节判断是否派出整理时依赖这个事实，以后做专题页列出相关会话也会用到。`topic` 的结果按普通工具输出占位，不进 skill 的重载机制，见 B2。

### 沉淀

| 候选 | 做法 | 结论 |
|---|---|---|
| **a** | 在通用提示里约定：打开专题后，出现新结论或新数据就更新专题 | **采用**，成本最低，但执行与否取决于模型 |
| b | 压缩时由压缩自己输出专题改写，并负责写回 | 否决：压缩会为专题长出一套专属逻辑；改为第 4 节的 fork 整理 |
| c | 会话闲置后单独跑一轮沉淀 | 暂不做；第 4 节已经覆盖了「可靠时机」这一诉求 |
| d | human 说「记一下」 | 自然可用，不需要机制 |

### 怎么查看

先不加页面，想看就让模型读给你，或者生成网页。专题页（渲染 `TOPIC.md` 并列出相关会话）等专题真正积累起来再说。在 Web 里直接打开模型生成的网页，需要 Gateway 托管 agent 产出的文件，安全边界要另行讨论，不放在本题里。

## 4. 压缩时派出 fork 整理（讨论中）

### 思路

把「压缩时沉淀」拆成三项正交能力的组合，避免为专题单独造一个模块：

- **压缩**只负责在合适的时候派出一个整理者，不知道专题是什么；
- **专题**只提供目录、索引和「打开过」的事实，不知道压缩是什么；
- **fork** 是一种通用的子会话形态：继承父会话当时的上下文，然后接着执行一段新的指令。

整理需要多步模型调用（读文件、比对、改写），所以放在独立的会话里跑，不阻塞主对话，也不占用主会话的上下文。

### 已定

- **开关**：设置里加一个实验开关，默认关闭，逐步试验后再决定是否常开。
- **前缀沿用父会话**：fork 使用和父会话相同的 system prompt 与工具定义，以便命中前缀缓存。职责和限制写在末尾的指令消息里：只整理专题文件，不继续原任务，不与用户对话。
- **派出条件**：开关已打开，且被压缩的那段对话里调用过 `topic`。压缩本来就会扫描窗口里加载过的 skill，读「打开过哪些专题」是同一种做法。闲置后的提前压缩不派出，因为那时缓存已冷。
- **承载方式：照定时任务的「一轮」来做**（human 提出）。下面列出它和其他候选的对比。

### 承载方式

后台任务模型和整理有两处冲突：

- **来源**：后台任务以模型的一次工具调用为来源，`core_jobs.origin_reply_id` 和 `origin_call_index` 必填，停止、`job_stop` 和交付对象都挂在上面。压缩派出的整理没有对应的工具调用。
- **交付**：子 agent 每次运行收尾都写 Completion 并唤醒父会话。整理结果不需要主模型回应，唤醒一轮纯属浪费，还会打断压缩之后的对话节奏。

| 候选 | 做法 | 结论 |
|---|---|---|
| **丁** | 照定时任务：每次整理新建一个 `Triggered` 会话，来源是压缩边界，输入是 `Trigger` 消息，结局只看这次运行的状态 | **采用**；不改任务模型，不新增交付方式 |
| 甲 | 仍然登记成 agent 任务，来源新增「压缩」，交付新增「通知」 | 来源和交付各要多一个变体，`core_jobs` 的 schema 也要改 |
| 乙 | 压缩前提示主模型自己调用 `agent { fork: true }` | 完全沿用现有任务模型，但仍会唤醒父会话，而且派不派出取决于模型 |
| 丙 | 作为压缩内部的后台子会话，只在 Trace 里可见 | 绕开了停止、重启和可见性的语义，等于另起一套机制 |

丁方案的行为：

- **来源**：会话类型是 `Triggered`，来源指向压缩边界消息（见第 5 节 R1）。`Trigger` 消息和压缩在同一个事务里提交。
- **结局**：和定时任务的一次触发一样，不写 Completion，也不唤醒任何会话。
- **可见**：父会话的压缩边界上显示「专题整理：进行中 / 已完成 / 失败」，由整理会话的运行状态推导，不另写消息。点击可进入整理会话，查看过程或停止。整理会话不进侧栏列表，只读。
- **停止与重启**：停止用会话停止；重启时由现有的恢复流程把运行记为中断，不重放。撤销压缩不会回滚已经写入的文件。
- **与父会话的关系**：通过来源（压缩边界）表达，不借用 `parent_session_id`（见第 5 节 R4）。

### 待定

1. 越界的工具调用是在执行时拒绝（第 5 节 R2），还是只靠指令约束？倾向执行时拒绝：工具定义是为了缓存而原样沿用的，并不代表都允许调用。
2. 归档父会话时，是否顺带停止正在进行的整理？
3. 整理会话的运行上限（墙钟时间、轮次）取多少？
4. `agent` 工具暂不开放 `fork` 参数，因为目前没有明确的消费方。

## 5. 触发式运行的正交梳理

丁方案让整理和定时任务共用「触发式运行」。现有实现是按「只有定时任务一种触发」写的，下面盘点哪些已经通用，哪些把定时任务的规则套到了所有 `Triggered` 会话上。

### 现状盘点

| 位置 | 现在怎么判断 | 性质 | 加入第二种触发后的问题 |
|---|---|---|---|
| `SessionKind::Triggered { module, ref_id }`、`Trigger` 消息 | 通用 | 来源与输入 | `ref_id` 是字符串，由各处自行解释 |
| `channel_prompt`、`jobs::tree`、`session_channel` | 按 module 查表或取名 | 通用 | 无 |
| `scoped_tools`、`JobPort` 禁止后台执行 | 所有 `Triggered` | 无人值守约束，规则来自定时任务 | 规则合理；但 fork 要沿用父会话的工具定义，和「工具列表即许可」冲突 |
| `run.rs` 的墙钟与轮次上限 | 所有 `Triggered` 都用 `SCHEDULE_RUN_TIMEOUT` | 名字属于定时任务，作用于全部触发 | 整理会被套上定时任务的常量 |
| `run.rs` 在运行开始和收尾时调用 `schedules.publish_changed`、`settled` | 所有 `Triggered`，内部再用 `fire_of_run` 判断 | 定时任务专属回调，硬编码在 run 引擎里 | 整理收尾要刷新压缩边界的状态，只能再加一个硬编码分支 |
| `compaction::instruction_note` 选择摘要提示词 | `module == SCHEDULE_MODULE` | 定时任务专属 | 字符串判断分散在多处 |
| `push.rs` 的来源标签，Gateway 的 `item` 与 `writable` | `module == SCHEDULE_MODULE` | 展示规则 | 同上；整理会话需要「不进列表、只读」 |
| `core_schedule_fires` | 定时任务自己的表 | 专属事实 | 无；整理的来源由会话本身表达 |
| 忙时跳过、失败推送、连续失败暂停 | 定时任务的 `settled` | 专属策略 | 无 |

结论：通用骨架已经成立，包括来源、输入、渠道说明、无人值守和重启中断。问题集中在两处：

- **来源是弱类型字符串**：「这是哪种触发」靠 `module` 字符串，在 run 引擎、压缩、推送和 Gateway 四个地方分别比较。
- **run 引擎直接调用定时任务**：生命周期回调和运行上限，都用「是不是 `Triggered`」代替了「是哪种触发」。

另外，fork 需要的「前缀沿用父会话」在现有结构里没有落脚点。system prompt 按会话自己的类型取渠道说明，工具列表既是给模型看的定义，也是允许执行的范围。

### 候选重构

- **R1. 来源强类型化**（倾向，可以独立先做）：store 读取会话行时，把 `(trigger_module, trigger_ref)` 解码为枚举 `Trigger`。现在只有 `Schedule(ScheduleId)`，做整理时再加 `Compaction { boundary: MessageId }`。`SessionKind::Triggered` 改为携带这个枚举，表结构不变。四处字符串比较都改为对枚举做 `match`，每种触发的差异都在 `match` 里写明：收尾回调、运行上限、摘要提示词、列表展示和可写性。
  - 两种触发都在 mic-core 内部，用一个枚举就能把差异写清楚，不需要模块登记表或 trait，也不为假想的第三方触发预留机制。
  - 运行上限的常量按触发种类命名；在整理有了自己的取值之前，先不拆开。
  - 这会改动 mic-store 的公开类型 `SessionKind`，调用方只有 core 和 Gateway。
- **R2. 拆开「给模型看的前缀」与「允许执行的范围」**（做 fork 时再做）：fork 的 system prompt 和工具定义取自父会话，允许调用的范围按自己的职责确定。越界调用返回 business 错误，并说明职责。没有 fork 之前，这一拆分没有消费方。
- **R3. fork 的历史基底**（做 fork 时再做）：子会话记录父会话、派出时父会话的边界和截止消息。组装上下文时，先渲染父会话的那一段，再接上自己的消息，不复制消息。必须记录派出时的边界：父会话紧接着会提交新的压缩边界，不能读父会话当前的边界。
- **R4. `parent_session_id` 只表示子 agent 的父会话**：整理会话和原会话的关系由 `Trigger::Compaction { boundary }` 表达。这样子 agent 的任务树（归档时整树停止、后台任务归属）不会混进整理会话；归档时要不要停止整理，在 `Compaction` 分支里显式决定（第 4 节待定 2）。

### 建议顺序

1. 先做 R1：它是独立的重构，不依赖专题，也能先去掉现有的字符串约定。
2. 再实现第 3 节的专题本体。
3. 专题用起来之后，如果确认需要整理，再把第 4 节和 R2、R3、`Trigger::Compaction` 一起写成 B2。
