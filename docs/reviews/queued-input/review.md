# queued-input 蓝图复审

**已被后续决策替代**：现方案由后端用 `InputsClaimed` 事件和 `ready.queued` 提供认领事实，见 [蓝图](../../blueprints/archive/queued-input.md)。下文关于旧后端快照方案的建议不再适用。

日期：2026-10-23。范围：按 human 明确的“只做轻量 UI 区分，不增加复杂或防御性机制”重新审查当前草案；不修改蓝图与实现。

## 结论

现有方案的规模合适：从现有 run_id / held 事实查询一组消息 id，经现有会话 SSE 同步，Web 只按集合显示样式。中途 absorb 不产生新消息，补一个提交后的 InputsAbsorbed 事件有当前明确消费者，不需要另建队列、持久化状态或任务生命周期。

## 一处需要补充的展示规则

### Q1 · P2：已归档会话不显示“排队中”

位置：`docs/blueprints/queued-input.md:7`、`:21`。

未认领输入可能在归档前留下；归档后不能继续认领（`crates/mic-store/src/scheduling.rs:65`），所以仍标“排队中”会误导用户。

上轮建议新增归档查询条件和 SessionChanged 排队重查，超出了这项纯展示需求。轻量处理只需规定：**已归档会话不显示排队样式**。Web 已有 info.archived_at，并且现有 SessionChanged 会刷新该字段（`web/src/state/session.svelte.ts` 的 #refreshTitle / #apply），渲染时加一个条件即可。排队 id 仍来自服务端；用已知归档字段控制提示是否显示，不是在客户端推断认领状态。

无需给输入补终态、改 held、增加事件、请求或存储字段，也不必为归档改变 Store 查询。

## 契约补全说明（不作为独立设计缺陷）

上轮 Q2 所说的 Kernel::queued_inputs 转发仍需写进 B2，因为它是公开方法；但它只是一层沿现有消息查询路径的转发，不需要新结构、查询服务或 HTTP 接口。Store 的 async / Result 签名一并写清即可。

## 实施时保持轻量

- ready 和 queued 都直接替换整组 id，不合并增量、不维护客户端队列；不新增轮询、专用连接、重试或恢复流程。
- InputsAbsorbed 仅在非空输入成功认领后发出，查询失败沿用现有 SSE 错误处理。这是既有写入/事件顺序，不另建防御机制。
- “排队中”标记挂在整条 UserInput 上，覆盖纯图片/纯文件消息；“气泡变淡”不应使无文字的消息没有提示，不改附件组件与加载流程。
- 保留一个 Store 功能测试；有必要时补一条认领→事件→快照更新的功能验证即可，不展开成组合测试矩阵。断线重连沿用 ready 重建当前状态。

不建议为本功能新增持久化列、迁移脚本、排队状态枚举、取消/重排入口、队列管理器或独立状态机。
