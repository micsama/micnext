# B1：把本地内容挂到 Web 子路径

**状态：暂缓（human 2026-11-12）。** 方向未定，后面再议。

## 动机

agent 在服务器上产出的网页内容（报告页、图表、看板、小工具），以及它起的本地 web 服务，目前用户在手机上看不到：`send_file` 发 html 只能下载，本机端口没有对外暴露。想法是让 agent 用一个工具，把它挂到 micnext 自己的地址下，比如 `https://<micnext>/p/<名字>/`，用户点链接就能打开。

## 硬约束：同源

挂载内容和 micnext 同源。登录 cookie 是 `Path=/`，挂载页面的请求也会带上；页面里的 JS 能直接 `fetch('/api/...')`，拿到完整管理权限，包括改设置、写 SQL、一键更新、读聊天记录。`HttpOnly` 和 `SameSite=Strict` 都挡不住同源请求。挂载内容来自模型生成或第三方程序，必须隔离，不能裸挂。

## 候选

### 挂什么

| 方案 | 能做的 | 代价 |
|---|---|---|
| A. 只挂静态目录或文件 | 报告、图表、单页工具 | 实现小：按路径读文件，防路径穿越 |
| B. 另外代理本机端口 | 跑起来的 web 应用、开发服务器 | 要处理 WebSocket（热更新）、超时、服务挂掉；很多应用默认挂在根路径（如 Vite 生成 `/assets/...`），挂到子路径下要配 base |

### 怎么隔离

| 方案 | 效果 | 代价 |
|---|---|---|
| 1. 响应加 `Content-Security-Policy: sandbox allow-scripts`（不给 `allow-same-origin`） | 页面成为匿名源，读不到 `/api`、不带走登录态 | 页面内 localStorage 和 cookie 不可用；静态报告基本不受影响，依赖登录态的应用会坏 |
| 2. 独立子域名或端口 | 隔离彻底，应用不受限 | 部署要多配泛域名证书或端口；micnext 的 cookie 不跨源，访问鉴权要另做（例如带签名的链接） |

方案 1 只对 A 足够。B 里的应用常要 cookie 或 localStorage，基本只能走 2。

### 访问权限

- 必须登录才能访问（沿用现有 cookie 校验），避免把本地文件或服务公开到公网。
- 或者生成带过期时间的签名链接，方便转发给别人看。这样会多出一种分享语义，当前没有需求。

### 生命周期与归属

- 挂载属于创建它的会话，同会话可列出、撤销；会话归档时一并撤销。
- 是否跨重启保留：保留就要存表（gateway 模块的 `web_` 表）；不保留就放内存，重启后 agent 重新挂。
- 有没有过期时间：不设上限是一种明确选择，也可以默认保留 N 天。

### 工具与页面

- 工具由 gateway 模块经 `Registry::tool` 登记（只有 Web 能打开），比如 `mount`，参数为名字和路径，返回 URL；撤销复用同一个工具。
- Web 端是否需要列表入口：最少只在工具结果里显示可点链接；要集中管理，再放到设置或开发者诊断里。
- 定时任务会话能不能挂：能挂的话，推送里可以直接带链接。

## 倾向

先做 A + 1：
- 挂静态目录或文件，强制登录，统一加 CSP sandbox；
- 挂载归会话，存 `web_` 表，跨重启保留，会话归档时撤销；
- 工具结果里给链接，先不做管理页面。

B（代理端口）等出现具体应用再定，届时连同隔离方案 2 一起考虑。

## 待 human 定

1. 范围：先只做静态（A），还是一开始就要端口代理（B）。
2. 隔离：接受 CSP sandbox 的限制，还是要上独立子域名或端口。
3. 挂载是否跨重启保留，有没有默认过期时间。
4. 要不要签名分享链接（给未登录的人看）。

## 2026-11-13 讨论：端口代理的部署方案

**现状**：公网只有 `https://<IP>` → Caddy(443，短期 IP 证书) → `127.0.0.1:7878`，没有域名；本机防火墙不拦新端口，暴露面取决于安全组。

**已修**：网关的写请求只接受本站页面发起（`Sec-Fetch-Site: same-origin`，没有这个头时比对 `Origin` 与 `Host`）。此前同 IP 其他端口或兄弟子域名上的页面能带着 cookie 触发一键更新、归档、停止等不带请求体的 POST，`SameSite=Strict` 挡不住同站请求。

**候选路线**：
- 无域名期：agent 的服务只绑 `127.0.0.1` 的固定几个端口，Caddy 在安全组开放的端口上做 TLS + `basic_auth` 转发。剩余风险：同主机不区分端口，这些服务能收到 micnext 的 cookie；它们由 agent 起，而 agent 本就有 shell，可以接受，不跑来路不明的第三方服务即可。
- 有域名后：每个工具一个主机名，统一走 443，安全组关掉工具端口；agent 侧不变，只改 Caddy 与「内部端口 → 公网地址」对照表。
- 会话 cookie 已加 `Secure`（只经 HTTPS 访问）。
