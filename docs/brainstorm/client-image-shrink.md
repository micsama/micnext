# B1：浏览器上传前预缩图片

状态：待定，未确认要做。

来源：human 2026-11-12。单条消息的图片上限提到 10 张后，手机一次传多张原图，加上 base64 膨胀，可能有几十 MB，上传慢。

## 现状

图片在服务器上统一规整（`mic_media::normalize`，见 [image-normalize](../blueprints/image-normalize.md)）：长边 ≤ 2048 且 ≤ 1 MiB 的 PNG/JPEG/WebP 原样保留；其余缩到 2048 以内，有透明像素的存 PNG，否则存 JPEG（质量 85）。Web 和微信共用这一个入口。

## 结论：服务器规整保留，浏览器只做可选的预缩

- 微信图片不经过浏览器，服务器规整必须保留。浏览器传来的内容也不可信，服务器照样要检查。
- 浏览器只做一件事：PNG/JPEG/WebP 图片长边超过 2048 或大于 1 MiB 时，用 `createImageBitmap` 加 canvas 缩到 2048 以内，转成 JPEG。带透明的图和 GIF 原样上传，交给服务器处理。
- 预缩后的图通常满足服务器的原样保留条件，不会被再压一次。电脑拖进来的原图照样走服务器规整，上限不变。

## 风险

- 浏览器出的 JPEG 如果超过 1 MiB，服务器会再压一次，画质损失两次。预缩时可以把质量设得略低，避开这个情况。
- iOS Safari 的 canvas 总像素有上限；照片方向要用 `imageOrientation: "from-image"` 处理。

## 不做

- 把规整整体搬到浏览器。
- 上传从 base64 JSON 换成 multipart：只省三分之一的膨胀，收益比预缩小，以后需要再单独评估。
