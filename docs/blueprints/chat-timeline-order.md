# 会话消息按发生时刻排成一条线

状态：IMPLEMENTED，human 已批准实现，本地验收通过，待页面人工验收。

## 问题

异步 shell 在 agent 第一次总结生成期间结束。服务器上的实际数据：

| id | 消息 | 请求开始 | 落盘 |
|---|---|---|---|
| 262 | Completion（后台完成） | | 01:14:28 |
| 263 | Reply（第一次总结） | 01:14:19 | 01:14:53 |
| 264 | Reply（补充收尾） | 01:14:53 | 01:14:57 |

现在消息按 id 排，id 只反映落盘先后，所以页面显示为 262 → 263 → 264：后台完成跑到了第一次总结前面，两次总结紧挨着，中间看不出是什么触发了第二次。

模型这边：生成 264 时，`arrange` 把 262 临时挪到末尾，这次请求的顺序是对的；但之后的请求又按 id 排，模型看到的历史和它当时看到的不一致，提示缓存的前缀也在这里断开。

## 规则

会话里的消息排成一条线，每条按它发生的时刻排。压缩边界是例外，规则不变。

- **AI 回复**：发生时刻是读取上下文窗口的时刻。回复只基于这一刻读到的上下文，所以之后到的消息，不论是用户输入还是后台回报，都排在它后面。重试复用同一个请求，也沿用同一时刻。
- **工具结果**：模型请求里由 `order()` 保证调用和结果相邻，同步工具执行期间到的消息移到结果后面。页面上，配对的 `ToolResult` 本来就不单独显示（`MessageList` 隐藏它，结果显示在调用所在的那条回复里），所以按位置排序不会把调用和结果拆开；执行期间到的消息显示在整条回复之后。只有调用不在已加载范围时，`ToolResult` 才单独显示，这时它按自己的位置排，行为和现在一样。
- **异步任务**：分成两个时刻。派发回执是工具结果，跟随工具调用；Completion 按任务结束的时刻排。
- **其余消息**（UserInput、Command、Notification 等）：按落盘时刻排。

按这个规则，上例排成 263 → 262 → 264。

## 契约

- `Reply.created_at` 改为该次请求读取上下文窗口的时刻，原来是 `finished_at`。HTTP 字段不变，只是含义变了。悬停栏显示的时间随之变成这一刻。
- `mic-store::NewModelCall` 新增 `context_at: i64`，`record_model_call` 用它写 Reply 的 `created_at`。不落库，也不改 `core_model_calls`。`started_at` / `finished_at` 仍按每次尝试记录，耗时统计不变。
- **位置 = `(created_at, id)`**。上下文读取、压缩保留、页面展示都按位置排。
- **id 只表示写入先后**，用于 SSE 续传游标、分页游标，以及"某次请求看到了哪些消息"这类集合判断，不再表示顺序。
- 删除 `tail` 整条链，见改动点 6。
- 旧数据不迁移：旧 Reply 的 `created_at` 仍是落盘时间，读路径不区分新旧。旧消息的 `created_at` 顺序和 id 顺序一致，所以旧历史的排序不变；但去掉 tail 搬运后，旧会话下一次请求里末尾几条的顺序可能和上次不同，缓存会在那一处断一次。

## 改动点

后端：

1. `run.rs::call_model`：读窗口前取 `context_at = now_ms()`，所有重试共用，传给 `NewModelCall`。`record_model_call` 用它写 Reply 的 `created_at`。
2. `read_range`：改为 `ORDER BY m.created_at, m.id`。
3. `through`（这次请求看到的最后一条消息）改为窗口内的最大 id，不再取排序后的最后一条。涉及 `context_window` 里计算 `filtered` 的地方、`run.rs::call_model`、`compaction.rs::history_request` 三处。
4. 压缩保留起点 `keep_from`（一条 Reply 的 id）：凡是按 id 大小判断是否在保留段里的地方，都改为按位置比较。涉及 `window_start` 的 SQL、retention 的 `quoted` 过滤，以及 store（`commit_compaction`）和 kernel（重建压缩请求）里统计 `kept` 的两处。不改的话，保留起点那条回复生成期间到达的消息 id 比它小，会被当成已压掉。
5. `arrange`：删除把本步输入挪到末尾的那一步，只保留 `order()`。函数是否保留，实现时视调用方而定。
6. 删除 `tail` 整条链：`ModelCallContext.tail`、`run.rs` 中收集 tail 的代码、`request::build` 的 `tail` 参数、kernel 重建请求时传入的 tail、store 写入和 trace 读取 `core_model_call_inputs` 的 `'tail'` 角色。加一条 schema 迁移：删除 `role = 'tail'` 的行，并从 CHECK 中去掉 `'tail'`。**旧调用的 tail 重放不保留**：重建旧请求时不再搬运，所以和当时实际发出的请求可能在末尾几条顺序上不同。这一点 human 已确认。

前端：

7. 消息列表按位置插入：SSE 收到的消息插到对应位置，分页取回的一页也合并后再排序。
8. 续传游标改用已加载消息里的最大 id，分页游标改用最小 id，不再取列表首尾两条。
9. 草稿：草稿存在期间新到的消息显示在草稿下面；Reply 落盘后按位置插回，草稿原地变成回复，下面的消息不动。

## 已知边界

- **毫秒级竞争**：消息的 `created_at` 在进入 store 写队列之前就取好了。如果某条消息先取了时间，但排在读窗口之后才写入，它的时刻早于 `context_at`，模型却没看到它，结果会排到回复前面。窗口只有写队列排队那一点时间，接受这个边界。
- **首字之前没有草稿**：请求已经开始、首个 token 还没到时，新到的消息先显示在最下面；Reply 落盘后它会挪到回复下面，有一次跳动。
- **分页切在中间**：分页正好切在"回复"和"它生成期间到的消息"之间时，往上翻加载出来的消息会插到已显示的回复下面。
- **排队的 Command**：一次 run 不会越过排队中的 Command 去接收后面的输入，所以 Command 后面的输入可能比后续几次回复更早，而这几次回复并没有看到它们。只在 run 执行中发 `/compact`、`/clear` 时出现，本次不处理。

## 验收

两个 store/core 功能场景，历史重建的断言并入其中；页面交给人工。

- **顺序稳定**：依次构造"读窗口 → 后台回报落盘 → Reply 落盘 → 下一次请求"。检查 `context_window` 的顺序是 Reply → 回报，之后的请求顺序不变；按调用记录重建这次请求，结果和实际发出的一致。
- **压缩保留**：保留起点那条回复生成期间到达的消息仍留在保留段里；重建压缩请求时 `kept` 计数正确。
- **页面（human）**：复现异步 shell 在总结期间结束，页面显示为"总结 → 后台完成 → 补充收尾"，刷新后顺序不变。
