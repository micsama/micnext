# 服务器 Codex 首输出延迟排查

日期：2026-10-22。状态：**暂缓，human 要求先记录，不急于开展实验**。

## 现象与目标

human 反馈：服务器上的 micnext 使用 Codex 接入时，TTFT 经常达到十几秒。具体模型、思考档位、受影响会话及发生时间待确认。

后续通过隔离实验梳理请求链路，判断耗时主要发生在连接与上传、上游等待、首次有效输出，还是 Web 展示阶段，再决定是否需要修改实现。

## 已确认的计时口径

- `crates/mic-core/src/attempt.rs` 从一次模型调用尝试开始计时；首次非空正文、可见思考或工具调用增量到达时记录 `first_output_at`。
- `crates/mic-provider-openai/src/responses.rs` 不把 `response.created`、`response.in_progress` 等生命周期事件当作有效输出。因此当前 TTFT 包含请求发送、网络等待及有效输出前的等待，不能等同于连接耗时。
- 当前记录不能单独区分响应头、首个 SSE 事件和首次有效输出的到达时间。
- 进度仅到本地代码核对；服务器访问入口尚未确认，服务器实验尚未开始，没有本次实测根因结论。

历史线索：[2026-10-21 网络排查](../../brainstorm/gpt-network-failure-2026-10-21.md)记录过服务器代理链路吞吐低、图片请求上传失败。这只能作为复测线索，不能直接认定是本次延迟原因。

## 恢复排查后的实验顺序

1. 确认服务器访问入口、部署版本、具体模型与思考档位，从既有 Trace/诊断 SQL 读取近期调用的 TTFT、总耗时、输入量、缓存命中与重试情况。
2. 保持模型与档位，使用简短、无工具副作用的隔离请求，记录请求体字节数及请求开始、响应头、首 SSE、首次有效输出、结束的相对时间。只记录必要元数据，不记录凭据和完整请求正文。
3. 对比最小上下文与能代表慢请求的输入规模，区分连接、上传及上下文处理的影响；同组重复少量次数，避免用单次波动下结论。
4. 再单独改变思考档位，必要时对比已有可用网络路径；不同时改变模型、上下文和代理配置。
5. 将服务器直接请求与 micnext 调用对照；只有后端已及时输出而页面仍迟到时，再检查 Gateway SSE 和浏览器展示链路。跨机器时间不直接用墙钟相减。

上游内部排队、预填充与不可见推理可能无法仅靠客户端完全拆开，应保留可观测范围的限制。实验结果出来后再决定是否需要长期保留阶段耗时日志。
