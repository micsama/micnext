# B1：压缩后的保留规则

状态：方向已定（human 2026-10-19），契约见 [B2](../blueprints/archive/compaction-retention.md)。前作 [context-compaction](context-compaction.md)（B2 已 CLOSED），本篇只改「压完留下什么」，触发、`/compact`、撤回、文件快照不变。

## 现状与问题

压缩后上下文 = 摘要 + 最近 N 步原文（默认 15）+ 必读文件快照。

- 步的大小差得多，15 步可能几千 token，也可能一次读大文件就占半个窗口。保留段没有总量上限，压完仍接近阈值时会接连再压，每次都是一次完整调用加一次缓存失效。
- 保留下来的多是最近的工具输出，量大、过时快；用户原话反而被改写进摘要，多次压缩后一轮轮走样。
- 摘要覆盖整段历史，与保留段重复。

## 已定

### 1. 保留原文按当前上下文长度的比例取

设置项「保留步数」改为「保留原文 %」，默认 15%，基数是当前历史的估算总长，不是模型窗口。

最新一步始终保留；从它往前逐步累加估算 token，更早的步只有整步放得下预算才保留，放不下就停。最新一步本身超预算是明确的例外（它是模型正在处理的内容），不做拆步。步仍是一次模型回复加其全部工具结果，切点只落在步起点，工具调用与结果不拆开。正在等结果的那一步始终在内。

每步 token 按第 2 条替换占位之后的大小，用现有的保守估算（与上下文占用圆环同一口径），不用两次调用的 `input_tokens` 差值。

### 2. 保留段里的旧工具输出替换为占位

长工具输出信息密度低，有用的部分已沉淀进模型的后续处理、摘要或写出的文档，所以保留段里也清理：

- 最新一步的工具结果原样保留；更早的、超过阈值（暂定 2k token）的结果换成一行占位：工具名、关键参数（路径、命令）、原长度、「要点见摘要」。不承诺重新获取：命令输出、网页等重跑结果未必相同。
- 失败与报错结果保留原文。
- 只在压缩时做，平时不清理：压缩本身会让前缀整体失效一次，此时清理不额外破坏缓存；压完后保留段的呈现固定，前缀重新稳定。
- 总结请求本身仍用未清理的原历史，沿用主对话前缀争取缓存命中。

### 3. 用户原话由 harness 补回

本次被压掉的范围内（上一有效窗口起点到保留段起点）的用户输入，按时间顺序原样放在摘要之后，作为一块独立内容，不伪装成对话轮次。

- 尽量全保留，不设总额。
- 单条不超过 500 token 放全文。
- 超过 500 token 的不放全文，只保留首尾：开头约 300 token + 「……省略约 N token……」+ 结尾约 150 token。带日志的输入，真实诉求通常在首尾；中间的长内容信息密度低，关键部分会出现在后续 AI 的解析里，交给摘要处理。
- 原话从会话记录取，不从摘要取。

### 4. 摘要指令补硬信息

摘要分节不变，指令里要求照抄：文件路径、错误原文、用户明确的约束、未完成任务；摘要覆盖保留段之前的历史，并提炼保留段里本次将被占位替换的工具结果的必要信息；保留段其余内容不再复述。总结请求本就带着这些原文，指令里列出将被替换的结果即可，不加调用、不存副本。

## 未定

- 更早压缩范围里的用户原话是否也一直带着：带着则多次压缩不丢原话，但内容只增不减；不带则只靠累积摘要。先实现「只带本次范围」，看实际长度再定。
- 工具输出 2k、用户原话 500 / 300 / 150 token 等阈值交给验收微调，放 `limits.rs`。

## 影响面（B2 写清）

- 设置：`compaction_keep_steps` 改为百分比列，schema、设置页、备份格式一起改。
- 压缩边界：保留段起点仍是 `keep_from`；保留段的占位规则在组装请求时确定性生成，或由边界记下被替换的结果 id，B2 二选一。
- 请求组装：摘要后加入用户原话块；上下文占用圆环的构成随之调整。
- Web 的压缩分隔条：「保留最近 N 步」改为显示保留的步数与约 token 数。
