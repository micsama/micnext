# B1：对话记录与用户所见一致

**状态：方向已收敛（2026-10-09）：长期记录与解释、临时微信媒体打扁；并发可见性选候选 A（解释关联输入，窗口按关联过滤）；确认结论见 §六，第一步见 [B2](../blueprints/conversation-parity.md)**

## 一、触发

微信用户只发一张图片：入站不落 UserInput，只追加 Notification「暂不支持这类消息。」。
模型看到一条没头没尾的通知，误判为「自己的 Markdown 回复被微信拒收」。
用户看到的是「我发图 → 系统说不支持」，模型看到的只有后半句。

## 二、早期原则（历史提议，以后文确认结论为准）

对话记录就是用户看到的那段对话，模型读同一份：

1. **用户做了什么就记什么**：每次被接收的入站都落一条 UserInput。不能交给模型的片段
   （不支持的媒体、当前模型不能看的图片）以强类型占位保留「是什么、为何没处理」，不丢弃、不伪造成文字。
2. **系统对用户说的话，模型看到同一句**：面向用户的系统提示一律是 Notification，
   用户与模型看到同一文本；文本须对双方都成立——说清对象和原因，不写「这类消息」这种需要上下文才懂的指代。
3. **单向通道只留 HarnessNote**（只给模型，如预算提醒）。不存在「用户可见、模型不可见」的消息；Boundary 截断除外。
4. **是否启动模型是独立的轴**：由 core 按 UserInput 内容判定（全是占位 → 只落盘不唤醒），
   不由各渠道各自约定。

## 三、现状盘点

| 场景 | 现状 | 与原则的差距 |
|---|---|---|
| 模型未配置 / 已删除 / 配置有误 | UserInput 已落 + Notification（run.rs） | 符合 |
| 上次执行中断、上次消息未执行 | Notification（recovery / store） | 符合 |
| 微信纯媒体、语音无转写 | 不落 UserInput；通知措辞模糊 | **违背 1、2**，本次触发 |
| 微信文字 + 媒体混发 | 文字落，媒体丢；通知在 UserInput 之后 | 违背 1；通知可能晚于本轮 |
| 入站整条拒收（空、图片超限/格式，`InputError`） | 不落盘，Web 直接回错误 | 用户见到错误、模型不知；需定是否入记录 |
| 模型不支持图片（todo 遗留） | 上游报错呈现 | 应为视图占位 + Notification |
| 微信投递失败 | 只记日志 | 用户没收到、模型以为发了；需定是否入记录 |

## 四、早期候选（历史记录，已选择 Text 打扁）

- **A（推荐）**：`ContentPart` 新增占位变体（媒体类型 + 未处理原因）。
  `model_view` 渲染为带说明的方括号头，Web 显示为占位卡片；core 据此判定是否唤醒。
  代价：改 `mic-message` 公开枚举，需走 B2，各 Provider 与 Web 渲染逐项判兼容。
- **B**：占位写成 Text 片段「[图片]」。改动最小，但伪造了用户文字，Web 与模型都分不清用户真打了这几个字，
  违背边界强类型。不推荐。

## 五、未知项

1. 「模型不支持图片」的占位由谁产生：落盘时不知道将来用哪个模型，应在出请求时按本轮模型能力渲染（Provider 视图层），还是落一条 Notification 就够。
2. `InputError` 整条拒收是否改为「落 UserInput 占位 + Notification」，还是保持拒收（Web 表单内即时报错，本来就不进对话）。
3. 投递失败是否入记录：入则模型知道「上一条没送到」，但会占上下文；不入则维持只记日志。
4. 混合消息中通知与 UserInput 的先后：通知先落才能被本轮看到，但阅读顺序是「系统提示先于用户原话」。

## 六、human 确认结论（2026-10-09）

- 目标是模型所见与用户所见大致一致，保留影响理解的事实，同时尽量省 token。
- 分开长期的对话记录/系统解释与临时的微信媒体打扁适配；对应功能实现后逐项删除临时适配。
- 不新增片段类型，选择 Text 短占位；占位说明用户发了什么，双方同文的 Notification 说明系统处置。
- 能处理的内容不额外解释；每条入站只合并一条差异解释，类型去重；纯占位不启动执行。
- 微信在打扁前保留强类型媒体事实，按能力选择普通/held 入站；core 不通过识别占位文本猜执行策略。早期「core 按内容判定」不再沿用。
- held 输入可能进入当前 run 的后续调用，不等于禁止模型读取。通知用「仅作记录」，避免声称永远不会交给模型。
- 并发契约尚未收敛：保留输入与解释同事务写入方案，但 Pending 输入与通知的窗口过滤不同，仍可能只见解释不见原话。要求两者同时进入模型窗口；明确关联与原子认领/读取两个候选退回 B1 比较，不能断言必须引入关联，也不能仅合并 absorb 与读窗口就认定所有场景解决。实体、场景、不变量与候选见 B2 §五；此项收敛并批准完整 B2 前不实施。
