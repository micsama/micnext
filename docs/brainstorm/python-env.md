# B1：命令里的 Python 用哪个环境

状态：待 human 定（2026-10-30）。

## 现状

- `bash` 命令直接继承服务进程的环境，`python` 是 PATH 上找到的那个。
  - 本机开发时恰好是 `~/.venvs/base`。
  - 服务器上由服务管理器启动，通常只有系统 python。
- 模型缺包时只能自己试：`pip install --user`、`--break-system-packages`、临时建 venv、`uv run --with`……每个会话都可能重来一遍，命令越写越长。
- skill 里的脚本写的是 `python foo.py`，跑在哪个解释器上取决于部署机器，同一个 skill 换台机器就可能缺包。

## 方向

给命令一个确定的 Python：模型不用猜，skill 脚本在哪台机器上都跑在同一类环境里。告诉模型的是事实，不加禁止条款。

## 候选

- **A 框架管一个固定 venv**：`<data_dir>/python`，启动时不存在就用 `uv venv` 建好。所有 `bash` 命令（前后台、子 agent）都把它的 `bin` 放在 PATH 最前面，并设 `VIRTUAL_ENV`。系统提示写明「`python` 是共享的 uv venv，缺包用 `uv pip install`，装了一直在」。
  - 好处：`python`、`pip` 和 skill 脚本默认都走它；包装一次，所有会话都能用；和数据目录一起备份或迁移。
  - 坏处：所有会话共用一份，可能装出版本冲突（单人 agent 可以接受，坏了删掉目录重建）；部署机器要先装 uv。
- **B 不建 venv，只告诉模型用 `uv run --with 包 python …`**：框架不改，只改 `bash` 的说明或系统提示。
  - 好处：零状态，依赖每次现解，不会互相冲突。
  - 坏处：每条命令都要带依赖，命令更长；skill 里写死的 `python foo.py` 照样走系统 python，问题只解决了一半。
- **C 每个 skill 自带依赖声明**：skill 目录里放 `pyproject.toml`，或者脚本里写 PEP 723 内联依赖，用 `uv run` 执行。
  - 好处：依赖跟着 skill 走，最干净。
  - 坏处：要改造现有 skill；模型临时写的脚本仍然没着落。可以和 A 叠加，不能替代 A。

倾向 A；skill 自己需要隔离依赖时再按 C 写，两者不冲突。

## 不做

- 不按会话分 venv：会话很多，重复装包没有收益。
- 不在设置页管理包列表：模型和用户都能直接 `uv pip install`，页面上不再维护一份副本。

## 待 human 定

1. 选 A、B 还是 C（或 A + C）。
2. 选 A 时，部署机器没装 uv 怎么办：启动失败并用中文提示先装 uv（倾向），还是只让这项不生效并对用户提示。
3. 选 A 时，设置页要不要能看到或重建这个环境（倾向不做，删目录重启即可）。
