## 结论

现有 crate 分层、业务事实与框架日志分开、SQLite 作为运行事实来源的方向适合当前个人项目。没有证据需要推倒存储、增加更多 crate 或引入通用工作流框架。

高收益的局部重构集中在几处：工具调用批次的提交与收尾、文件操作的取消与提交、投递终态的唯一归属，以及调用统计的统一口径。这些地方已出现行为错误，适合在整理模型和所有权时一起解决，避免逐出口加特判。

过度防御和额外复杂度也有具体删减空间：为了确认“已处理”而解码整份发送计划、恢复不会重放的批次时重新做业务解析、只写不读的任务关系字段、核心层绕通用工具入口复制文件快照等。每项需要先明确当前真实消费者；减少代码应同时减少约定和状态同步。

## 过度防御与额外复杂度

| 主题 | 当前额外负担 | 更小的整理方向 | 范围 |
|---|---|---|---|
| 微信已处理判断 | stored 只用于确认存在，却解码全文 plan、逐段校验、解释四个最终动作相同的 outcome | 按消费者查询存在事实；实际引用段文字的路径继续正确解码 | 私有局部整理；与投递终态方案一起核对 |
| 入站中断批次 | recovery 完整解码、业务解析 snapshot，结果不用且不重放 | 明确保留现场究竟需要哪些事实，删除无消费者的重新解析和敏感副本 | 改完整快照契约需 B2 |
| 投递双终态 | 模块 outcome 与 core 送达/失败分别提交，迁移、恢复和运行路径各自同步 | 明确一个权威终态，保留微信实际需要的计划和尝试事实 | B1 选择方案，再 B2 |
| 调用统计 | run/session/dashboard/Web 各自定义未知、失败、缓存完整性 | 基于现有调用事实统一聚合语义，删重复规则，无需新统计表 | 公共语义调整需 B2 |
| 工具结果身份 | 上游字符串 id 同时承担 wire 关联、Web 关联、job 去重/恢复 | 明确真实发生范围和内部身份，协议 id 保持自身职责 | 跨层 B2 |
| 压缩文件快照 | core 通过工具名和 JSON 参数读文件，拼展示文本，再猜完整性 | 选择确需冻结内容还是只需文件路径；删除无用途复制和字符串约定 | B1 取舍，再 B2 |
| 任务冗余关系 | core_jobs.report_message_id 只写不读，创建调用关系重复携带 | 核对诊断读者后删除冗余列/投影，保留真正的来源和交付关联 | schema/公开类型 B2 |
| 无消费者存储 API | bind_identity、set_pwd、sessions_with_unclaimed_input 当前代码和测试均零调用 | 删除死入口及其查询/事务，不为保留入口增加新消费者 | 小型公开 API B2 |
| 无生产者 File 变体 | 正常入站只有 Text/Image，File 却要求多层解码、展示或拒绝 | 先确认实际历史数据，再删除变体和跨层分支或做一次性迁移 | 持久化/消息 B2，不能直接删历史数据 |
| 无实际取值的装配维度 | 六个 Module 全为 Always，仍保留 WhenConfigured、缺省方法和每个覆盖 | 若无仓库外扩展消费者，按已传入模块安装，删除单一取值的维度 | Module/Assembly B2 |
| 会话来源与能力 | channel 字符串混合 Root 来源和 Triggered 模块，再跨层推导能力 | 明确来源、种类和操作语义，由 Gateway 做清楚投影，避免加更多布尔标记 | HTTP B2 |
| Gateway 可选装配和独立 GET 默认模型 | 当前唯一装配总提供 restart sender；独立 GET 无仓库内读者 | 随相邻修改缩小构造和接口表面 | 低优先级 B2，不宜单独发动重构 |

这些候选的目标是删掉状态、约定、解析和无用路径。没有建议为了“优雅”新增通用仓储、协议引擎、状态机框架或前端查询框架。

## 已有设计应保留

- Reply 模型与统计从调用事实 JOIN 还原，FireOutcome 从触发、run、push 关系推导；这体现了底层事实足够、上层自然组合。
- 图片和 HTTP/协议数据的入站解码、会话归属检查有实际边界职责；归档和权限会变化，不能按“内部互信”删掉操作时检查。
- 条件终态更新和事务用于当前确实存在的停止/完成竞争；多一个运行态不自动等于冗余事实。
- Provider 的 Chat/Responses 各自处理协议，共用传输；目前没有建立通用协议框架的收益证据。
- 简单时间函数、少量文本格式化的重复，可以比跨层公共依赖更便宜。

已排除 Trigger 无 person 导致后台失败、删除标题模型后不能导出等候选：前者路径被现行工具策略阻断，后者符合已批准约束。已批准的追问竞态、微信发送次数及不保证恰好一次等选择不重新包装为代码缺陷。

## 建议实施顺序

1. **先处理能直接定位的行为错误**：图片引用与附件写入。按完整内容类型和文件所有权整理局部结构，同时删除不必要分支；验收图片后引用、x.part 后接收 x、失败/取消清理。
2. **按根因分组整理执行与投递**：工具调用批次与压缩时机、工具内部身份及恢复关系、文件取消提交归属、投递唯一终态分别列清 B2；每组包含它能删除的同步和特判，避免把所有生命周期塞进一个大重构。
3. **统一统计并清理实际冗余**：先修 S1/S2 的公共语义，再随相邻模块整理 R5 重复校验、无读者字段、装配和 API 表面。快照内容是否必要先做 B1 取舍。

本报告是方向候选，尚未进入这些实现阶段。`todo.md` 沿用只索引未关闭 B2 的约定；本轮不把候选批量加入待办，也不修改已有蓝图状态。
