# B1：存储执行与并发使用

状态：方向讨论，未批准实施。2026-10-28。

来源：[加载故障与深入审查](../reviews/web-loading-2026-10-28/README.md)。目标是让会话交互、agent 提交、Channel 与历史查看能并存，并为多个客户端同时操作建立可验证的资源边界。当前没有生产容量测量，本文不承诺任意用户数下都稳定。

更新：已分析 human 提供的真实备份。库约 16 MiB，37 个会话，其中定时会话 25 集中 17,730 次模型调用；不是用户手动聊了近万轮。在副本上真实查询能重现 settings 等待重读的现象。完整数据、计时与边界见审查文档的“真实库核验”。这将近期优先级收敛到反查索引、轻量 usage 投影和有界执行隔离；暂不优先做全库换型或大范围缓存。

## 1. 哪些设计保留，哪些需要推翻

保留单进程、SQLite、业务事实共用、日志独立存储、事务内关联写入、提交后发布事件。当前瓶颈不能证明必须改 PostgreSQL、微服务或另建一份 Trace 数据库。

推翻“单 writer 所以所有读写单连接”的推导。SQLite 的 WAL 支持 reader 与 writer 并行；当前 `schema.rs` 已开启 WAL，应用的全局连接锁却把这个能力屏蔽了。reader 仍与 writer 共享 CPU、I/O，隔离连接不等于无限容量。[SQLite WAL](https://sqlite.org/wal.html)

修订“任何结果都从全部原始消息即时推导”的成本假设。事实只有一份不等于每次列表都扫描正文。现有消费者需要的关系和执行结果可以作为权威窄字段保存；可重建的索引/投影可以派生，但不能由两套规则分别维护。

不再把 `async fn` 当成已具备背压和取消的保证。当前每次调用都先创建 blocking 任务再等同一互斥锁；线程池有运行时上限，但没有存储操作级的有界准入。增加线程不会使一个连接更并行。[Tokio spawn_blocking](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)

## 2. 候选比较

| 方向 | 解决什么 | 留下什么/成本 | 判断 |
|---|---|---|---|
| 仅补索引、继续全串行 | 解决已知反查退化，改动小 | 下一个搜索/备份/重统计仍可堵住所有业务 | 必做修复，不能作为完整方向 |
| 主连接 + 一个独立重读连接 | 隔离 Trace/搜索对写入的排队 | 重读之间排队，轻读仍可能被主连接维护任务堵住 | 可作为最小落地阶段 |
| 一个写入执行者 + 有界轻读与重读容量 | 事务写串行，交互读取与历史分析隔离，可明确过载 | 需要只读路由、snapshot、取消、关闭契约 | 推荐目标 |
| 所有请求进一个通用读写连接池 | 降低部分串行等待 | reader 被重查询占满、多 writer 竞争、写事务和取消更难管理 | 不建议机械替换 |
| SQLite 分模块/分 Trace 库 | 物理隔离部分 I/O | 跨库原子性、同步、恢复和重复事实成本 | 当前不建议 |
| PostgreSQL + 多实例执行 | 多机访问、更高写并发、成熟运维能力 | 部署、迁移、调度租约、工具环境、认证均要重设 | 达到明确产品/容量触发条件再立项 |

推荐按第 3 项设计，但实现规模保持小：一个写入执行者；至少分别给轻量业务读取和历史重读保留容量，先各 1 个文件库只读连接作为实验起点。连接数不是最终配置值，要按小内存服务器测出；诊断专用只读连接保留自己的授权和期限。不开每个会话/每个用户一个连接。

执行者可先用“异步取得容量 → 一次阻塞操作”实现，也可采用专用线程拥有连接和有界队列。前者改动小，但仍要跟踪 blocking 任务结束；后者连接所有权、队列和关停更清楚，但需要队列调度。推荐先比较二者代码与生命周期复杂度，不为了 actor 形式增加 crate 或 trait。

只加 Semaphore 也不完整：它可能限制正在执行的任务，却让无限等待的 HTTP future 留在内存。容量必须覆盖排队等待，设置等待期限或立即拒绝策略，并把过载显式返回。不能绕过限制另行 spawn，不能偷偷掉到主连接执行。

## 3. 存储操作按成本与语义分路

| 类别 | 当前消费者 | 推荐执行方式 |
|---|---|---|
| 提交/读改写事务 | 追加输入、claim、记录调用和回复、finish、Channel 状态更新 | 单写执行者；事务内读和写保持同一连接 |
| 有界业务读取 | settings、模型配置、会话元信息、最近消息、Channel 状态 | 轻读容量；先使结果和扫描有合理界限 |
| 重读取 | Trace 时间线、用量、peers、搜索、看板 | 重读容量；可取消、有期限、不能阻塞写者的应用锁 |
| 运维 | 数据转换、整库备份、开发者写 SQL | 明确维护窗口或独立受控流程；不假装普通短请求 |

不根据 SQL 是否以 SELECT 开头自动路由。`claim_next` 中的 SELECT 属于写事务；读改写拆成两个连接会破坏原子性。`with_module_tx` 当前混合微信纯读和写，应提供明确的模块只读入口，并把既有调用方分类迁移；模块仍只访问自己的表，装配和 crate 方向不变。

文件库 reader 使用只读打开方式；每个连接初始化自己的 busy 策略等参数。写入连接保留 foreign_keys。连接复用不能残留前一个任务的 progress handler、事务或取消状态。普通 `:memory:` 库不通过文件路径共享，测试要么使用临时文件覆盖真实多连接路径，要么明确单连接测试模式，不能让测试意外读到几个不同的空库。

## 4. 一致性：拆连接时必须重新写清的契约

当前 `Store::call` 内的多条查询，因为业务操作全串行，隐含得到“不被其他业务写入穿插”的效果。拆 reader 后，这个隐含条件消失：例如 Trace 先选 run，再查调用、消息、总数；`session_usage` 先算自身，再遍历后代。需要同一份事实的组合读取要放在短只读事务中，并在返回前结束事务。[SQLite isolation](https://sqlite.org/isolation.html)

写入成功回复后，新开始的读取必须能看到该提交。不要让池化 reader 把上一次事务带到下一次请求。页面不同组件可以分时更新，但不要把旧缓存与新事实拼成声称同一时点的统计。

分页不跨浏览器交互时间持有数据库 snapshot。用游标表达边界；run 可被原地接续，所以“已结束 run 永远不变”不成立。列表与 run 缓存要在执行/接续/结束后失效。消息正文通常稳定，但 `delivered_at` 会变化；当前单价、系统提示也可变，不能把整个 Message、TraceCall、系统提示永久按 id 缓存。

WAL 长读会阻止 checkpoint 完全回收旧页，因此不能让连接/事务贯穿 SSE 生命周期或等待客户端下一页。先读取有界数据、结束读事务，再发送。观测 WAL 增长与 checkpoint 延迟，不为性能擅改持久化保证或强制每请求 checkpoint。[SQLite WAL 长读限制](https://sqlite.org/wal.html#avoiding_excessively_large_wal_files)

## 5. 取消、提交、过载与关闭

| 操作状态 | 应有语义 |
|---|---|
| 只读请求尚在队列中 | 页面离开/期限到即移除，不继续占用工作容量 |
| 只读查询已执行 | 请求级取消或期限通过 progress handler 等终止 SQL；Rust 解码/聚合循环也要合作检查 |
| 写请求尚未接受 | 可明确拒绝，不能返回成功；调用者知道没有提交 |
| 写请求已由执行者接受 | 交给明确的服务端拥有者执行至提交或回滚，连接断开不造成无人负责的半段流程 |
| 写入结果未知 | 不自动重放；若产品要支持安全重试，再定义持久化请求标识/去重契约 |
| 服务停止 | 先停止准入，取消排队读取和重读，跟踪已经接受的写入与事件交接；明确排空期限与重启处理 |

HTTP timeout 只终止等待者，不等价于取消已经开始的 `spawn_blocking`。当前没有连接级查询取消的普通业务入口，需要把取消一路传给真正执行的任务，而不是只加外层 timeout。[Tokio 取消说明](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)

`progress_handler` 作用于一个连接，不能终止 Rust 自己的 JSON 处理；`interrupt` 也作用于连接上正在执行的操作。取消 token、连接租用与任务生命周期必须绑定，旧请求的迟到取消不能打断下一个请求。SQL 执行期限与 SQLite busy 等待、blocking 排队分别计量。[SQLite progress handler](https://sqlite.org/c3ref/progress_handler.html)、[SQLite interrupt](https://sqlite.org/c3ref/interrupt.html)

不能把所有容量拒绝/查询超时都包装成现有致命 `StoreError`：当前 scheduler/title runtime 将存储错误向 assembly 传播并触发整体关闭。浏览器重读超时应终止这次请求；核心写入失败如何终止由 B2 明确，不能因为页面过载把 agent 或整个进程一起停掉。

## 6. 提交与事件不能被连接池改坏

`Events::publisher` 保证消息提交与发布顺序，SSE 依赖消息 id 游标回放去重。这是有实际消费者的约束，不能直接删除全局发布锁。

先缩短临界区：`subscribe_from_now` 改查最后一个可回放消息 id；将能够安全提前获取的路由信息放到锁外，不在持锁期间扫历史、做网络或读大文件。关联写入仍在事务内完成。只在确认全局顺序不再需要并更新所有消费者后，才讨论按会话排序；当前不建议先改成分片锁。

更深的生命周期风险要单独验证：当前发布锁由 async 调用方持有，而写入在 blocking 闭包中。若 async 调用方被取消，blocking 写入可能继续，原调用方却已无法发布事件。当前顺序保证依赖该流程没有在这个窗口被取消。需要用受控阻塞测试复现，不把它写成已观察到的数据丢失。

目标是让“提交 → 按序发布 → 唤醒消费者”有服务端拥有者，HTTP 只等结果。若通过命令执行者管理，仍由 core 持有业务事件语义，store 返回提交结果，不让 mic-store 依赖 core。当前稳定消息可回放且有重启恢复，尚无必要引入通用 outbox 表；要改变交付保证时再评估。

## 7. 数据布局和查询职责

### 7.1 调用详情与用量聚合拆开

`session_usage`、`schedule_usage`、`dashboard` 复用 `load_calls/CALL_SELECT`，读取消息反查、重试分组、时间字符串等聚合不需要的字段。保留一份费用/未知用量计算规则，查询只取用途、模型、用量、时间和当前价格所需字段；优先轻量投影，是否 SQL 聚合根据收益决定，避免在 SQL 与 Rust 复制计价规则。

不要提前保存不可失效的累计美元费用：当前契约按“当前单价”估算，改价会改变历史展示。若后续按天/模型做可重建汇总，应保存足够的用量事实和未知计数，再按当前单价计算；缓存要按模型价格变化失效。

看板当前日期过滤对每行调用 `strftime`。在确定本地时区/夏令时口径后，把日期窗口先转换成时间戳边界，用原始时间列做范围筛选，日期函数只用于分组。是否增加时间索引由真实范围选择性和 EXPLAIN 决定，不盲目为每个字段建索引。

### 7.2 列表、摘要、正文的读取边界

Trace 的 20 个完整 run 不约束总消息数或总字节。建议把 run 概览列表、选中 run 的时间线、单条内容/调用输入分开，并给重型详情分页或显式展开。深链接直接定位目标 run，避免从最新页逐页扫到目标。“到顶”不应靠下载全部中间历史才到达；接口契约在 B2 中定义。

会话列表最近活跃排序从消息逐会话推导。若测得这是下一瓶颈，可以维护窄的会话读取投影：最新消息 id/对应活动时间、最新需要计未读的消息 id、首条输入预览来源等，按实际查询逐项选择。现有 act 是最大消息 id 对应的 created_at，不等同于 `max(created_at)`；消息存在回填时序，不能偷换排序规则。投影在消息写入事务内由唯一入口更新，可独立重建；已读水位与投递事实仍各自保留，不冗余存一堆相互矛盾的布尔值。

工具名称、调用引用、结果类别、开始/结束时间已有统计和时间线消费者，可以评估从 JSON 移为权威窄字段/子表，正文只存内容。读取时还原领域类型，类比当前 Reply 的 model/stats 已从调用表还原。若仅使用表达式索引/生成列就足够，优先它们；别同时保留可独立修改的 JSON 元数据和列。JSON 在 SQL 内截取预览仍可能解析长正文，不应把“没传全文”误认成“没读全文”。

正文与元数据纵向分表是更后一步候选：降低元数据扫描的页面体积，但增加写事务和 JOIN；大文件已经有独立交付路径，暂不把所有消息内容改成外部 blob 系统。

### 7.3 搜索与全库统计

搜索未命中也会扫全库。先隔离和限时、避免收集所有命中全文；之后讨论可索引检索。FTS5 不应悄悄替换当前任意子串、多词同时匹配语义；尤其中文一两个字查询，trigram 的全文匹配有最小长度限制。可选“保持语义但分批扫描”或“明确改搜索契约并用索引”，由 human 决定。[FTS5 trigram](https://sqlite.org/fts5.html#the_trigram_tokenizer)

`trace_sessions` 整库树和 `call_peers` 全历史精确中位数即便有索引仍随历史增长。可以根会话分页、子树按需，peers 延迟显示；若缩短时间窗/抽样改变统计口径，必须可见并批准。缓存只可带明确的失效/刷新规则，不能把陈旧统计伪装成实时值。

## 8. 多模块与多客户端的放大链

全局事件总线同时承载 token 增量、完整稳定消息和列表变化。每个 SSE 与 Channel 订阅者收到后才过滤自己的 session/channel；`KernelEvent` 的 Clone 包含 Message 和 String。多会话、多订阅者下会产生无关唤醒与消息复制，繁忙会话还可能挤掉其他订阅者的事件，随后重连回放增加查询。

建议先区分轻量变化通知与会话数据流；稳定大消息用共享所有权减少重复拷贝，按 session 路由草稿流是否值得做由并发实验决定。保留提交后发布、订阅早于回放、去重、lag 后重连语义。不建设通用消息中间件。

前端收到 `session_activity` 后丢掉具体 id，整轮刷新标签、置顶和全部渠道及已加载页。多个客户端会按客户端数重复做同一批查询。先按变化域和 session id 收窄失效、合并在途请求；页面切换取消旧 GET；重连做一次明确补齐，不能靠持续全量重拉。

`scheduler.rs` 只有同会话互斥，没有全局活跃会话上限；title 使用 unbounded channel 且跨会话启动任务；一轮工具调用也是并行启动。读写分离可能暴露之前被数据库阻塞掩盖的模型/工具并发。需要按实际资源设容量：模型请求、工具进程、重读、入站等待分别控制，不套一个大 Semaphore。

特别注意父 agent 等子任务：若父任务一直占着唯一执行额度、子任务也要求额度，会形成资源等待死锁。模型调用额度在等待工具/子 agent 时释放；若限制整会话执行，必须明确父子任务调度规则。忙时排队、拒绝或延后启动的用户体验需 B2 决定，不能悄悄不执行工具。

## 9. “多用户”需要分两种产品

当前默认按共享个人实例、多客户端和多个 agent 并发来设计上述改进。真正的独立账户/租户是另一项公开契约，尚待 human 明确。

当前 Gateway 一个 Bearer 即全实例权限；`Kernel::owner` 固定身份，Web 写入使用它；settings 单行；session 无租户归属，seen 水位在 session 上；全局流、Trace、文件与开发者 SQL 均按单实例信任设计。表里有 person 不等于已有租户隔离。

| 目标 | 合适路径 |
|---|---|
| 同一用户多设备、可信多人共用 | 本文读写隔离、事件刷新、容量控制；共享已读/设置是产品选择 |
| 几个互不信任用户，各自 agent 与文件 | 优先评估每人独立进程、数据库、数据目录、凭据和工具执行环境；共享入口负责路由认证 |
| 共享服务里的独立账户或协作空间 | 定义用户与 workspace/会话归属、ACL、每用户已读、配置作用域、配额；所有查询、文件、流票据与事件按身份过滤；开发者权限单独划分 |

独立实例隔离也不能省略宿主机总资源限制。共享进程的多租户不只是加 user_id 或换数据库：工具读写的目录与 OS 权限、凭据、后台任务、全局通知都必须随身份隔离。没有这一契约之前，不把当前个人实例作为互不信任多人服务部署。

## 10. 分阶段推进与决定点

1. **已知查询修复**：反查索引、轻量聚合投影、最后消息 id 查询；补可定位的请求/存储时间分段。服务器复测，形成基线。
2. **执行边界 B2**：读写类别、连接所有权、有界准入、查询期限/取消、短 snapshot、失败范围、提交与事件交接、关停。推荐本轮核心重构优先做这一阶段。
3. **读取契约 B2**：run 摘要/时间线/内容分层，树分页和直达 run；搜索语义；会话列表投影。按阶段 2 后的测量决定先后，避免一次改完整 schema。
4. **并发调度与事件 B2**：模型/工具容量、父子 agent 规则、事件路由、客户端失效范围。
5. **多账户决定**：确认是共享个人实例还是租户产品，再选隔离实例或共享账户模型。若单 writer 在短事务、查询隔离后仍持续饱和，或必须多机同时写，再讨论 PostgreSQL；不要用随意的用户数阈值替代测量。

验收必须包含单条查询成本和交互可用性：人工延长重读时，settings 与消息提交仍能完成；过载有明确结果；取消后 CPU/队列能回落；同一会话不会双 claim；回复/调用关系、分页和事件游标不丢不重；长读期间 WAL 和内存受控。具体性能目标用目标服务器基线制定，不以“任何机器任何规模都小于 1 秒”作为承诺。

## 11. 真实库揭示的另一条边界：自动化生命周期

定时会话 25 的规则是每分钟一次，在约六天中产生 8,854 次实际触发、17,730 次模型调用。成功任务也会持续消耗资源，已有“连续失败暂停”和单 run 轮次/墙钟限制都不限制它几天、几周的累计执行次数。改善查询速度不能替代这个治理问题。

该会话记录的输入约 9.39 亿 token，其中约 99.59% 为缓存读取；不能据此按全部输入的普通单价算账。备份缺可用价格，真实账单未知。它最后因 missed 触发记录被自动暂停，这说明一次资源拥塞还会改变自动化的业务结果，不只是让页面变慢。

候选需要由 human 选择，不能暗中改变现有任务：

| 能力 | 行为与权衡 |
|---|---|
| 创建/修改时显示频率与预计次数 | 每分钟明确显示约 1,440 次/天；模型调用数和费用只能按已有样本估算，标明不确定性 |
| 到期时间或最大执行次数 | 能在触发事务内确定是否还允许新的执行，达到后明确停用并通知；不会依赖未知的上游 token 统计 |
| 每任务/每天的用量预算 | 输入、缓存、输出分别显示；用量在调用结束后才返回，单次可能跨越预算，必须明确检查点与最大超出范围 |
| 费用预算 | 当前价格未知时不能按零放行并称为限额；当前估价也不等于供应商账单，严格金额上限需要相应上游保证 |
| 确定性检查 + 条件触发模型 | 对只需检查固定条件的任务可减少模型调用；这是能力和执行方式变更，须确认具体任务可这样执行 |

执行次数和用量以已有 fire/call 事实为依据；若需要高效累计投影，在同一事实提交点维护且能核对重建。配额检查和“登记一次新触发”必须原子，不能多个调度者各看一眼余额再一起放行。停止新触发与取消已经执行的 run 是不同动作，需分别说明，不能因为用户调整预算自动重放或丢弃已有副作用。

反查索引和短查询先修；执行隔离与自动化生命周期分别形成 B2，可独立批准和验收。多用户时再决定预算属于实例、workspace、用户还是任务，不提前叠加所有层级。

## 12. 长会话应按访问职责划边界

human 明确：限频和提前压缩是策略，根本方向要解决长期增长的存储与上下文访问。当前已有压缩边界，不另造一套通用 memory 系统；应把这些边界落实到 SQL、页面读取和模型工作集。

| 现有概念 | 保留的职责 | 成本边界 |
|---|---|---|
| session | 长期身份、关联、用户可见入口 | 不要求生命周期内全部消息一次读取 |
| run/call/message 事实 | 执行、结果、回看、Trace 重建 | 按 run/id 范围按需查；run 可接续，不能当永远不可变分区 |
| 有效 Boundary/keep_from 与必要引用 | 当前模型工作上下文 | 范围读取加引用补入，旧历史增长不应增加无关扫描 |
| 当前任务规则和跨轮有效状态 | 下一次执行真正需要知道的内容 | 规则有既有权威来源；已推送事实等优先查询已有记录，不靠无限增长的对话回忆 |
| 历史统计 | 全期用量、费用、错误等 | 专门窄投影；达到实测瓶颈再做可重建汇总，不混入模型工作窗口 |

真实长会话当前窗口 1,530 条，现有查询约 970,000 VM 指令；分解范围与保留引用、增加位置索引后约 137,000 指令，结果一致。说明语义上已分段，查询路径尚未充分利用。详细 SQL 实验与局限见审查文档。

“将来历史一百万条，读取本轮仍只需当前窗口及必要引用”是更合适的验收目标。近似成本可为索引定位 O(log N) 加工作集 K；不承诺数据库变大后一切时间绝对不变。当前窗口本身也要有合理 token/字节预算，既有模型容量比例只保证不撑满模型，不等于经济的工作集大小。必要内容超预算时必须有明确整理/失败行为，不能 SQL LIMIT 静默漏掉用户输入或工具配对。

任务每轮可用“任务规则 + 当前有效状态/摘要 + 本轮输入和工具结果”组织工作集，历史作为按需回查。不是机械每轮新建会话，也不是每次强制压缩；具体哪些状态必须跨轮保留、如何更正和验证，需要根据任务契约选择。已推送记录等结构化事实已有消费者和来源，优先复用；不为通用记忆提前增加任意键值表。

物理布局上优先保留一个 SQLite：范围/部分索引、生成列与窄投影、WAL 读写隔离、必要时同库元数据/正文纵向分表。压缩边界可撤销且有跨边界引用，不作为直接搬走历史的物理分区键。跨库或 DuckDB 主存储暂不采用；多年离线分析确有需求时再评估可重建分析副本。官方特性依据、实际索引体积与取舍已集中写入审查文档。
