# B1：压缩后 skill 怎么接上

状态：已定方案 B（2026-10-30），见 [B2](../blueprints/skills-after-compaction.md)。来源：[skills B2](../blueprints/skills.md)、[cold-trim B2](../blueprints/cold-trim.md)。

## 现状

- **目录**：skill 目录一直在 system prompt 里，压缩不影响。
- **压缩段里的正文**：会被总结掉。总结提示里没有提 skill，模型可能把正文要点复述进摘要（稀释、占篇幅），也可能漏掉「当前任务正在用某个 skill」。
- **保留段里的正文**：换成占位「Skill X was loaded here… Load it again if needed」，名字还在。
- **用户点名**：带回的用户原话里只剩 `[skill：name]`；模型通过工具加载的，压缩后除摘要外不留痕迹。

所以压缩后能不能接着按 skill 做，取决于模型自己有没有发现需要重新加载。

## 方向

参照现有的 `<required_files>`：

1. **总结提示**：skill 正文不写进摘要，只记用了哪个 skill 做了什么；末尾可选一个 `<required_skills>` 块，只列当前未完成任务依赖的 skill，没有就丢弃，拿不准也丢弃。
2. **压缩后怎么用这份清单**，下面三选一。

## 候选

- **A 只提示**：上下文里加一行「压缩前在用的 skill：x、y，继续前先用 `skill` 工具加载」。
  - 好处：零自动成本，不需要的就不加载。
  - 坏处：多一步工具调用，而且靠模型听话，和现在差别不大。
- **B 自动加载**：压缩提交时，core 读出清单里各 skill 的加载结果，作为边界后的一条消息存下来，形式和 `/name` 点名一样。
  - 好处：压缩后第一次请求就带着正文，不依赖模型；存下来的就是模型当时看到的内容，前缀稳定，之后照常可被整理成占位。
  - 坏处：清单列错了会白占上下文；skill 读取失败时要像点名那样附一条通知。
- **C 自动加载，但有上限**：同 B，只是总正文超过阈值时，超出的部分退回 A 的提示。

倾向 B。模型列进清单本身就是一次「接下来要用」的判断，再让它调一次工具是重复；skill 正文通常不大，误列的成本有限。等真遇到大 skill 再考虑 C。

## 不做

- 不按关键词或正则自动推荐 skill（skills B2 已经搁置）。
- 冷时整理（Trim）不调用模型，不产生清单。占位里已经保留了名字，维持现状。
