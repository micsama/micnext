# B1：Web 闭环后的最小正交审查

**状态：C、D、E 的已证实部分已落地（2026-10-08）；A 并入模型设置运行期化 B2；B、F 待定。**

落地结论：
- C 选 C1：所有发 `MessageAppended` 的写入在内核互斥，发布顺序即提交顺序（run-execution §3.1）。
- D 选 D1（按 run）：core 算收尾消息，`Store::interrupt_run` 单事务写入并转终态（run-execution §4.6）。
- E 只做详情一处：`GET /api/sessions/{id}` 返回 `SessionItem` + `writable`（gateway §4.2）；
  Root 键重复、Task 父关系、`session_channel` 语义仍按下文待定。
- 另修：SSE 发送响应停止并限定优雅关闭时长；前端入站逐字段解码（web-ui §4.1）。
范围：以 `5dcc65d` 为基线，承接最近四个提交的 review；寻找类似存储重整的职责与建模收益。
不替换已批准 Blueprint，不新增实现。方向确定后按主题起 B2，不把本稿当成整体重写授权。

## 一、判断标准与排序

最小正交不是类型、trait 或 crate 越多越好：独立变化的语义分开，共同变化的保持在一起。
每次调整必须指出现有摩擦、最终消费者、可以删除的约定，以及复杂度去了哪里。

| 候选 | 判断 | 当前证据 | 建议时机 |
|---|---|---|---|
| A 启动装配与模型实例创建 | accept：既有职责混杂 | install 后通过 provider 数量反推模块类别；模型配置误写已有待办 | 和模型设置运行期化合为一份 B2 |
| B 历史事实与模型上下文呈现 | accept：既有职责分散 | L0 拥有提示文案/时区；core 与 provider 重复生成模型视图 | 最适合独立的小步正交化 |
| C 稳定事实与实时显示 | accept：既有发布顺序与本次 Gateway 契约冲突 | commit 与 emit 分离，SSE 却承诺按消息 id 升序 | 正确性优先，先收敛交接协议 |
| D 终态提交与崩溃补齐 | accept：既有事务边界缺口 | 先改 interrupted，再分事务补结果；恢复再中断无法续补 | 与 C 协调写入边界，独立确定恢复契约 |
| E 会话身份、列表投影与来源关系 | accept：详情依赖分页缓存、创建键重复；全面拆分 needs-investigation | 深链缺元数据；Root 参数重复；Task 父关系靠约定 | 先解决已出现的两处摩擦，来源全面拆分随真实生产者 |
| F 工具参数对象与非法原文 | accept：既有跨层隐式编码，收益较小 | Value::String 被三处用作非法参数原文哨兵 | 下次相关协议调整时一起评估 |

以上 accept 只确认问题有证据，不代表批准某个候选方案。

## 二、候选与复杂度去向

### A. Module 登记实现能力，模型条目描述一次可配置的使用

现状：`mic-core/src/assembly.rs:139` 先 install，再比较 `providers.len()` 判断是否误配模型模块；
`parse_models` 用所有模块名校验模型 kind。`ModuleConfig` 对普通模块是一个配置段，对模型模块
却是多个条目的映射。`Assembly` 最后只保留默认 Provider；当前 run 始终用这个实例。

这里混合了两个生命周期：启动时安装 Service/工具/迁移，以及按用户模型条目创建 Provider。
`storage-and-models.md` §二已确定模型设置运行期化，更新模型不能重跑包含 Service/迁移的整次 install。

候选：

- A1：保留目前的 Module 入口，显式声明配置类别，消除靠 install 结果猜类别。改动小，但运行期实例创建仍需另定。
- A2：Module 只登记 Provider 创建能力；模型条目由一个明确的解析/创建入口交给对应实现。
  普通 Module/Registry 保留，工厂仍可作为模块贡献，不建立平行的插件系统。

倾向 A2 随运行期模型设置一起做。能删除装配时模型条目的特殊分组/探测，复杂度转移到唯一的
条目解析与实例创建边界。最终消费者是 run 的模型选择与 Web 模型管理，不是为了泛化注册表。
具体配置形状仍由懂协议的 Provider 解析，不能让 core 接管服务商字段。

待定：模型编辑何时影响 run（现有 B1 是 run 开始时选取，执行期间是否固定快照须明确）；
条目身份、请求模型名、推理兼容身份是否需要不同表示。当前只用模型名比较，不足以证明跨服务商同名兼容，
但现在只有固定 Provider，不把未来多模型场景当成已发生的故障。

### B. 历史事实、模型输入、供应商 wire 各归其主

现状：`mic-message/src/model_view.rs` 格式化框架头、失败文本、本地时间并决定 role；
`mic-core/src/request.rs` 拼 system、调整工具结果与插话顺序，还在第 71 行为了判断 user role
构造一次完整 model_view；`mic-provider-openai/src/request.rs:22` 随后再构造它。

“这条消息发生过什么”与“这次给模型看什么、怎样表达”是独立变化轴。
修改框架提示策略不应迫使 L0 历史类型拥有更多呈现规则。

候选：

- B1：仅把共享呈现函数移到 core，Provider 仍收历史 Message。移动少，但 Provider 仍需理解历史变体。
- B2：core 在已有 request 职责内完成上下文选择、排序与框架呈现，产出独立的模型输入；
  Provider 只做协议映射、能力检查及供应商特有推理回传。无需新增 crate 或可插拔提示词框架。

倾向 B2。最终消费者是所有 Provider；可移除 Message 上的 model_view 呈现方法与重复转换，
提示文案/时区集中归 core。复杂度是一个明确的输入类型与一次转换，不是删除业务规则。
不能把 OpenAI 的全部 role/内容限制误当成通用模型输入，也不能为假想协议设计巨大联合类型。

待定：工具调用与结果相邻是统一上下文约束还是协议适配约束；模型输入需要保留哪些来源元数据，
才能继续支持推理兼容判断。迁移应逐字段比较当前请求 JSON，不能仅靠编译证明行为等价。

### C. 稳定消息的完整性与草稿的低延迟分别建模

现状：`KernelEventKind` 同时传稳定消息、草稿增量和 run 状态。
同一枚举本身不是问题；问题是 consumers 对三者使用了不同可靠性假设，而生产侧没有保证。
`kernel.rs:136` commit 后还要 await 查会话再 emit，worker 可先发布更大的消息 id；
Gateway 回放后直接转发事件，Web 又用最后一条消息 id 作为重连游标。

候选：

- C1：core 对同一会话所有稳定写入及发布提供明确的串行边界，Gateway 继续消费有序消息事件。
  保留直接推送，代价是所有写者必须经过这个边界，不能只给某一个 append 加锁。
- C2：稳定事件仅负责唤醒读取；Gateway 从库按游标读取有序事实，实时增量仍直接流送。
  减少对跨任务 emit 顺序的依赖，代价是查询/合并唤醒，以及更明确的草稿与落盘交接规则。

暂不选。两者都不需要持久化所有 token、引入消息中间件或完整事件溯源。
复杂度分别落在写入发布协调处或订阅读出协调处，不能推给每个前端做去重补洞。
任何新封装的消费者必须是现有 Kernel 入站、run 写者与 Gateway；Store 不反向依赖 core 事件类型。

待定：C2 下读库可能先见到 Reply、后见到其缓存增量，如何可靠结束该草稿；
是否需要调用尝试身份，应由交接场景证明，不能先添加无人消费的 id。
若采用带 ack 的内部命令通道，命令处理器不得等待发给自身通道的 ack。

### D. “run 已收尾”应有单一可验证含义

现状：`recovery.rs:16` 先把全部 executing 标成 interrupted，再读取各 run，逐次补 ToolResult/Notification。
这使“终态”与“恢复完成”脱钩，且库中没有可再次选择的未完成恢复标记。

候选：

- D1：每个 run 的补结果、通知与终态同事务提交；core 计算领域恢复计划，store 原子应用，
  或由 store 专用操作完成计算。两种所有权需要比较，不为此暴露任意核心表事务。
- D2：恢复可重入，有明确可查询的未完成判据，重复执行不会补重复结果/通知。
  能拆开事务，但必须承担判据、幂等和中间状态复杂度。

倾向优先评估 D1。单进程启动期间没有 worker，是天然的简化条件；事务粒度按每个 run
还是全部 run 的选择仍未批准。复杂度回到一次领域操作的事务边界，不建立通用 saga。
正确性要求是重启后结果完整；隐私不新增输出；失败留下可恢复状态；审计保留 unknown-side-effects 通知，
绝不能靠重跑工具来“补齐”。

### E. 当前会话不从列表推断，创建身份不重复传入

当前已出现的摩擦：

- Web `ChatView.svelte:12` 从分页缓存查当前会话，列表未加载即失去渠道/工作目录并误显示发送框。
  会话详情的消费者是打开的聊天页，列表只是浏览投影。
- `Store::resolve_root_session(channel, chat, NewSession)` 的查找键和 NewSession.kind.Root 内的键重复。
  现有调用方必须自行维持相等；可以用一次明确构造消掉约定，不需要运行时重复检查。
- `SessionKind::Task` 的父工具调用与通用 `parent_session_id: Option` 分开，Kernel 的 expect 声称
  store 保证父会话必有，但 store 构造/SQL 并未保证非空；目前尚无 Task 生产者。
- `session_channel` 给 Root 返回渠道、Task 返回祖先渠道、Triggered 返回模块名，同一个字符串有不同语义。

候选：

- E1：只收紧已有构造和读取边界：Root 身份只给一次；详情独立按 id 读取，或随流接入返回。
  API 与 SSE 二选一，不引入重复维护的第二份元数据。Task 父关系未来进入对应构造。
- E2：把来源、父子关系、出站目标、事件过滤标签全部作为独立轴重新建模。
  表达能力更强，也会增加允许组合及合法性规则；Task/Triggered 尚无真实生产者，当前证据不足。

倾向 E1；E2 留待 cron/子 agent/微信具体场景。不要先给每个 session 加一堆可空字段，
也不要把前端可写性硬编码成内核事实：授权策略归 Gateway，返回值可由当前来源和策略计算。

### F. 工具参数的对象与非法原文不靠 JSON 类型暗示

`provider-openai/src/response.rs:147` 把无效 JSON 或非对象参数包装成 `Value::String(raw)`；
`request.rs:82` 遇到 String 又直接当原文回传；`mic-tool/src/handle.rs:69` 用 is_object 区分可执行参数。
这是一条跨三层的隐式协议，不是普通字符串参数。

候选为保留现有约定，或用小类型显式表达“对象参数 / 非法原文”。后者能消除 String 哨兵约定，
消费者仍是工具入参解析与 Provider 历史回传；复杂度是把已有两种状态放进类型，不新增验证框架。
对象内部的动态 JSON 仍应保留，具体 Args 的 schema 属于 Tool，不能把工具规则推给 Provider。
该调整会触及磁盘 payload 与 Web wire，需单列兼容判断；收益小于 B/C，不宜为它单独发动全库重写。

## 三、实体、写者与状态（用于检查候选，不是新 schema）

| 实体 | 写者/所有者 | 状态与变化 |
|---|---|---|
| 已编译模块贡献 | Assembly + Module.install | 未安装 → 已登记 → 随进程退出；运行期模型编辑不得重装 Service |
| 模型条目与选定实例 | 当前配置/装配；将来模型管理入口待 B2 | 条目校验 → 可选实例 → 被 run 选取；编辑影响范围待定 |
| Session 身份/关系 | Kernel 创建入口，Store 持久化 | 不存在 → 创建；列表投影加载与否不改变身份 |
| Message | 入站 Kernel、run 引擎、启动恢复经 Store 写入 | 未提交 → 已提交；输入的 run_id 认领另有既定约束 |
| Run | scheduler 认领；Engine 完成；recovery 中断收尾 | 未认领 → executing → completed/provider_failed/max_turns/interrupted |
| Model call | run 引擎，Store 记录 | 调用中 → 成功记录（可有 Reply）或失败记录；当前仅结束时落盘 |
| 草稿 | Provider 产增量，core 转发，客户端归约 | 空 → 增量中 → Reply 替代 / discarded；断线可丢，不充当稳定游标 |
| 订阅与游标 | Gateway feed / 前端 SessionView | 订阅 → 回放 → 实时 → 断开 → 按稳定游标重连；停止从等待点均可结束 |
| 模型输入投影 | core request 构造，Provider 消费 | 历史快照 → 选择/排序/呈现 → wire；不回写历史、不建立第二份事实库 |

上述状态箭头是各实体的概念状态图；“调用中”“草稿”等内存状态不意味着需要新增数据库状态。
恢复操作目标为：`遗留 executing → [补结果 + 通知 + interrupted]`，括号内原子还是可重入待 D 收敛。

## 四、两个必须走通的时序

### 场景 1：插话与模型完成并发，期间浏览器断线

```text
入站任务       Store            run worker       Gateway         浏览器
写输入 M11 ──> commit
等待调度                         写 Reply M12 ──> commit
                                emit M12 ──────> 转发 M12 ────> 游标12
                                                               断线
emit M11 ──────────────────────────────────────>（旧流已断）
                                                               after=12 重连
```

现状可漏 M11。C1 须保证提交/发布次序；C2 须保证以 12 为游标前已读出包括 11 的稳定前缀。
之后还要验证回放已含 Reply 时，迟到的同次调用增量不会重新打开重复草稿。

### 场景 2：启动恢复期间再次停止

```text
启动恢复        Store                          下一次启动
现状改终态 ───> commit interrupted
补部分结果 ───> commit
进程停止                                       扫 executing → 选不中 → 遗留悬空调用

D1 候选：准备补齐计划 → 原子提交结果/通知/终态
提交前停止：仍可恢复；提交后停止：完整闭合。
D2 候选：分步写入，但下一次启动仍能识别未完成恢复并幂等补齐。
```

## 五、必须成立的不变量与验收证据

1. 稳定游标代表该会话已呈现的完整消息前缀，不只是“见过的最大 id”；增量可丢不影响最终历史。
2. 同一调用尝试的草稿恰以稳定 Reply 或 discarded 收口；快照与缓存交接不重复打开旧草稿。
3. run 终态时工具调用配对完整；恢复再中断也不会失去补齐机会，不重新执行未知副作用。
4. 模型编辑不重复安装模块；在运行的 run 使用何种配置有明确口径，不混用新旧凭据/参数。
5. 模型输入呈现只有一个框架策略来源；Provider 仍拥有协议规则，历史原始事实保持不变。
6. 会话身份不随分页缓存改变；创建查找键与写入键无须调用方重复维护。
7. 所有候选保持 crate 依赖方向；新增类型/签名/模块进入 B2，完成迁移后不长期保留双轨。

验收应针对上述不变量：可控并发与断线、恢复提交前后停止、深链刷新、模型更新期间的请求口径，
以及投影重构前后的请求 JSON 对比。正常 DeepSeek 对话与 fmt/clippy 无法单独证明这些性质。

## 六、不建议现在做的调整

- reject：把 Engine 的每个步骤拆成 trait/插件。当前循环直接表达调用、重试、工具、落盘，尚无独立替换消费者。
- reject：为“正交”统一所有事件为 action 字符串/Value，或持久化所有流式 token；削弱类型或增加事实来源。
- reject：把 Scheduler Running/Dirty 当成数据库 RunState 的重复而删除。前者表达唤醒是否待处理，后者表达执行事实。
- reject：拆更多 crate、改框架、上完整 CQRS/事件溯源/通用工作流。没有本轮实际摩擦支持。
- reject：为极简删掉工具类型擦除。ToolHandle 的消费者是异构工具集合，保留 Args/schema 同源与领域侧解析有直接收益。
- needs-investigation：异步 Completion/Dispatched、投递字段的未来契约。已有路线图用途，不因当前没生产者就顺手删；随对应 B1 核实生命周期。

建议先讨论 B（边界最清楚）与 C（正确性最迫切），A 并入已有模型设置 B2，D 单列恢复事务契约，E 只做已证实的最小范围。
