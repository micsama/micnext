## 确认缺陷

### E1 · P1：自动压缩失败或被停止，会留下永远没有结果的工具调用

触发：对话模型回复包含工具调用，且本次用量达到自动压缩阈值；工具启动前的压缩请求失败、摘要解析失败，或用户在压缩期间停止。

证据链：

- `run.rs:411` 的 `call_model` 已通过 `persist_reply` 把带 ToolCall 的 Reply 提交；`run.rs:415` 先压缩，`run.rs:419` 才进入 `run_tools`。压缩失败在 416 行直接返回，因此没有启动工具，也没有为这些调用写取消结果。
- `compaction.rs:185`、`:257`、`:282` 分别返回停止、摘要错误和上游错误。
- `run.rs:285` → `mic-store/src/scheduling.rs:206` 的 `finish_run` 只更新 run 终态、可选交付，不补齐悬空调用。
- `recovery.rs:21` 只恢复 Executing run；已经 ProviderFailed / Stopped 的 run 重启后也不会补齐。
- `request.rs:270` 的重排只移动消息，不生成缺少的结果。后续上下文继续带着没有结果的 ToolCall。

影响：一次压缩故障留下持久化的未闭合执行事实；后续请求继续回传该调用，无法靠重启恢复正常闭合。对于工具调用与结果须配对的 Provider，这还会使后续对话请求被拒绝。具体上游报错未联网复现，不以某一服务商的报错文案作为结论。

此外，在压缩输入未被预算裁剪掉的情况下，压缩请求本身也带着尚未返回结果的 ToolCall，再追加压缩指令；Chat/Responses 序列化逐条映射，没有替它补结果。这是相同阶段划分问题的另一表现。

核实：临时副本的 `audit_reproduces_unclosed_calls_after_compaction_failure` 已通过，断言了压缩请求中存在未闭合调用、失败后没有 ToolResult、落终态后恢复处理数为 0、后续窗口仍未补齐。现有 `compaction_right_after_tool_call_keeps_the_call_for_its_result` 只覆盖压缩成功路径，未覆盖此出口。

改进方向：让“已接受的模型工具调用批次”有完整收尾路径，压缩失败也必须明确结束未启动调用；同时明确压缩输入如何处理尚未执行的一步。优先整理这一阶段边界，避免仅为一个错误出口另加特判。调整压缩时机/保留语义须 B2；单纯补齐未启动调用的取消结果可作为缺陷修复评估。

### E2 · P2：文件写入已排队时取消，停止返回后仍会真正修改文件

触发：`write` / `edit` 已提交到 blocking 池但尚未执行，或已经开始较慢 I/O；用户停止 run。工具 future 被取消后，阻塞闭包继续执行。

证据链：

- `mic-tool/src/tool.rs:30` 明确要求丢弃 future 时释放资源，不留下后台副作用。
- `mic-tool-fs/src/common.rs:50` 使用 `spawn_blocking`，drop 只置取消标志，未取消排队任务或等待实际收尾。
- `write.rs:31`、`edit.rs:52` 的闭包忽略取消标志，最终仍在 `write.rs:42` / `edit.rs:82` 执行原子替换。
- `run.rs` 的 `run_tools` 中止并等待的是外层异步任务，不是内部 blocking 工作；随后可落取消结果并结束 run。

影响：用户看到停止后，文件仍可能变化；下一轮读写可能与上轮残留写入交错。原子 rename 只保证单次替换，不建立取消与提交的先后关系。

核实：临时副本使用 `max_blocking_threads(1)`，先占住阻塞线程，再派出 `Write.execute`，取消并确认外层 JoinHandle 已结束，此时文件不存在；释放线程后文件被创建。`audit_reproduces_cancelled_write_committing_later` 已通过。这不是仅推测 syscall 正在执行时的极短竞态。

改进方向：先明确文件操作的提交/取消契约。至少取消尚未开始的写入；已进入不可取消提交阶段的操作应有实际收尾拥有者，并在停止完成前等待收尾，或明确告知结果尚未确定。只在 rename 前读一次 AtomicBool 不能消除检查与提交之间的竞态。修改通用工具取消契约须 B2，不应给所有工具堆一套无消费者的回滚机制。

### E3 · P2：后台任务落终态失败后被移出运行表，数据库仍显示运行中

触发：后台任务已经退出/超时/停止，`finish_job` 因数据库错误未提交。

证据链：`jobs.rs:276` 只记录 `finish` 错误，接着在 `:279` 无条件移出 `running`、在 `:280` 标记 done；数据库仍保持 Running。之后 `stop_tool` 在 `:537` 找不到运行项，返回 AlreadyFinished；列表按数据库在 `views` 中仍显示 Running。只有重启恢复才会再处置它。

影响：同一任务同时表现为“运行中”和“已结束”，没有完成回注，停止接口不能说明真实失败原因。普通 run 的 Store 错误会上抛给 scheduler，后台路径却只留日志。

核实方式：代码调用链确认，未做磁盘满/数据库错误注入。结论限于错误返回后的确定控制流，不声称该故障在当前真实环境已发生。

改进方向：确定后台持久化失败如何上报拥有者，与现有执行主路径保持一致；不要通过无条件清理运行项把“未成功提交终态”转成“已结束”。可用既有服务错误通道上抛；不建议默认引入重试队列、补偿表或第二套任务状态。

## 当前结构摩擦与局部重构候选（不是自动批准的缺陷修复）

### R1：文件快照建立在已格式化工具文本上，增加了跨层约定和重复数据

`compaction.rs:295` 的 `read_snapshots` 按工具名 `read` 找实现，自造 JSON 参数，经过通用工具入口，再从 ContentPart 拼回字符串；还包含 Dispatched 不可达分支和 NoBackground。`read` 原本就会按 2000 行、单行长度和字节数截断，但这里在 `:328` 只根据本层 remaining 推导 Complete / Truncated。事实已丢在展示文本中，核心层只能依靠英文尾注间接解释完整性。

这不是建议再加一层通用文件系统接口。先让 human 选择当前真正需要的能力：

1. 若冻结的文件内容确实是恢复工作必须保留的事实，读取结果应明确提供内容与截断范围，再由工具展示、快照共用；不要解析工具文案，不能让核心层依赖 fs 实现层。
2. 若需要的只是继续工作时知道该看哪些文件，保存路径、下一轮按需 read，可删除整段快照读取、字节预算和冻结文本复制链。

两者都会改变公开行为/数据语义，需要 B1/B2 取舍。收益在于删掉字符串往返、名字约定和完整性猜测，不是为了抽象而加 trait。

### R2：执行结束原因在不同路径里被重新翻译成文案

当前后台超时是 `JobState::TimedOut`，但 `jobs.rs:322` 的 Completion 却是 `ExecOutcome::Completed`，超时只放在 `[timed out ...]` 文本里；子 agent 超时在 `jobs/agent.rs` 中又投影成 Cancelled，前台 shell 则把超时/退出码拼进 Completed 正文。它们是已存在的行为选择，不能直接当作“非零退出就是错误”来修。

代价是上层若要一致展示结束原因，必须回查另一张事实或读文案；每条路径各维护转换分支。可以围绕当前确有消费者的结束原因统一投影规则，让输出内容与结束原因正交。避免复制更多状态字段，也不要求把所有工具自己的业务结论都枚举进核心。涉及 Message/ToolOutcome、存储及前端，须 B2。

### R3：取消的边界需要整理，不能用更多布尔值补齐

当前存在三种合理但分散的所有权：普通工具随 future drop 取消、后台任务登记后归 Jobs、注册和通知在独立 spawn 中确保提交完成。`JobPort::register`、Sink::notify 均有明确消费者；它们不是应直接删除的空抽象。但 E2 说明文件阻塞操作实际形成了第四种“没人等待、又不检查取消”的路径。

局部整理应围绕“何时提交、谁等待实际结束”展开，删掉无法兑现的同名取消假设。无需为所有异步操作增加一套统一协调框架，也不建议扩大本次变更到已接受的追问竞态。

### R4：工具调用的内部身份应带上真实的发生范围

主审查已核实 Web 将外部 tool_call_id 当作全会话唯一键。执行/存储侧还把它用于 `core_jobs` 的 `UNIQUE(origin_run_id, origin_tool_call_id)`（`mic-store/src/schema.rs:245`），恢复在 `recovery.rs:52` 也仅用 run + 外部 id 找旧 job。

如果同一个 run 的不同模型轮次复用 call_0，第二次派出后台任务将碰唯一约束；第二次尚未派出便退出时，恢复查询还可能命中第一轮 job。这两个执行分支未单独构造复现，不列作新增确认缺陷。它说明只修前端 Map 键无法明确系统的调用身份。

建议把外部协议 id 与内部发生位置区分，用已有模型调用/Reply 的身份加调用位置描述一次发生，而不是通过保证外部字符串全局唯一、加遇重重试或文案规则补齐。与 E1 共同审视“调用批次”的归属和收尾，但二者根因不同：E1 是已接受调用缺少终态路径，这里是身份范围缺项。涉及消息、job 起源和恢复关系，需要 B2；不应为审查先行增加一套通用执行 ID 体系。

## 过度防御核对与保留项

- 未把 `ensure_session_active`、`in_subtree`、子 agent owner 检查列作重复防御：归档和权限归属会变化，且模型管理工具确有不同会话消费者。
- `RunControl` 的停止闸门、`JobPort` 的登记结果、输出 Seal 都解决当前实际的并发先后，不能只因状态多就删掉。
- 类型边界检查、内部 `expect/unreachable` 在本范围大多遵循写入路径/外键保证，没有发现值得增加“损坏数据 fallback”的必要性。R1 的不可达 Dispatched 分支应随快照消费方式一起消掉，不值得孤立再包一层类型。
- 少量错误链格式化、时间函数重复无需增加跨层公共依赖；未以此凑去重项。
- 已排除 `archive/async-jobs.md` P2.6 中 human 明确接受的“追问已提交、回执尚未落盘”和“停止与追问交错”窗口，不重新列为待修复缺陷。
- 超时/输出有界、模型重试只在 core、崩溃恢复不重放外部副作用，这些现有方向应保留。没有证据支持新增工业化的队列、快照版本或分布式协调机制。
