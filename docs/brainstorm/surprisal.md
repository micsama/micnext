# B1：阅读重点（意外度高亮）

**状态：试验中（2026-10-27）。** 试验页在 `scripts/surprisal/`，看过效果再决定是否接入消息菜单、是否写 B2。

## 想法

对一段文本做一次前向，取每个位置上实际 token 的概率，意外度 = −log₂ p(token | 前文)。意外度越高，信息量越大，可以当作阅读重点高亮。

## 为什么只能用本地模型

- 意外度要的是给**现成文本**逐 token 打分（prompt logprobs / echo）。OpenAI 早已下线 echo，Anthropic 从未提供。
- ChatGPT 订阅接口和 OpenAI 推理模型不返回 logprobs。DeepSeek 的 `deepseek-chat` 有 `logprobs`，但只覆盖它自己生成的 token；`deepseek-reasoner` 不提供。
- Ollama 的 logprobs 也只覆盖生成部分。
- 让大模型「标出意外的词」只是印象分，不是概率。

## 跑在哪里

服务器只有小内存 CPU，不跑模型。打分放在浏览器里：前端本来就有消息文本，本机加载小模型算完直接着色，服务端不参与，也不新增接口。

- 不采用：服务器回调 Mac 上的服务（Mac 关机即失效，多一条网络链路）；浏览器调本机 mlx 服务（https 页面访问本地网络受限，还要常驻进程）。

## 浏览器里的技术选择

- **模型**：`onnx-community/Qwen3.5-0.8B-ONNX-OPT`，与官方 WebGPU 演示相同，用 `AutoModelForCausalLM` 加载时只取文本部分（`embed_tokens` + `decoder_model_merged`），不加载视觉编码器。
  - q4 词嵌入用的 `GatherBlockQuantized` 只有 WebGPU 实现，WASM 下建 session 报错（`Could not find an implementation for GatherBlockQuantized(1)`）。拆分版的词嵌入是单独文件，WASM 改用 fp16 词嵌入即可。
  - 不用纯文本版 `Qwen3.5-0.8B-Text-ONNX`：词嵌入和主体在同一个文件里，量化词嵌入换不掉。
- **运行时**：transformers.js（ONNX Runtime Web），同一份模型能跑两种后端，且能直接拿到每个位置的全部 logits。
  - 不选 WebLLM：只支持 WebGPU，且为生成设计，不方便取整段 logits。
  - 不选 wllama（llama.cpp 编成 wasm）：只用 CPU，也不方便取整段 logits。
  - 不选 Rust（candle）编 wasm：没有 Qwen3.5 混合线性注意力的实现，浏览器里通常单线程、没有 GPU；打分只在浏览器跑，与服务端 Rust 代码无可共用。

### WebGPU 与 WASM 的分工

| 后端 | 用什么算 | 量化 | 作用 |
|---|---|---|---|
| WebGPU | GPU（macOS 上浏览器转成 Metal） | 全 q4，约 620MB | 主路径，速度快 |
| WASM | 只用 CPU（多线程 + SIMD） | 主体 q4 + 词嵌入 fp16，约 950MB | 兜底：浏览器没有 WebGPU 时用 |

- WASM 是 CPU 上的字节码，本身不能调用 GPU。ONNX Runtime 自身就编成 WASM；选 WebGPU 后端时，控制逻辑仍在 WASM 里，矩阵乘法等重计算交给 GPU。
- WASM 多线程需要页面跨源隔离（COOP + COEP），否则只能单线程。Safari 不支持 `credentialless`，所以用 Chrome。
- 神经网络引擎（ANE）浏览器调不到，只有 CoreML 原生程序能用。
- 确认是否用上 GPU：`chrome://gpu` 中 WebGPU 为 Hardware accelerated，或在活动监视器的 GPU 历史记录里看占用。

## 计算要点

- 文本分段前向，段与段之间接上缓存。整段 logits 一次性放进内存太大：词表约 24.8 万，每个 token 约 1MB。
- 前文必须前向才能进缓存，但不打分的位置不算 logits：每段用 `num_logits_to_keep` 只保留从第一个要打分的位置起的末尾几行。输出层（约 24.8 万词表）占前向的大头，长前文时省得明显。
- Qwen3.5 的位置编码是 3 维 mrope，纯文本时三维相同，由页面按段自行给出。
- 在文本前面加 `<|endoftext|>`，让第一个 token 也有预测；可选的「前文」只作条件，不着色。
- 逐字节 BPE 会把一个汉字拆成多个 token：凑不齐 UTF-8 的 token 并入下一个；再用 `Intl.Segmenter` 聚成词，词的意外度等于其中各 token 之和。

## 已知局限

- 意外度是相对打分模型而言的：小模型没见过的专有名词、代码标识符分数也高，未必是阅读重点。
- 意外度量的是措辞，不是意思：小模型首选「脚本」（64%）、实际写 shell 时记 5 bit，也会算作笃定落空；同义的大小写、空格变体还会分散概率。可选改进：合并写法变体，按词向量相似度给落空打折，未做。
- 第一次使用要下载约 620MB（WebGPU）或 950MB（WASM）模型；没有 WebGPU 的手机基本不可用。

## 着色方式

- 按固定 bit 上限着色几乎满屏都是颜色（2026-10-27 实测，上限拉到 24 bit 仍如此）：小模型对中文每个 token 普遍有好几 bit 的意外度，按词着色时多个 token 还会相加。
- 改为在本段内排名，只标最突出的前 N%，标点与空白不参与排名。
- 排序依据可选：意外度本身，或「笃定落空」：只算小模型首选概率过半、实际却没写首选的 token。曾试过「意外度 − 熵」，高意外度的位置熵远小于意外度，减掉后排名几乎不变，标出的范围与意外度大体重合，故换掉。
- 不算格式：小模型常想先换行、先加粗，这部分概率会把后面的内容词也算成意外。把只含空白与 Markdown 标记的 token 视为格式，剔除格式概率后重新归一：意外度 = −log₂(p / (1 − p格式))；格式 token 本身记 0。
- 按分句着色（默认）：中文标点与换行处断开，英文标点后跟空白才断。分句取平均（分母加 3 压住短句），只给最突出的分句加底色，单个词的近义替换被同句其余词摊薄；未入选分句里猜中的词仍标浅绿，悬停仍看词级候选。
- 首选猜中标绿：小模型 top-1 等于实际 token 的地方是可预测的套话；不算格式时内容 token 比非格式 top-1，格式 token 比总 top-1。标点虽不参与排名，猜中也标绿，免得 `json_output` 两侧的反引号断开。这相当于把小模型当投机解码（speculative decoding）的草稿模型，猜中率就是贪心接受率；它不是 MTP，MTP 是同一个模型一次预测后面多个 token。

## 上下文

- 不给上下文时，大量意外度来自「小模型没看到大模型看过的对话和工具结果」，不是内容本身。补上上下文后，剩下的才是大小模型的能力差距与大模型自身的措辞选择。
- 试验页：`serve.ts` 把消息接口转发到本机 micnext（地址和 token 读本机 `config.toml` 的 `[gateway]`），页面按会话拉取消息，选中的回复之前（最近一次清空或压缩之后）的消息按 Qwen 对话模板拼成前文，工具结果截断，只留最近约 2.4 万字。也可以「分析整个会话」：按清空、压缩切成窗口，每个窗口从头前向一次，只给回复正文打分；每条回复的前文就是它前面的内容，结果与逐条分析一致，前文只算一次。右栏给出总体统计和逐条回复的平均意外度、首选猜中率。
- 接入 micnext 时，前文窗口应复用 core 组装上下文的规则（压缩、预算裁剪、排除项），由服务端给出产生该回复的那次调用的窗口，前端只负责转成小模型的对话模板，不在前端另写一套窗口规则。

## 待验证

- WebGPU 和 WASM 在本机的实际速度。
