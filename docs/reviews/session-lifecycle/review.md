## 结论与处理

- **已修的视图重建回归**：诊断同步读取侧栏状态，将其带入 App 的 `$effect`。`06a3f93` 的 `untrack` 放在生命周期调用边界是合适的；保留，不另建视图管理层。历史输入的排队状态由 `ready.queued` 建立，实时输入增量维护，也保留。
- **取消没有完整结束诊断**：切走时若 `getSession` 尚未返回，原实现要等返回后才结算；后台标签页若停在 `requestAnimationFrame`，心跳定时器和可见性监听也会继续存活。现将诊断结算接到会话取消信号，结算同时取消待执行帧，`tick` 返回后也检查是否已结束。会话信息请求返回后先检查取消，不再赋值或继续建流。没有扩展 HTTP 请求接口；在途信息请求本身仍会完成。
- **context 刷新缺少关闭检查**：成功与失败路径均可能在视图关闭后写入状态。与 title、jobs 保持一致，请求成功后先检查取消，失败后仅在视图仍打开时写入错误。保留三个直接的合并刷新循环，不为简单重复引入回调抽象。
- **事件状态与副作用分散**：`#apply` 在 switch 前后分别组合事件条件，阅读一个事件需要横跨三处。现把刷新、已读上报放回相应事件分支，先归约状态，再执行副作用；回放消息不逐条刷新，`ready` 统一刷新。保留一个 `#live` 表达当前连接是否完成回放，不增加状态类型或通用事件分发层。
- **工具耗时提交遗漏测试调用方**：`toolResults` 从 outcome 改成 `{ outcome, ms }`，现有三项测试仍断言旧结构，`bun test` 失败。更新断言，继续校验重复上游 id 和分页结果归属，并验证正常耗时、无开始时间、后台派发三种情况。

本地存储整理、工具耗时计算、诊断接收端的本次检查未发现需要进一步改结构的具体缺陷。LoadProbe 已单独承载计时与上报，没有依据再拆模块。诊断仍是临时能力，按原蓝图收集证据后整体移除；生命周期隔离、回放规则与取消后的状态保护是常驻实现。
