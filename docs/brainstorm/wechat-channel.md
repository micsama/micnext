# 微信 Channel：B1 方向与待定事项

**状态**：B1 产品行为已收敛（2026-10-08）；B2 Phase 1 CLOSED（2026-10-09，human 功能验收通过）；其余阶段仍为 DRAFT。
**B2 文档**：[`../blueprints/wechat-channel.md`](../blueprints/wechat-channel.md)；下文的早期接口/流程草图由 B2 细化，批准和实现状态按阶段记录。
**协议事实**：[`wechat-protocol.md`](wechat-protocol.md)（取自官方 `openclaw-weixin` 2.4.9）。
**已定**：扫码登录在 Web 设置页，凭据入 SQLite；无流式，每次模型调用出话就发一条；要 typing；
协议未验证点接入后自行实测；一个微信对象持有自己的凭据，对应一个用户、一个会话。

**2026-10-08 human review 收敛**：切换微信相当于切换用户/会话，旧对象保留自己的历史和投递现场，
旧凭据被顶、旧回复发送失败属于正常故障，不迁移到新对象。未来可能同时运行两个 ClawBot 对象；
本版不做双对象管理 UI，但对象的凭据、游标、token、会话和投递必须独立。
自动压缩是统一 core 功能，与微信无关。异常退出后重启待命，保留现场供开发修复，不自动重放旧任务。
断网和发送失败可接受；回复发往微信失败后只重试一次，再失败则跳过并保留失败事实。
Web 登录过程最终提供一个强类型的完整配置结果即可。

**后续确认**：同一微信重新扫码继续原会话。旧任务仅手动恢复；新消息可正常启动新一轮，
沿用已有上下文及故障描述，不由程序自动恢复旧 run。自动压缩与微信接入正交。
本版接文本和服务端语音转写，图片、表情包、视频、文件等媒体接入延期到 V2。

## 一、做什么、不做什么

做（v0b）：

1. Web 设置页扫码绑定微信（含验证码、过期重取、状态显示、重新登录）。
2. 微信文本入站 → 对象自己的会话 → 每次模型调用的文本回复发一条微信消息，失败/中断通知同走此路。
3. run 期间 typing。
4. 持久化收发现场；异常退出后重启待命，不自动重放旧任务或补发积压。

刻意不做（避免过度设计/过度防御）：

| 不做 | 理由 |
|---|---|
| 群聊、双对象管理 UI、白名单管理 | 本版只配置一个对象；未来双对象沿用对象独立的形态，每个对象只认自己的扫码人 |
| 图片、表情包、视频、文件等媒体接入 | 延期到 V2；普通文本 emoji 随文本支持，表情包的协议表示待实测 |
| 入站去重表、投递 ack、发送幂等 | 本版接受失败并保留现场；入站重复与出站回执是独立问题，不以无回执作为不做入站去重的理由 |
| `getconfig` 缓存、typing 刷新退避 | 每个 run 取一次 `typing_ticket`，失败就不发 typing |
| `-14` 之后的 1 小时暂停 | 直接置「需重新登录」，停止轮询，设置页提示 |
| 引用消息存储、silk 转码、`notifystart/stop` | 无已知需求；实测需要再加 |
| Markdown 转换 | 先原样发，实测观感再决定 |
| 微信专属压缩机制 | 自动压缩统一由 core 提供；已有 UserClear 边界，命令入口随统一上下文功能另定 |
| 微信区域的模型/人设选择 | runtime-settings Q7 已定后续再做；微信先用默认设置 |

## 二、形态与依赖

```
mic-channel-wechat ──→ mic-core（Kernel / Module / Service）
mic-gateway        ──→ mic-core
（两者互不依赖；bin/micnext 装配）
```

- **`mic-gateway` 只是 Web 这个 Channel 的适配器**，不是统一中间层；统一层是 `Kernel`。微信与 Web 平级，
  直接调 `Kernel`，不经 Gateway。`mic-store.md` §九、`mic-core-module.md` 中「经 Gateway 入站和发送」的措辞需在 B2 修正。
- 微信模块 = 一个 `Module` + 一个 `Service`（`Activation::Always`：未登录时 Service 空转等待，登录后开始轮询，
  这样不依赖 `config.toml`）。用 cargo feature 控制是否编入二进制，与现有模块一致。
- 状态存模块表（`with_module_tx`，`wechat_` 前缀 + `Migration`）：

| 表 | 内容 | 写者 |
|---|---|---|
| `wechat_account`（按对象归属，键待 B2） | `bot_token`、`ilink_bot_id`、`baseurl`、`ilink_user_id`、状态（正常/需重新登录） | 对象接受登录配置；该对象的收发流程遇 `-14` 改状态 |
| `wechat_state`（按对象归属） | `get_updates_buf`、`context_token` | 该对象的入站流程 |

投递复用 core 的 `delivery_target` / `delivered_at`。一次重试耗尽后如何持久记录跳过，在 B2 定；
现有 `delivered_at` 只表示发送成功，不能把失败跳过伪装成已送达。target 必须标明对象归属；
每个对象只处理自己的投递。旧对象的失败不得阻塞新对象，也不得用新对象的凭据或 token 处理。

## 三、主路径

**入站**（`Service` 内的 `getupdates` 循环）：

```
getupdates(游标) → 对每条消息：
  非本对象扫码人 / 有 group_id → 丢弃（见待定 E）
  无文本 → 按 C 处理
  存本对象的 context_token
  kernel.resolve_root_session("wechat", 本对象的会话标识, 会话参数含对象专属 delivery_target)
  kernel.append_user_input(session, 本对象 person, [文本])
```

B2 提案先保存完整批次现场和新游标，再逐条导入；异常重启不重放旧批次。
这替代早期“消息先写、游标最后写”的草图，明确允许崩溃窗口中部分输入未导入，但现场保留供手动恢复。
旧未认领输入由统一 core 启动处置为 held；接口、错误和兼容迁移见 B2，不承诺既不重复也不丢失。

**出站**（同一 `Service` 内订阅 `Kernel` 事件）：

```
RunStarted(本对象会话)     → getconfig 取 ticket → sendtyping(1)
MessageAppended(本对象)    → drain：只取本对象 pending，按 id 依次
                              文本非空 → 分段 sendmessage → mark_delivered
                              文本为空 → 直接 mark_delivered
                              发送失败 → 只重试一次 → 再失败则记录跳过，继续下一条
RunFinished              → sendtyping(2)
```

一条 `Reply` 即一次模型调用的产出，其文本非空就发一条微信消息，天然满足「每次调用出话就发」。
`Notification`（失败/中断提示）同一路径。发送失败只重试一次，再失败则跳过，不 `mark_delivered`；
记录两次尝试与最终失败事实，继续后续投递，不等下一次交互反复重试，也不做重启自动补发。

**登录**（Web 触发）：取二维码 → 轮询状态（含 `scaned_but_redirect` 切换域名、`need_verifycode` 等用户输入）
→ 最终得到强类型的完整配置结果，交给对应对象保存并启动收发；中间态留在登录流程。

**token 失效**：B2 提案中 sendmessage 的 `-14` 先完成当前一次重试预算，再停止本对象收发；
其他认证请求的 `-14` 立即置「需重新登录」并停止本对象收发，保留现场与历史。
设置页重新扫码得到配置；同一用户更新凭据并继续原会话，不自动补发旧积压；
换用户则切换到该用户的独立对象/会话，不迁移旧对象的现场。

## 四、需要 human 决定的事项

### A. Gateway 如何触发微信登录（公开契约，走 B2）

设置页要二维码、状态、验证码输入、重新登录，但 Gateway 不能依赖微信模块。候选：

- **A1（倾向）**：`mic-core` 定义一个薄 port（暂名 `ChannelLink`：`status` / `start_login` / `poll_login` / `submit_code` / `logout`，
  返回强类型的二维码与状态枚举）；微信模块通过 `Registry` 登记，Gateway 经 `Kernel` 取到并转成 HTTP。
  依赖方向干净；port 只有微信一个实现，是否「抽象有进有出」需 review 确认——消费者是 Gateway，生产者是微信，成立。
- A2：登录整个流程由微信模块在后台自驱，把二维码/状态写进它的模块表，Gateway 只读通用的「Channel 状态」表。
  需要 core 定义状态表契约，且验证码回传仍要一条写通道，复杂度不低于 A1。
- A3：`bin/micnext` 把微信句柄直接注入 Gateway。要 Gateway 认识一个具体类型，违反「模块互不依赖」。

**human 已定边界**：Web 登录最终交付统一的强类型配置结果，微信收发对象消费它；
扫码、验证码、重定向等中间态属于登录流程。A1 仍是候选，不因此批准通用 Channel 管理协议。
A3 若注入共享 port 的 trait 对象则不违反依赖约束；port 所在层与句柄传递方式分别判断。

### B. 投递接口缺口（公开契约，走 B2）

`Store` 已有 `pending_deliveries` / `mark_delivered`，但 `Kernel` 没有对应委托，微信模块拿不到。
需在 `Kernel` 新增这两个方法（与 `messages_after` 等同类的薄委托）。是否同意？
另：`Lagged` 后查询本对象 pending 可恢复落盘消息；typing 是可丢实时状态，不能靠 drain 恢复。

### C. 本版入站支持哪些内容（方向已定）

本版只接文本和服务端语音转写 `voice_item.text`。普通文本 emoji 随文本支持。
图片、表情包、视频、文件等媒体接入延期到 V2；表情包的协议表示接入后实测，不凭空新增 wire 类型。
沿用草案行为：无语音转写或不支持的媒体回一条提示，提示的落盘与投递契约在 B2 明确。

### D. 上下文增长（方向已定）

统一自动压缩由 core 提供，覆盖 Web、微信等全部入口，不在微信模块做专属截断或压缩。
当前 `context_window` 无自动截断；已有 `ContextBoundary::UserClear` 及读取语义。
自动压缩的触发、执行协调和失败行为另起 B1/B2，微信接入不在这里决定其契约。

### E. 无法处理的入站消息怎么办

扫码人以外、群消息：直接丢弃，不回复（避免骚扰，也不用白名单配置）。
扫码人发了不支持的内容：见 C。请确认「丢弃」不需要日志之外的任何提示。

### F. 入站重复的容忍度

**human 已定**：异常退出后重启待命，保留现场等开发修复，不自动继续或重放旧任务；本版不建入站去重表。
旧任务手动恢复。收到新消息时可自动启动新一轮，带已有上下文和故障描述；这不等于程序恢复旧 run。
现有 recovery 会落盘中断通知与悬空工具的取消/结果未知描述，模型视图会呈现这些内容，继续复用。

**现行 core 契约（B2 Phase 1，2026-10-09）**：`recovery` 将遗留 Executing 收尾为 Interrupted，不重跑；
随后将遗留未认领输入登记为 held，不自动调度，上下文保留。新指令启动新 run，不恢复旧 run。
微信批次先落现场与新游标、重启不重导的契约见 B2 §五，留到入站阶段实现。
统一恢复行为不在微信模块绕行实现。

### G. 发送失败与顺序

**human 已定**：这里的发送失败指回复发往微信失败。首次失败只重试一次，再失败则忽略该条投递，
保留历史和失败事实，继续后续投递；不要求最终送达，不以无限重试阻塞队列。
顺序只在同一对象内讨论，旧对象的失败不阻塞新对象。
B2 需定义有限重试及最终跳过的持久记账，包含分段文本的尝试单位；不得用 delivered_at 表示失败跳过。

### H. 配置面

倾向 `config.toml` 不放任何微信项（启用靠编译 feature + SQLite 里有无账号）。
`baseurl` 以登录返回为准，不让用户填。请确认没有必须写进 `config.toml` 的启动项。

### I. 账号更换

**human 已定**：一个微信对象对应一个用户、一个会话。同一用户重新扫码更新凭据，继续原会话。
换用户切换到独立的用户/会话对象，旧对象保留自己的现场，
旧凭据失效或旧回复发不出去均可接受，不迁移历史、上下文或投递。以后可能同时启动两个 ClawBot 对象。
对象身份、凭据更新与会话标识的确切关系在 B2 明确；不直接把会变化的 token 字符串当对象身份。

### J. 实体与协调（B1 草图）

| 实体 | 写者 | 状态变化 |
|---|---|---|
| 登录尝试 | 登录流程 | 待扫码 → 待验证码/继续扫码 → 完整配置结果；过期或失败可重试 |
| 微信对象的账号与收发状态 | 本对象的运行流程；接受登录结果时串行交接 | 无配置 → 收发中 → 凭据失效/故障待命 |
| 会话、run、消息 | core | 既有执行路径；异常启动将 Executing 收尾为 Interrupted、遗留未认领输入登记为 held |
| 投递记录 | 本对象发送流程 | 待发送 → 成功；首次失败 → 一次重试 → 成功/失败跳过；历史和失败事实保留 |

关键场景：

1. 换号：Web 登录 → 完整配置结果 → 新对象及其会话 → 新对象独立收发；旧对象的请求结果仍只写旧对象。
2. 批次中崩溃（B2 提案）：对象先保存批次现场与新游标 → 写入部分输入 → 进程退出 → 启动收尾 → 待命保留现场；
   不重新导入旧批次，旧未认领输入不自动调度。新消息 → 携带历史和故障描述 → 新一轮执行。

不变量：凭据、游标、context_token 与投递均归属确定的对象；对象间不串状态、不共用阻塞队列；
异常重启不自动重放旧任务；失败事实与已成功发送事实分开保留；自动压缩只由 core 提供。

## 五、实现顺序（B2 通过后）

分阶段范围、批准状态与人工验收以 [B2 §十一](../blueprints/wechat-channel.md#十一实施顺序与人工验收) 为唯一索引：
统一启动待命 → 共享 Kernel 能力 → Web 扫码登录 → 微信入站 → 微信回复投递 → typing 与整体验收。
代码完成后由 human 人工验收和矫正，通过后更新文档、继续下一阶段；当前 Phase 1 CLOSED。
协议不确定项先读本地参考 SDK，不足以定论交 human 搜索或实测，AI 不自行联网搜索。

## 六、风险

- 协议未公开文档，字段与行为只来自一个插件版本的源码；`iLink-App-Id` 的取值与合规性需 human 判断（protocol §八-3）。
- 无送达回执：补发可能重复，丢失无感知。已按「先记录失败，观察后再加机制」接受。
