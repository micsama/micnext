# B1：模型出站脱敏、工具隔离与授权

**状态：已记录、明确延期（2026-10-10）。human 接受只减少部分意外披露，不要求全部检出。候选未批准，不实现；恢复时按够用原则重新收敛。**

## 一、起因与现状

- 用户提出：进 LLM 前自动处理密钥、身份证等敏感内容，可开关，模型可申请权限，并与 bwrap 配合。
- 2026-10-09 服务器实测：模型以 root 经 bash 读到数据库与主密钥目录。专用用户部署由 human 进行中；Ubuntu 24.04 下已加 `/etc/apparmor.d/bwrap` 放行，并以 micnext 用户验证隔离可用（仅环境验证，应用内未实施）。
- 出站内容不只有用户输入：人设、偏好、摘要、工具结果、历史正文与工具参数都会发给模型，只处理 Channel 入站会漏。
- bash 继承完整环境，fs 工具只拼接路径、无访问范围；提示词里的 OFF_LIMITS 不是执行边界，系统提示还写着「Full OS permissions, no sandbox」，实施隔离时要同步改。

## 二、三个独立轴

| 轴 | 管什么 | 落在哪里 |
|---|---|---|
| 工具访问 | 路径读写、进程环境、网络 | bash / fs / web 工具执行侧 |
| 模型披露 | 发给服务商的内容 | 所有模型请求的同一出口，换 Provider 不能绕过 |
| 人工授权 | 某次受限操作的一次例外 | 前两者各自消费授权结果 |

三者分开：允许执行不等于允许披露；关脱敏不等于关沙盒。不做一个「安全模式」开关统管，不给模型全局解除限制的工具。

## 三、候选

| 候选 | 判断 |
|---|---|
| A：部署隔离 + 本地规则脱敏 + Web 全局设置 | 推荐首期 |
| B：A 上加操作绑定的一次授权，Web 审批 | human 确认确有需要后另起 B2 |
| C：可逆占位符，本地工具代入真实秘密 | 暂不选 |
| D：本地 NER/OCR 或另一个模型识别 | 暂不选；禁止把原文发给另一个云模型「查隐私」 |

## 四、A 的要点

- 设置存 SQLite、经 Web 改，用枚举（规则脱敏 / 原文发送）而非 bool。
- 每次调用前处理出站副本，不改原消息；按结构遍历内容字段，不正则替换整个序列化请求；协议 ID、角色不变。
- 首批规则：应用已知秘密精确匹配、可识别的 API token / PEM 私钥、带密码连接串、身份证（格式 + 日期 + 校验位）。占位符按类型，如 `[已隐藏：API 密钥]`，不还原。
- 检测出错或遇到不支持的结构即拒发，不静默发原文。只承诺已定义的规则。
- 图片不在文本脱敏范围内，是否阻止上传待 human 定。
- 本地历史、日志、备份仍存原文，不在本项范围；Web 显示脱敏类别与数量。

## 五、隔离要点

- 出站脱敏管不住 bash 的 curl 和 web 工具，直接外传靠隔离。
- bash：专用用户 + bwrap，只挂允许目录，私有 tmp，隔离 PID/proc，环境白名单，不暴露数据目录、主密钥、控制 socket；bwrap 不可用时启动报错，不回退裸 bash。
- 禁止访问的路径清单由启动侧下发一份（key_file 不一定在 data_dir），bash 与 fs 各自落实。fs 需覆盖 read/write/edit/glob/grep 及符号链接、路径遍历；方案（目录句柄 vs 隔离子进程）待定。
- micnext 自身控制文件始终禁止工具访问，不提供审批解除入口。
- 网络：运维助手需要广网络，受限工作区可默认断网；域名白名单需另评估代理。

## 六、待 human 决定

1. 首期是否选 A，暂不做审批？
2. 定位是受约束的运维助手，还是以工作目录为边界？网络范围随之定。
3. 规则模式下图片：阻止上传，还是接受仅文本保护？
4. 默认识别是否只限密钥与身份证，手机号、邮箱按需开启？
