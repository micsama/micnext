# B1: 定时任务

状态：方向已定（human 2026-10-20），进 B2。§五 的健康手段先按此实现，用下来再调。前情：[产品路线](product-roadmap.md) §四、[早期核对](cross-check-2026-09-23.md) §三-4～6、[Trace 原型](../../tmp/trace-preview/index.html) 的 `TASKS` 示例（聊天侧无任务列表原型）。

## 一、已定（human 2026-10-20）

- 一次运行**不必有结果**：没发现就安静结束；有发现可能写文件、可能推送。运行本身只留记录。
- 每次运行的记录在**定时任务列表**里可看，能点进去看过程。
- 对外只有一个出口：**`push` 工具**，agent 明确要告诉用户时才调用。任何会话都能用（例：让主会话跑个长任务，完了微信提醒我）。
- **推送发给人**：按 person 的 Channel 投递（微信私聊、Web 通知中心、以后的 IM 私聊），见 §四。落到会话里的形态是现有 `Notification`：系统发给用户、不唤醒 bot，但留在上下文里供之后追问。
- 运行之间共享上下文：每个任务一个会话，加边界与运行间压缩保持健康，见 §五。
- **定时任务属于 person，不属于会话**：在哪个会话都能建、查、改；会话归档与任务无关。
- 系统级失败（没能启动、模型调用失败、中断、错过）必须被框架捕捉、记录并通知，不依赖 agent。
- 工具少、正交，细节靠参数。定时任务与后台任务是两回事，不共用工具。

## 二、概念

| 概念 | 是什么 | 落在哪 |
|---|---|---|
| 定时任务 | 归属 person：名字、时间规则、指令、启停 | `core_schedules`（见 B2） |
| 任务会话 | 每个任务一个 `Triggered` 会话（`ref_id` = 任务 id），运行共享上下文 | 现有会话 |
| 运行 | 到点往任务会话追加一条触发输入，跑一轮 | 现有 run / trace；运行列表即该会话的 run 列表 |
| 推送 | person 级：`push` 发给人，按 Channel 投递 | 一条推送记录 + 各 Channel 的投递 |

## 三、工具（3 个）

| 工具 | 谁有 | 参数 | 说明 |
|---|---|---|---|
| `schedule` | Root 会话 | `id?`、`name?`、`when?`、`prompt?`、`enabled?`、`delete?` | 省略 `id` = 新建（`name`/`when`/`prompt` 必填）；带 `id` = 只改给出的字段；`enabled: false` 暂停；`delete: true` 删除。返回下次运行时间 |
| `schedules` | Root 会话 | `id?` | 省略 = 列出全部任务（规则、下次运行、最近一次结局）；带 `id` = 该任务的运行记录与每次的最终回复摘要 |
| `push` | 所有会话 | `text`、`via?` | 推给用户本人，见 §四 |

`when` 一个参数同时接 cron 表达式（`0 9 * * *`）与一次性时刻（`2026-10-21 09:00`），一次性的跑完自动停用。指令在每次到点时读取，改了下次生效。

## 四、推送（person 级）

推送发给**人**，不发给某个会话。`via` 是 Channel 列表，可同时发多个（如微信 + Web）；省略用 person 的默认推送 Channel（Web 设置里多选，存 SQLite；未设时有微信用微信，否则 Web）。一次推送一条记录，各 Channel 分别记投递结局。

| Channel | 投递 | 回看与追问 |
|---|---|---|
| 微信 | 该 person 的私聊（即其微信 Root 会话），以 `Notification` 写入并走现有投递 | 在微信里直接回，主 agent 上下文里有这条通知 |
| Web | 右上角通知入口，新推送加红点；每条显示来源（哪个任务 / 哪个会话）、时间、正文 | 每条带【去会话里问】：跳到来源会话，输入框带上引用前缀（复用聊天页的回复机制）。来源会话自己调用过 `push`，上下文里有这件事，可直接接着问 |
| 以后的 IM | `via` 该 IM 即默认私聊该用户；群聊另议 | — |

- 每次推送存一条记录（person、via、正文、来源会话、时间、投递结局），Web 通知中心与任务列表的「已推送 / 投递失败」都读它。
- Web 现在没有登录，单用户即 owner；加登录后按 person 区分，不改模型。
- 通知中心列出全部推送作为记录，只有发往 Web 的计未读。
- Web 没有统一的私聊会话，所以推送不写进任何 Web 会话；能回答追问的是**来源会话**，Web 侧的追问一律回到那里，不另造「Web 收件会话」。

## 五、任务会话保持健康

任务会话会无限增长，靠「边界 + 运行间压缩」控制，全部是构建期常量（`limits.rs`），不做成任务参数。

| 手段 | 做法 |
|---|---|
| 运行间提前压缩 | 每次到点、追加触发输入**之前**检查上下文：超过任务专用阈值（低于普通会话的设置值，如 50%）就先压缩再跑。压缩落在两次运行之间，不打断运行 |
| 压缩保留 | 沿用 [compaction-retention](compaction-retention.md)；任务会话的摘要要求保留：已推送过的事项、待跟进状态、用户在任务会话里给的修正 |
| 单次运行轮数 | 同子 agent 上限，收尾轮提示总结 |
| 单次运行时长 | 墙钟上限（如 30 分钟），超时停止该轮，记「超时」，按系统级失败处理 |
| 重叠 | 到点时会话正忙（上次未完或用户正在问）：跳过，记「忙」 |
| 连续失败熔断 | 连续 3 次系统级失败自动暂停任务并推送原因，用户修好后在列表里恢复 |
| 用量可见 | 列表每个任务显示最近 N 次运行的累计用量，异常增长一眼可见 |

## 六、页面

- **定时任务列表**（侧栏入口）：每行名字、规则（人话）、下次运行、启停、最近几次运行的状态点、累计用量；展开看运行列表（时间、结局、是否推送及送达、最终回复首行），点开进任务会话 / Trace。
- 运行结局：**完成·已推送** / **完成·未推送** / **失败** / **超时** / **已停止** / **中断** / **错过** / **忙**。「未推送」与「推送了但投递失败」分开。
- **通知中心**（右上角）：见 §四。
- 编辑：改规则与指令、暂停、删除都在列表页；新建主要靠对话里让 agent 建。

## 七、其余结论

| # | 问题 | 结论 |
|---|---|---|
| 1 | 停机期间错过 | 不补跑，记「错过」并推送 |
| 2 | 系统级失败 | 没能启动、模型调用失败、超时、中断、错过：框架记录并推到默认推送 Channel；agent 判断「没发现」不算失败 |
| 3 | 时区 | 服务器本地时区，列表与 `schedules` 都标出 |
| 4 | 运行的工具 | 全套基础工具 + `push`；不含 `schedule`、`schedules`、`agent` |
| 5 | 删除任务 | 任务会话与 trace 保留，列表不再显示 |
