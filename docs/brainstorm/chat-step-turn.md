# B1：聊天页的「步」与「轮」

**状态：方向已确认，见下方“最终方向”；[B2](../blueprints/archive/chat-reply-footer.md) 已实现并 CLOSED（2026-10-20）。此前五层嵌套、run 底栏、一问一答边界的分析均为已撤回的探索，不作为设计依据。**

## 最终方向（2026-10-20 human）

- 客观载体是 session 和连续的上下文；agent 执行器有待处理输入时工作，AI 产出结果或被打断后休息。工作期间在检查点接入新输入。代码的 run 只是激活执行过程的记录，不定义业务轮。
- 后台任务独立启动和运行，在完成或其他约定时机通过消息推动执行器。现有 owner/session 与来源调用关联仍负责路由和管理，不把后台任务的生命周期塞进业务轮。
- 人看到的通常是人的消息与 AI 回复块，可以用这种交互称呼业务上的“轮”；不要求它与 run、模型调用或单条用户消息一一对应，不构建精确问题归属体系。
- 每个 AI 回复块底部各有一行，所有信息悬停才显示。复制只取该块最后一条回复消息的正文，不跨消息补齐。
- 插嘴前的 AI 块可能只调用了工具、没有说话；复制不到正文是正常情况，不显示复制即可。
- 从简，不留兼容展示路径。聊天显示每条回复对应请求的简要统计，删除聊天专用 run 合计链路；trace 保留完整细节与执行合计，不能用 run 驱动聊天分组。

## 以下为已撤回的探索记录

## 问题

聊天页现在没有把「这一步」和「这一轮」分开表达。悬停信息行一半说的是这一步，一半说的是整轮；看不出哪几步属于同一轮，也看不出新的一轮从哪里开始。

## 概念层级

从大到小：

| 层 | 是什么 | 边界 | 承载的信息 |
|---|---|---|---|
| 会话 session | 一个对话窗口。Root：Channel 入站（Web 会话、一个微信聊天）；Triggered：模块触发（cron 等）；Task：子 agent 的会话，挂在父会话的一次 `agent` 调用下 | 创建到归档 | 消息流、模型、人设、工作目录、后台任务 |
| 上下文段 | `/clear` 或压缩切出的段 | 边界消息 | 只决定模型看到哪些历史；界面消息流不断开，显示分隔条 |
| run（执行） | 认领一批待处理输入，循环若干步直到终态 | 起：用户消息 / 后台回报 / 指令；止：完成、停止、调用失败、轮数用尽、中断、超时 | `ChatRunStats`：耗时、步数、工具数、token、缓存、费用 |
| 步 step | 一次模型调用：思考 / 正文 / 工具调用，加上这些工具的执行 | 一条 `Reply` 消息及其工具结果 | 时间、模型；失败重试只多几次请求，不多出步 |
| 工具执行 | 前台工具当步返回结果；后台工具立即返回「已转入后台」，成为任务 | 一条 `ToolResult` | 状态、参数、输出 |

横跨各层的是**后台任务 job**：它属于会话，可以跨 run 存活。完成时写一条后台回报（`Completion`）：会话空闲就唤醒它，开始新的 run；正在执行就并入当前 run。子 agent 也是 job，背后是一个 Task 会话，有自己的 run 和步。

用户感知的「一问一答」不是系统里的某一层：它从一条用户消息起，到下一条用户消息止，可能包含多个 run；而一个 run 也可能包含多条用户消息。

```
会话
├─ 用户：帮我跑个后台 bash ─────────────┐
│  run 1                                │ 一问一答
│   ├─ 步：bash（后台）→ 任务 #2           │
│   └─ 步：「已经在后台跑了」               │
│  后台回报 #2 ──→ 唤醒                   │
│  run 2                                │
│   ├─ 步：job_output                    │
│   └─ 步：「结果如下……」                  │
├─ 用户：再跑一个 ───────────────────────┤
│  run 3                                │
│   ├─ 步：……                            │
│   │  （执行中用户又发「顺便看下日志」→ 并入 run 3）
│   └─ 步：回答两件事                       │
└─ ……
```

## 现状事实

**层级**

| 层 | 对应数据 | 聊天页现有信息 |
|---|---|---|
| 轮（run） | 一次执行：由用户输入或后台回报唤起，到最后一次回复为止 | `ChatRunStats`：耗时、步数、工具数、token、缓存、费用；锚在该轮最后一条消息（`anchor_id`），结束后才有 |
| 步（step） | 一次模型请求，落成一条 `Reply` 消息 | 时间、模型 |
| 块 | `Reply` 内的思考 / 正文 / 工具调用；工具结果是单独消息，前端并入调用行 | 工具状态、参数、输出 |

- 一轮的起点不只有用户输入：后台任务完成会唤醒空闲的会话，开启新的一轮（`jobs.rs` 的 `wake`）。
- run 执行中到达的新输入（用户追加的消息、后台回报）会并入当前 run（`run.rs` 的 `absorb`），不另起一轮。
- 因此 run 与用户问句不是一一对应：一句问话之后可能有多个 run（派发后台任务 → 回报唤醒 → 再回复）；一个 run 也可能包含多条用户消息。
- 前端目前没有「消息属于哪一轮」的字段；轮的范围只能用相邻两轮的 `anchor_id` 推出来，进行中的轮还没有统计。

**现有界面**

- 每一步下方留一行，悬停时显示：复制（仅有正文的步骤）· 时间 · 模型。
- 轮统计接在**最后一步**的信息行后面，同一行里前半是这一步、后半是整轮。
- 轮以非回复结尾（如以后台回报结尾）时，统计改成常显的独立一行，同一事物有两种形态。
- 「复制」只复制这一步的正文。用户要的往往是整轮的最终回答；而中间步骤的过渡句（如「我来跑几个」）也各自带一个复制按钮。
- 轮与轮之间没有视觉边界。同一轮内连续的步骤间距已收紧，但不同轮之间也是同样的间距。

## 要定的问题

1. **主单位**：悬停信息行以「轮」为单位，还是以「步」为单位？
2. **复制什么**：整轮的最终回答、整轮全部正文，还是逐步复制？
3. **轮的边界**：要不要在视觉上显式区分？由后台回报唤起的新一轮，怎么和上一轮区分开？
4. **步级信息**：每一步的时间、模型，是否还需要在聊天页有入口？还是交给 trace？

## 候选

### A. 步、轮各一行

每一步下方：悬停显示「时间 · 模型」，有正文时带复制。每一轮底部另起一行显示轮级信息：统计 + 复制本轮回答。

- 优点：两种粒度都在，各自归属清楚。
- 缺点：最后一步下方连着两行（步级一行、轮级一行），信息最密；最后一步的步级行和轮级行内容容易重复，比如时间、复制都出现两次。

### B. 只有轮级一行

步不再有信息行。每一轮底部一行，悬停显示：复制本轮回答 · 时间 · 模型 · 统计。步级的时间和模型改到工具行或思考行的悬停提示里，或者只在 trace 看。

- 优点：最简洁；一轮一个操作栏，这也是常见聊天产品的做法。
- 缺点：中间步骤的时间看不到；同一轮里如果中途切换了模型，需要另想办法表达。

### C. 按轮分组

前端把同一轮的消息包成一组：组内间距紧，组间间距宽或加细分隔；后台回报唤起的轮，组头标明来源。组底部是轮级信息行（同 B）；步级信息退到每一步的轻量悬停提示里。

- 优点：轮的边界最清楚，「这几步属于哪一轮」一眼可见。
- 缺点：要推出每条消息的归属。用 `anchor_id` 推大概够用，进行中的轮另行处理；如果推不准，需要后端给消息带上 `run_id`，那就是改契约。

## 初步倾向

以 run 为统计和底栏单位；不再用「我问了一句」解释 run。用户问题与执行次数不是一一对应，底栏的位置、统计的范围、复制的对象需要分别定义，见下方复核建议。步级信息可以退到 trace。

## 决定

| 问题 | 决定 |
|---|---|
| 主单位 | 只有轮级一行（B） |

待定：界面上的「轮」取 run，还是取用户问句（到下一条用户消息为止）。

## 复核建议（待 human 定方向）

### 没对齐的地方

1. **五种概念不是严格嵌套的五层。** 会话内有 run → step → 工具调用；上下文段是另一条轴。`run.rs` 在执行循环内调用 `compact_if_full`，一次 run 可以跨越压缩边界。job 也是会话维度的独立生命周期。
2. **按下一条用户消息截断，只是时间上的分组。** 它不能代表问题的归属：用户已经问了 B，A 的后台结果才回来，按此规则会被归进 B。即使把比例重新计算正确，归属仍然错误。要表达问题完成过程，需要额外的因果关系，当前没有明确消费者，不建议新增。
3. **“执行中新输入都会并入”过于绝对。** `mic-store/src/scheduling.rs::absorb` 只吸收队首连续、与 run 首条输入同 person、非 held 的输入；队首是 Command 时不吸收。停止后 core 也不再吸收。文档中的常见路径不能当作所有输入的契约。
4. **底栏只有一行，不代表其中每项都属于 run。** 现在 `ReplyView` 的时间、模型、复制取自一条 Reply，统计来自整个 run。挪到同一行之前，必须明确各项含义。

### 推荐方向

保留已定的 B：每次执行底部只有一行。**单位取 run，界面用“本次执行”或“执行”，避免用“轮”同时指问题、模型调用和执行。** 不建立一问一答聚合层，也不要求先给所有消息加 run 分组。

| 项目 | 建议语义 |
|---|---|
| 底栏位置 | 独立放在 run 的结束锚点之后，回复结尾与非回复结尾使用同一种形态 |
| 统计 | 本次执行的耗时、步数、token、缓存、费用；包含该 run 实际吸收的追加输入所带来的执行成本 |
| 时间 | 如显示，明确为本次执行结束时间，不沿用末条 Reply 的创建时间冒充执行时间 |
| 模型 | 第一期从底栏移除；每步的模型在 trace 查。以后确有需求，再定义多模型展示 |
| 复制 | 明确标为“复制回复”，推荐只复制该 run 最后一条有正文的 Reply 的全部正文块；不称“复制本轮回答”。如果结尾是失败或停止，正文可能只是进度说明；没有正文就不显示复制 |
| 后台唤醒 | 新 run 保留自己的底栏；Completion 条目继续说明后台任务来源，不把两次执行合为一次 |
| 进行中 | 保留处理中状态；本次执行结束后出现统计底栏，不用上一份统计表示当前执行 |

例如：用户 A → 执行 1（派发任务、回复已开始）→ 底栏 1；后台回报 → 执行 2（回复结果）→ 底栏 2。执行中追加 B，则在同一消息流中显示 B，最后只有一个底栏，表示这一整次执行的成本。

### 实施边界

现有 `anchor_id` 足够定位已结束 run 的统计底栏，**不足以保证精确的消息归属**；相邻锚点之间可能夹有未认领输入。不能用这个区间猜出“复制回复”的目标。复制目标的可靠选择需要在 B2 明确数据来源，不能为省契约改动而启发式回找上一条正文。

`ChatRunStats` 目前没有执行结束时间和回复目标；新增字段、改变统计接口或消息契约都需先写 B2。本节只是方向建议，不批准接口或实现变更。
